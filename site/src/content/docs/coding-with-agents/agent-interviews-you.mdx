Un collègue demande une modification du programme de liste de tâches : « Les
éléments faits encombrent la liste. Vous pouvez la ranger ? Je veux quand même
voir ce que j’ai terminé le mois dernier. » La demande paraît claire jusqu’au
moment de la construire. « Ranger » veut-il dire la commande `clear` que le
programme a déjà, qui supprime les éléments faits ? Ou veut-il dire les
déplacer à un endroit où on peut encore les lire ? Dans cette leçon, l’agent
vous interroge sur la fonctionnalité avant qu’un plan existe. Vous répondez à
ses questions, et vous arrêtez ensemble les mots de la conception. À la fin,
vous comparez deux fichiers à ces mots : la spécification, et le plan qu’une
nouvelle session écrit à partir d’elle.

*Décider s’il faut construire, avant tout* se terminait par des critères de
réussite qu’un inconnu pourrait vérifier. Vous ne pouvez les écrire qu’une
fois que vous savez ce qu’est la fonctionnalité. Pour une fonctionnalité plus
importante, la page des bonnes pratiques de Claude Code recommande que l’agent
vous interroge d’abord et écrive une spécification, puis qu’une nouvelle
session travaille à partir de cette spécification
(@Claude Code best practices). Les questions de l’agent font apparaître les
décisions que vous n’avez pas encore prises, à un moment où les changer coûte
encore peu.

## L’exemple

L’exemple est le programme de liste de tâches de *Votre première session avec
un agent de code*, quelques semaines plus tard. Il a une commande `clear` et
il est découpé en trois modules. Il se trouve dans le dépôt du cours, sous
`site/examples/coding-with-agents/agent-interviews-you/`. Copiez tout ce
dossier à un endroit à part. La copie contient `fixture-repo/`, où l’agent
travaille, un script `check_terms.py` et un dossier `sample/` que la seconde
moitié de la leçon utilise. Pour réinitialiser, supprimez la copie et copiez
de nouveau. Travailler dans une copie garde aussi les fichiers d’instructions
du cours hors de la session, parce que Claude Code, par exemple, charge les
fichiers d’instructions de chaque dossier au-dessus de celui où il démarre
(@Claude Code memory).

La mémoire automatique (auto memory) de Claude Code est activée par défaut
dans les sessions locales. Elle enregistre des notes que l’agent écrit pour
lui-même et les charge dans la session suivante du même projet. Elle range
les notes sous le dépôt git, ou sous la racine du projet hors d’un dépôt
(@Claude Code memory). Dans cette leçon, une note issue de l’entretien
atteindrait la nouvelle session censée démarrer sans elle, et une copie
réinitialisée au même chemin chargerait de nouveau les notes. Lancez donc
chaque session Claude Code de cette leçon avec la mémoire automatique
désactivée. Placez-vous d’abord dans `fixture-repo`, parce que cette commande
démarre l’agent dans le dossier d’où vous la lancez :

```sh
CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 claude
```

Avec un autre agent, vérifiez s’il garde des notes d’une session à l’autre, et
désactivez-les pour cette leçon. Avant de lancer l’agent, regardez la liste
depuis `fixture-repo`.

## Demander l’entretien

Un entretien de conception est une session où l’agent pose les questions et
où vous répondez. Il a lieu avant que l’agent planifie quoi que ce soit ou
écrive du code. Lancez votre agent de code dans `fixture-repo`, avec la
mémoire automatique désactivée comme ci-dessus, et donnez-lui une courte
description de la fonctionnalité avec la demande de vous interroger. Demandez
des questions sur le comportement, les cas limites, les risques et les
compromis, et dites-lui de sauter ce qu’il peut lire dans le code. Dites-lui
quand s’arrêter, et quoi écrire à ce moment-là.

```text
Je veux un moyen de ranger la liste de tâches. Les éléments faits
l’encombrent, mais j’ai toujours besoin de voir ce que j’ai terminé le
mois dernier. Avant de planifier quoi que ce soit ou de modifier du code,
interroge-moi sur cette fonctionnalité. Pose une question à la fois.
Interroge-moi sur le comportement attendu, les cas limites, ce qui
pourrait mal tourner et les compromis, et ne me demande pas ce que tu
peux trouver dans le code. Quand un mot peut avoir deux sens, demande-moi
lequel je veux dire. Continue jusqu’à ce que plus rien ne soit ouvert.
Écris ensuite TERMS.md, une ligne par terme sous la forme exacte
"- **term**: meaning. Avoid: word, word.", et SPEC.md, qui n’emploie que
ces termes. Mets ce que j’ai laissé indécis sous "Questions ouvertes"
dans SPEC.md.
```

La forme des lignes de `TERMS.md` reste en anglais, parce que le script de
contrôle de la leçon lit le mot `Avoid:`. Les termes et leurs sens peuvent
être en français.

Pour Claude Code, la page des bonnes pratiques suggère de nommer son outil
`AskUserQuestion` dans la demande (@Claude Code best practices). L’agent pose
alors ses questions avec cet outil. Un autre agent pose ses questions dans la
conversation.

L’échange ci-dessous est une illustration. Il a été écrit pour cette leçon et
n’a pas été enregistré auprès d’un modèle. Il montre le type de première
question que la demande devrait produire.

<Pitfall title="Une réponse pour arriver au code">

règle : une réponse inventée pour avancer devient une exigence que l’agent
construit. Dites « pas encore décidé », et la spécification range le point
parmi les questions ouvertes.
</Pitfall>

## Écrire les termes

Pendant un entretien, les mots dérivent. Vous dites « fait » et l’agent dit
« terminé ». Une phrase plus loin, la spécification dit « achevé ». Chaque mot
paraît clair à celui qui l’emploie. Une nouvelle session qui lit la
spécification voit trois mots et doit deviner s’ils désignent une chose ou
trois, et certaines de ses suppositions sont fausses.

La solution est un vocabulaire commun : un seul sens convenu pour chaque terme
de la fonctionnalité, écrit, et employé de la même façon dans la
conversation, la spécification, le plan et le code. L’idée vient de la
conception pilotée par le domaine (domain-driven design), une façon de
construire des logiciels décrite par Eric Evans (@Evans 2003). Son résumé de
référence gratuit dit d’employer une seule langue à l’oral, à l’écrit et dans
le code, et de traiter un changement de cette langue comme un changement de la
conception (@Evans DDD Reference). Cette leçon n’en prend que cette partie :
une courte liste de termes, en mots simples, chacun avec les mots à éviter.

Le dossier `sample/` de votre copie contient les fichiers sur lesquels
pourrait se terminer un entretien sur la fonctionnalité d’archivage. Ces
fichiers d’exemple sont en anglais. Voici `sample/TERMS.md` :

```md
# Terms

- **item**: one line of the to-do list, with its text and its done mark. Avoid: task, tasks, entry, entries.
- **done item**: an item marked with `done`. Avoid: completed, finished.
- **archive**: move every done item from the list to `archive.json`, where `archive list` shows it. Avoid: hide, hides, hidden.
- **clear**: delete every done item from the list for good. It never touches `archive.json`. Avoid: purge, wipe.
```

Les mots à éviter sont ceux qui sont apparus pendant l’entretien pour la même
chose, ou pour une autre chose facile à confondre avec elle. « Hide »
(cacher) est sur la liste parce qu’un élément caché est toujours dans
`todos.json`, et qu’un élément archivé n’y est plus.

## Comparer la spécification aux termes

`check_terms.py` lit une liste de termes et affiche chaque ligne d’un autre
fichier qui emploie un mot à éviter. Il compare des mots entiers et ignore la
casse. Laissez la session d’entretien tourner dans son propre terminal, et
ouvrez un second terminal pour le script. Placez-vous en haut de votre copie
et lancez le script sur la spécification d’exemple.

## Planifier à partir de la spécification dans une nouvelle session

La page des bonnes pratiques suggère qu’une nouvelle session réalise la
spécification, parce que son contexte contient alors le travail et rien du
long entretien (@Claude Code best practices). Écrivez aussi le plan dans une
nouvelle session. Terminez la session d’entretien, ouvrez-en une nouvelle dans
`fixture-repo` avec la mémoire automatique toujours désactivée, et demandez un
plan qui emploie la liste de termes.

```text
Lis TERMS.md et SPEC.md. Écris PLAN.md avec les étapes pour construire ce
que décrit SPEC.md, en employant les termes de TERMS.md et aucun autre mot
pour les désigner. Ne modifie encore aucun code.
```

Une fois le plan écrit, lancez le contrôle dessus dans le second terminal,
depuis le haut de votre copie :

```sh
python3 check_terms.py fixture-repo/TERMS.md fixture-repo/PLAN.md
```

Un mot à éviter dans le plan veut dire l’une de deux choses. Soit le plan a
dérapé et vous corrigez le mot, soit la spécification a laissé ouvert un point
que le plan a comblé par une supposition. Dans le second cas, la correction
va d’abord dans la spécification.

3. Écrivez les termes arrêtés pendant l’entretien dans une courte liste, chacun avec son sens et les mots à éviter, et employez les mêmes mots dans la spécification, le plan et le code (@Evans DDD Reference).
4. Comparez la spécification et le plan à la liste de termes. Un mot qui a dérivé est soit une étourderie, soit une décision mal écrite, donc lisez la ligne entière.
5. Commencez le plan dans une nouvelle session qui travaille à partir de la spécification et de la liste de termes, sans l’entretien dans son contexte.
</Recap>

<Habit id="ask-for-the-interview">
La prochaine fois que vous confiez à un agent une fonctionnalité qui demande plus d’une phrase pour être décrite, demandez-lui de vous interroger avant d’écrire un plan.
</Habit>
