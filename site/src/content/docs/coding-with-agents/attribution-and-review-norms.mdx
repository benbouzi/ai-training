Un agent a corrigé un bug dans l’import nocturne des ventes, les tests passent,
et vous êtes sur le point d’ouvrir une pull request. Un relecteur lit ce que
vous envoyez cette semaine et décide de l’attention à y porter. Quelqu’un qui
lira l’historique dans un an voudra savoir qui a fait la modification et qui
l’a vérifiée. Dans cette leçon, nous écrivons le message de commit et la pull
request pour ces deux lecteurs. La première moitié porte sur les accords de
revue de l’équipe, et la seconde sur la façon dont le commit dit qu’un agent a
aidé, et sur ce que seule une personne peut y ajouter.

La [leçon sur la mention de l’aide de l’IA](/safety/saying-ai-helped/) donnait
trois parties à une ligne de mention : ce qu’a fait l’IA, ce que la personne a
vérifié, et qui en répond. Une pull request a besoin des trois mêmes parties,
et un commit les contient sous une forme que les outils peuvent lire.

## Avant de demander une revue

Les règles de revue sont les accords qu’une équipe passe sur la façon de relire
les modifications faites avec un agent. Les équipes les écrivent avec des mots
différents. Voici les points que la plupart partagent.

**L’auteur lit d’abord chaque ligne.** C’est vous qui avez demandé la
modification, et vous en êtes le premier relecteur. Les étapes sont celles de
[la relecture du diff](/coding-with-agents/reviewing-the-diff/). Quand vous
demandez une revue, vous dites au relecteur que vous comprenez la modification
et que vous la pensez juste. S’il trouve une ligne que vous n’avez jamais lue,
il apprend que votre demande voulait dire moins que cela.

**La description dit ce qu’a fait l’agent et ce que vous avez vérifié.** Nommez
la partie que l’agent a écrite, les contrôles que vous avez lancés vous-même, et
ce que vous n’avez pas vérifié. « L’agent a lancé les tests » rapporte ce qu’a
dit l’agent. « J’ai lancé les tests, et le nouveau échoue sur `main` et passe
ici » rapporte ce que vous avez vu.

**Le relecteur lit le diff.** La description dit au relecteur où regarder, et
c’est le diff qui est fusionné. Une description écrite par un agent peut décrire
la modification qu’il voulait faire, et non celle qu’il a faite. La
modification d’un agent passe par les mêmes barrières que toute autre
modification : l’exécution de la CI et l’approbation d’un relecteur. « L’agent
l’a testé » ne remplace ni l’une ni l’autre, parce que les tests de l’agent
font partie de la modification relue.

**La modification est assez petite pour être lue.** Un agent écrit du code bien
plus vite qu’une personne ne peut le relire. Un diff trop gros pour être lu est
survolé ou bloqué. Découpez-le avant de demander. Mettez un renommage mécanique
dans sa propre pull request, et limitez chaque modification à un seul but. Un
rangement que l’agent a fait au passage va dans une pull request à part, ou au
moins dans la description.

Votre équipe a peut-être sa propre liste, souvent dans le fichier d’instructions
pour agents du projet ou dans `CONTRIBUTING`. Là où les deux diffèrent, suivez
la liste de l’équipe. Quand vous n’êtes pas d’accord avec l’une de ses règles,
proposez une modification du fichier et respectez la règle jusqu’à ce que
l’équipe soit d’accord.

## Le dire dans le commit

L’attribution consiste à indiquer dans la modification elle-même qu’un agent y a
contribué, à côté de la personne qui a dirigé et vérifié le travail. Dans un
commit, elle va dans une **ligne de fin** (trailer). Git lit les lignes de fin
dans le dernier paragraphe d’un message de commit, après une ligne vide, sous la
forme `Key: value` (@Git docs git-interpret-trailers). Les outils les lisent à
cet endroit, donc une ligne au milieu du corps qui ressemble à une ligne de fin
n’est que du texte.

Plusieurs formes sont en usage. GitHub affiche un commit comme écrit par
plusieurs personnes quand le message se termine par une ligne
`Co-authored-by: name <email>` pour chacune (@GitHub docs creating-a-commit-with-multiple-authors).
Le noyau Linux demande une étiquette `Assisted-by` qui nomme l’aide de l’IA,
dans un format que donne sa règle (@Linux coding assistants). Claude Code ajoute
par défaut une ligne de fin `Co-Authored-By` à ses commits. Son réglage
`attribution.commit` remplace cette ligne par celle que demande le projet, et
une valeur vide la retire (@Claude Code all settings). Quel que soit l’agent que
vous utilisez, vérifiez la forme que demande le projet, et lisez le bloc de
lignes de fin de chaque commit avant de le pousser.

L’auteur du commit reste vous. Git enregistre un auteur pour chaque commit,
l’identité de la personne qui l’a fait sauf si quelqu’un en définit une autre
(@Git docs git-commit). La ligne de fin ajoute l’agent. Elle ne retire pas votre
nom.

L’exemple de cette leçon se trouve dans le dépôt du cours, sous
`site/examples/coding-with-agents/attribution-and-review-norms/`. L’agent a
écrit `commit-message.txt`, et `trailers.py` lance
`git interpret-trailers --parse` dessus, ce qui n’affiche que les lignes que git
lit comme lignes de fin.

## La signature que seule une personne donne

La ligne de fin `Signed-off-by` est plus ancienne que les agents de code.
`git commit -s` en ajoute une avec le nom de la personne qui committe, et la
documentation de git dit que son sens dépend du projet. Dans les projets du
noyau Linux et de Git, et dans d’autres qui l’ont adoptée, elle certifie le
Developer Certificate of Origin (DCO, certificat d’origine du développeur)
(@Git docs git-commit). Le DCO est une courte déclaration en quatre parties. Avec
nos mots : j’ai fait la contribution, en tout ou en partie, et j’ai le droit de
la soumettre sous la licence du projet, ou elle repose sur un travail open source
antérieur que je peux soumettre, ou une personne qui a certifié l’une de ces
choses me l’a donnée et je ne l’ai pas modifiée. Et j’accepte que la
contribution et ma signature restent dans un registre public (@DCO).

Chaque partie est une déclaration sur les droits et les connaissances d’une
personne, et un agent n’a ni les uns ni les autres. La règle du noyau Linux le
dit directement : un agent d’IA ne doit pas ajouter d’étiquette
`Signed-off-by`. La personne qui soumet la modification lit le code, s’assure que
sa licence convient au projet, signe en son propre nom et répond du résultat
(@Linux coding assistants). Ne signez vous-même qu’après avoir lu la
modification, parce que la signature dit que vous savez d’où vient le code.

Le dépôt d’origine de ce cours est un exemple concret. Le dernier commit sur
`main` au moment de la rédaction de cette leçon se terminait ainsi :

```text
Co-Authored-By: lsimons-bot <bot@leosimons.com>
Assisted-by: Claude:claude-opus-5-5
```

La ligne `Co-Authored-By` nomme un compte de robot, et la ligne `Assisted-by`
nomme l’agent et le modèle. L’auteur du commit est le mainteneur, et le message
n’a aucune signature.

<Recap>
1. Avant de demander une revue, lisez vous-même chaque ligne et découpez une modification trop grosse pour être lue. La pull request dit ce qu’a fait l’agent et ce que vous avez vérifié, et la modification passe par les mêmes barrières de revue et de CI que toute autre.
2. Les relecteurs lisent le diff, et la description leur dit où regarder. Répondez de toute la modification en tant qu’auteur, y compris des parties que l’agent a écrites.
3. Mettez l’attribution dans une ligne de fin du dernier paragraphe du message de commit (@Git docs git-interpret-trailers), sous la forme que demande le projet, comme `Assisted-by` ou `Co-authored-by`.
4. Dans un projet qui utilise le Developer Certificate of Origin, une ligne `Signed-off-by` le certifie, et seule une personne peut la donner. Un agent ne signe jamais, et vous ne signez qu’après avoir lu la modification (@Linux coding assistants).
</Recap>

<Habit id="read-the-trailer-block">
Avant de pousser un commit écrit par un agent, lisez le dernier paragraphe de son
message. Il doit nommer l’agent comme le demande votre équipe, et ne doit pas
contenir de signature que vous n’avez pas donnée.
</Habit>
