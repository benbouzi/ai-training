Dans [la leçon sur les hooks et la CI](/coding-with-agents/ci-and-hooks/), deux
règles d’équipe sont sorties d’une consigne pour entrer dans le projet, où
chaque session les applique. Le plan de la prochaine modification se trouve
souvent encore dans les notes d’une personne ou dans un fil de discussion, et
les remarques de revue qui reviennent sans cesse sont dans d’anciennes pull
requests. Une nouvelle session d’agent démarre sans elles. Dans cette leçon,
nous déplaçons les deux vers un endroit que l’agent lit de lui-même : la
spécification dans l’outil de suivi des tickets de l’équipe, et une remarque de
revue répétée dans un fichier de normes ou dans un contrôle.

Le projet est l’import nocturne des ventes des leçons précédentes :
`importer.py` additionne les exports d’une nuit et convertit chaque montant en
euros avec les taux de `rates.json`. L’équipe veut réimporter une nuit passée
avec les taux de cette nuit-là, et elle a une courte spécification pour cela.

## Mettre la spécification dans l’outil de suivi

Un backlog accessible à l’agent rassemble les spécifications et les tickets de
l’équipe dans son outil de suivi, où les personnes comme les agents peuvent les
lire et les mettre à jour. L’outil de suivi enregistre aussi quel ticket en
bloque un autre. Une spécification dans une note privée aide une personne. La
même spécification sous forme de ticket aide chaque personne de l’équipe et
chaque session d’agent, parce que chacune peut la trouver, la lire en entier et
y rendre compte de son travail.

La spécification des nuits passées a deux parties, et la seconde a besoin de la
première. L’import doit garder les taux de chaque nuit avant de pouvoir
réimporter une nuit passée avec ces taux. La spécification devient donc deux
tickets, chacun avec sa propre liste « terminé quand », et un lien entre eux.
GitHub appelle ce lien « blocked by » (bloqué par) sur un ticket et
« blocking » (bloque) sur l’autre, et il marque un ticket bloqué d’une icône
dans la liste des tickets et sur les tableaux de projet
(@GitHub docs creating-issue-dependencies). L’ordre se trouve alors dans
l’outil de suivi, où le lecteur suivant le voit. Il ne dépend plus de la mémoire
de la personne qui a écrit la spécification.

Avec l’outil en ligne de commande de GitHub, `gh`, les deux tickets
correspondent à deux commandes. Les corps des tickets sont les deux fichiers
`issue-rates.md` et `issue-rerun.md` dans
`site/examples/coding-with-agents/backlog-and-standards/` du dépôt du cours.
`--blocked-by` prend le numéro du ticket à terminer en premier
(@GitHub docs creating-issue-dependencies). La seconde commande ci-dessous
suppose que le premier ticket a reçu le numéro 1. Mettez le numéro de votre
premier ticket à la place s’il est différent. Les titres restent en anglais,
comme dans l’exemple : « garder les taux de chaque nuit » et « importer une
nuit passée avec ses propres taux ».

```sh
gh issue create --title "Keep the rates of each night" --body-file issue-rates.md
gh issue create --title "Import a past night with its own rates" --body-file issue-rerun.md --blocked-by 1
```

Si `gh issue create --help` ne liste pas `--blocked-by`, votre `gh` est plus
ancien que la fonctionnalité. Mettez-le à jour, ou créez le lien sur la page du
ticket dans le navigateur, sous **Relationships** dans la barre latérale.

Dans un autre outil de suivi, cherchez les deux mêmes éléments, peut-être sous
d’autres noms : un ticket avec un corps, et un type de lien pour « celui-ci
attend celui-là ». Utilisez le type de lien. Une personne lit une phrase du
corps comme « à faire après celui des taux », mais seul un lien permet à l’outil
de suivi de marquer le ticket comme bloqué.

## Laisser l’agent la lire en ligne de commande

L’agent atteint l’outil de suivi avec le même outil en ligne de commande. Le
guide de l’éditeur pour Claude Code recommande les outils en ligne de commande
comme la façon de travailler avec des services extérieurs qui coûte le moins de
contexte, cite `gh` pour GitHub, et suggère que l’agent lise le `--help` d’un
outil qu’il ne connaît pas encore (@Claude Code best practices). Voici les
commandes dont l’agent a besoin ici :

```sh
gh issue list
gh issue view 2
gh issue view 2 --json blockedBy,blocking
```

`gh issue list` affiche les tickets ouverts. `gh issue view` affiche un ticket
en entier, et sa sortie a une ligne « Blocked by » et une ligne « Blocking »
quand un lien existe. Avec `--json` et les champs `blockedBy` et `blocking`,
les mêmes liens reviennent en JSON (@GitHub docs creating-issue-dependencies).

La consigne désigne alors l’outil de suivi comme la source du travail, et
personne ne colle la spécification. La transcription ci-dessous est une
illustration et ne reproduit pas les mots d’un modèle précis.

suivi vous permet de créer un jeton (token) avec moins de droits, utilisez-en un pour

version 2.1.283, une session lancée dans un terminal démarre par défaut en mode
automatique, donc vous choisissez le mode Manual délibérément avec
`claude --permission-mode default` (@Claude Code permission modes).

## Écrire une fois une remarque répétée

Les remarques de revue posent un second problème. Une relectrice écrit
« utilisez `Decimal` pour l’argent, pas `float` » sur une pull request, et deux
semaines plus tard elle écrit la même remarque sur la suivante, pour une
modification qu’une autre session a écrite. La remarque est dans l’ancienne pull
request, où aucune nouvelle session ne la lit. La page de Claude Code sur la
mémoire cite deux moments où écrire une règle, qui conviennent ici : l’agent
répète une erreur, ou une revue de code révèle un fait sur le projet qui
manquait à l’agent (@Claude Code memory).

Un fichier de normes est la liste des règles de code de l’équipe qu’aucun outil
ne vérifie. Les relecteurs humains et les agents relecteurs lisent le même
fichier, et vérifient une modification par rapport à lui. Un court
`STANDARDS.md` pour l’import pourrait commencer ainsi :

```markdown
# Standards

Rules that no check enforces. Reviewers block a change that breaks one
of these, and mark every other style point as a suggestion.

## Errors

- An error message names the file it is about, and the row when there is one.
  For example: "nights/2026-09-15/store-03.csv, row 12: 5 fields, expected 4".
```

Le fichier, en anglais comme le reste du projet, dit ceci : ce sont des règles
qu’aucun contrôle n’impose, les relecteurs bloquent une modification qui en
enfreint une et marquent tout autre point de style comme une suggestion. Sa
première règle demande qu’un message d’erreur nomme le fichier concerné, et la
ligne quand il y en a une.

Pour qu’un agent lise le fichier dans chaque session, les instructions du projet
y renvoient. Une ligne `@STANDARDS.md` dans `CLAUDE.md` importe le fichier, et
Claude Code le charge au lancement avec `CLAUDE.md` (@Claude Code memory). Un
relecteur reçoit le même fichier par un lien dans le modèle de pull request ou
dans la liste de vérification de la revue.

Certaines remarques n’ont pas besoin d’une ligne, parce qu’un script peut les
trouver. La remarque sur `float` en fait partie. La
[leçon sur les hooks et la CI](/coding-with-agents/ci-and-hooks/) a montré
comment une règle qui doit tenir à chaque fois devient un hook ou une étape de
CI, et une remarque répétée peut suivre le même chemin. Ce contrôle signale
chaque appel à `float(` dans les fichiers qu’on lui donne. Il est grossier
exprès. Le jour où le code aura besoin d’un float pour autre chose que de
l’argent, rendez le contrôle plus précis à ce moment-là.

## Bloquer sur le fichier, suggérer le reste

Le fichier change aussi ce sur quoi un relecteur peut bloquer. Le guide de revue
de code de Google pour les relecteurs dit que, sur les questions de style, c’est
le guide de style de l’équipe qui décide, et qu’un point de style que le guide ne
couvre pas relève de la préférence personnelle du relecteur. Il propose un
préfixe comme « Nit: » (détail) pour une petite amélioration que l’auteur n’est
pas obligé de faire (@Google eng-practices). Le guide considère que la
conception va au-delà du goût, et un bug ou un problème de conception peut
toujours bloquer une modification. Pour les conventions du code, le fichier de
normes est le guide de style de l’équipe. Une règle du fichier enfreinte, ou un
contrôle en échec, bloque la modification. Tout autre point de style est une
suggestion.

Cela donne une consigne claire à un agent relecteur. Demandez-lui de relire le
diff par rapport à `STANDARDS.md` et de ne marquer une remarque de style comme
bloquante que si elle nomme la règle enfreinte. Demandez-lui d’écrire tout autre
point de style sous la forme « Nit: », et de bloquer sur un bug comme
d’habitude. Quand un relecteur, humain ou agent, bloque sur une question de
goût, l’auteur ne distingue plus les règles du fichier des préférences, et
commence à traiter les deux comme facultatives.

<Pitfall title="Le jeton qui pouvait tout faire">
Une équipe a donné à son agent les identifiants personnels de la responsable
pour l’outil de suivi, parce qu’ils étaient déjà configurés sur la machine. Un
après-midi, quelqu’un a demandé à l’agent de « faire le ménage dans le
backlog ». Il a fermé trente tickets qu’il jugeait périmés, dont quatre qui
attendaient une décision d’un client, et personne ne l’a vu avant la réunion de
planification suivante. L’agent avait besoin de lire des tickets et d’ajouter
des commentaires, et les identifiants permettaient de les fermer et de les
supprimer. Donnez à l’agent des identifiants limités à ce dont la tâche a
besoin, et lisez chaque commande qui modifie l’outil de suivi avant qu’elle
s’exécute.
</Pitfall>

<Recap>
1. Un backlog accessible à l’agent garde les spécifications et les tickets dans l’outil de suivi de l’équipe, où les personnes comme les agents les lisent. Une spécification dans une note privée ou dans une discussion n’atteint personne d’autre.
2. Enregistrez l’ordre du travail avec les liens de l’outil de suivi lui-même. GitHub marque un ticket bloqué par un autre, et `gh issue view` affiche les liens (@GitHub docs creating-issue-dependencies).
3. L’agent lit l’outil de suivi avec un outil en ligne de commande, qui coûte peu de contexte (@Claude Code best practices). Donnez-lui les droits dont la tâche a besoin, et lisez chaque commande qui modifie l’outil de suivi avant qu’elle s’exécute.
4. Quand une remarque de revue revient, écrivez-la dans le fichier de normes que lisent les relecteurs humains et les agents relecteurs, et importez ce fichier dans les instructions du projet (@Claude Code memory). Quand un script peut trouver l’erreur, faites-en un contrôle et supprimez la ligne.
5. Les relecteurs bloquent sur une règle du fichier, un contrôle en échec ou un vrai défaut, et marquent les autres points de style comme des suggestions (@Google eng-practices).
</Recap>
