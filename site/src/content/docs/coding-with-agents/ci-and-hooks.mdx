Dans [la leçon sur les boucles d’autovérification](/coding-with-agents/self-checking-loops/),
vous avez donné à une session d’agent un test à lancer et une règle selon
laquelle le fichier de test était en lecture seule. La règle était une ligne de
votre consigne. Un collègue qui lance sa propre session sur le même dépôt n’a
pas votre consigne, et son agent ne connaît pas la règle. Dans cette leçon,
deux règles d’équipe s’appliquent sans que personne ait à s’en souvenir. Un hook
empêche les outils de modification de l’agent de changer le test dans chaque
session Claude Code du projet, et une tâche de CI (intégration continue,
continuous integration) lance le test sur chaque pull request, quel qu’en soit
l’auteur.

Le projet est le même import nocturne des ventes, avec `test_nights.py` à côté
de `importer.py`, avant la correction. Le test échoue sur le 15 et le 17
septembre, parce que l’import découpe un montant entre guillemets comme
`"1,250.00"` en deux champs.

## Bloquer la modification avec un hook

Les hooks d’équipe sont des scripts qui s’exécutent d’eux-mêmes à des moments
fixes du travail, par exemple avant un commit ou avant qu’un agent modifie un
fichier. Ils vérifient une règle et arrêtent l’étape quand elle n’est pas
respectée. Le guide de l’éditeur pour Claude Code décrit la différence ainsi :
ce que vous écrivez dans les instructions du projet est un conseil que l’agent
peut suivre, et un hook s’exécute à chaque fois, quoi que décide l’agent
(@Claude Code best practices). Un hook impose une règle qu’une instruction peut
seulement demander.

Claude Code a un événement de hook appelé `PreToolUse`, qui s’exécute avant un
appel d’outil (tool call) et peut le bloquer. Le hook reçoit l’appel en JSON (JavaScript
Object Notation) sur son entrée standard, avec le nom de l’outil dans
`tool_name` et ses arguments dans `tool_input`. Pour les outils Edit et Write,
`tool_input` contient le `file_path` du fichier. Quand le hook se termine avec
le code de sortie 2, Claude Code bloque l’appel et montre à l’agent ce que le
hook a écrit sur sa sortie d’erreur standard. Un hook configuré dans
`.claude/settings.json` appartient au projet, et vous committez ce fichier dans
le dépôt, donc chaque session lancée dans le projet reçoit le hook
(@Claude Code hooks).

Voici le réglage. Le `matcher` indique pour quels outils le hook s’exécute, ici
Edit et Write :

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "python3 \"${CLAUDE_PROJECT_DIR}/.claude/hooks/protect_paths.py\""
          }
        ]
      }
    ]
  }
}
```

Et voici la partie du script du hook qui décide. Le script complet est
`protect_paths.py` dans le dépôt du cours :

```python
PROTECTED = [
    "test_nights.py",
    "nights/",
    ".claude/",
    ".github/",
]

REASON = (
    "{path} is protected: agents may not change it. If it must change, stop and tell the user why."
)
```

La liste protège le test et les nuits enregistrées, ainsi que le hook, ses
réglages et le workflow de CI. Sans les deux dernières entrées, un agent bloqué
pourrait modifier le réglage et retirer le hook. Le motif (en anglais dans le
script) nomme le fichier et dit quoi faire ensuite : le fichier est protégé, et
s’il doit changer, l’agent s’arrête et explique pourquoi à l’utilisateur.
L’agent lit ce motif et en déduit sa prochaine étape.

Le hook fonctionne aussi quand Claude Code déplace la session dans un worktree,
qui est par défaut un dossier sous `.claude/worktrees/`. Dans un worktree,
`${CLAUDE_PROJECT_DIR}` garde le dossier dans lequel la session a commencé,
alors que le `cwd` de l’entrée du hook devient le worktree
(@Claude Code worktrees). Le script retire donc la partie
`.claude/worktrees/<name>/` du chemin avant de comparer avec la liste. Sans
cette étape, chaque modification dans un worktree correspondrait à l’entrée
`.claude/` et serait bloquée.

## Lancer les barrières dans la CI

Le hook couvre les sessions d’agent dans Claude Code. Une tâche de CI s’exécute
sur les modifications qui arrivent dans le dépôt, qu’elles viennent d’une
personne, d’un agent ou d’un outil. L’intégration à la CI fait de la chaîne de
CI la barrière commune des modifications d’agents. Les barrières déterministes
que vous avez vues avec la boucle d’autovérification s’exécutent sur chaque pull
request, et l’équipe convient qu’une modification qui ne les passe pas n’est pas
fusionnée.

Dans GitHub Actions, un fichier de workflow se trouve sous
`.github/workflows/`, et une étape `run` réussit ou échoue selon le code de
sortie de sa commande (@GitHub docs workflow-syntax). Un workflow qui s’exécute
`on: pull_request` démarre quand une pull request est ouverte ou rouverte, et
quand de nouveaux commits y sont poussés (@GitHub docs events-that-trigger-workflows).
Voici la tâche de l’import nocturne, dans `checks.yml` :

```yaml
name: checks
on:
  pull_request:
  push:
    branches: [main]
permissions:
  contents: read
jobs:
  gates:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
      - name: Compile the Python files
        run: python3 -m py_compile importer.py test_nights.py
      - name: Run the nightly test
        run: python3 test_nights.py
```

La ligne `uses` nomme l’action qui récupère le code par le hash complet d’un
commit, son SHA (Secure Hash Algorithm), avec la version en commentaire. La
page de GitHub appelle le SHA du commit d’une version publiée le choix le plus
sûr (@GitHub docs workflow-syntax). Git peut déplacer une étiquette (tag) vers
un autre commit (@Git docs git-tag). Un hash de commit ne peut pas être
déplacé, parce qu’il est calculé à partir du commit lui-même. Le dépôt du cours
fige chaque action de la même façon. `permissions` fixe ce que le
`GITHUB_TOKEN` de la tâche a le droit de faire, et GitHub conseille le minimum
dont la tâche a besoin (@GitHub docs workflow-syntax). Cette tâche ne fait que
lire le code.

## Pour aller plus loin en équipe

Le cours de l’Academy The AI-native SDLC playbook (SDLC désigne le cycle de vie
du développement logiciel, software development life cycle) va plus loin qu’un
hook et une tâche. Il a des leçons sur les hooks comme points d’approbation et
sur l’ajout d’un relecteur IA dans la boucle des pull requests
(@Academy ai-native-sdlc-playbook). Voici ces idées avec nos mots, avec ce que
disent les pages de Claude Code sur chacune.

**Un hook peut demander à une personne.** Un hook `PreToolUse` peut aussi
renvoyer une décision en JSON sur sa sortie standard, et l’une des décisions est
`ask`, qui montre à l’utilisateur une demande d’autorisation pour cet appel
(@Claude Code hooks). Un hook peut ainsi faire intervenir une personne à une
étape précise, par exemple une commande de déploiement ou une modification
d’une migration de base de données, et laisser le reste du travail se faire.
Choisissez ces étapes comme vous choisissez toute approbation : les étapes
irréversibles ou qui touchent d’autres personnes.

**Un agent relit la pull request.** Claude Code a un mode non interactif,
`claude -p`, pour la CI et les scripts (@Claude Code best practices). Une tâche
de CI peut s’en servir pour relire le diff de chaque pull request et publier
des remarques classées selon leur importance. Une seconde tâche, avec son propre
prompt, peut relire le même diff pour les seuls problèmes de sécurité, afin que
ces remarques ne se perdent pas parmi les commentaires de style. Les remarques
sont un avis à côté des barrières, et une personne les pèse toujours.

**Une remarque qui revient va dans les instructions.** La première fois qu’une
revue trouve une erreur, corrigez-la dans la modification. La deuxième fois que
le même genre d’erreur revient, ajoutez une ligne aux instructions du projet,
ou un contrôle quand un script peut la trouver. Le guide de l’éditeur conseille
aussi de transformer une instruction en hook quand la règle doit tenir à chaque
fois (@Claude Code best practices).

**Une session neuve donne un second avis.** La session qui a écrit une
modification a tendance à la favoriser. Le guide de l’éditeur propose une
seconde session qui relit la modification sans l’historique de la première
(@Claude Code best practices).

**Les évaluations s’exécutent aussi dans la CI.** Quand le projet est un agent
ou un prompt, les tests comprennent des évaluations des réponses du modèle. Le
cours Construire des agents enseigne comment noter ces réponses, en commençant
par [une grille d’évaluation de ce qu’est une bonne réponse](/building-agents/rubrics/).

<Exercise stretch="Demandez ensuite à votre agent, dans une nouvelle session, d’ajouter une nuit sous nights/ pour le 18. Vérifiez que le hook la bloque, et lisez la raison que l’agent vous rapporte.">
Faites votre propre projet à partir des fichiers du cours. Depuis la racine de
votre clone du dépôt du cours, lancez :

```sh
cp -R site/examples/coding-with-agents/observing-and-debugging/nightly ~/ci-me
cp site/examples/coding-with-agents/self-checking-loops/test_nights.py ~/ci-me/
mkdir -p ~/ci-me/.claude/hooks ~/ci-me/.github/workflows
cp site/examples/coding-with-agents/ci-and-hooks/protect_paths.py ~/ci-me/.claude/hooks/
cp site/examples/coding-with-agents/ci-and-hooks/settings.sample.json ~/ci-me/.claude/settings.json
cp site/examples/coding-with-agents/ci-and-hooks/checks.yml ~/ci-me/.github/workflows/
cd ~/ci-me
git init --initial-branch=main
git add .
git commit -m "Nightly import with a hook and a CI job"
```

Testez d’abord le hook en faisant l’erreur qu’il attrape. Cette commande lui
donne le JSON d’une modification du test et affiche son code de sortie, qui
doit être 2 :

```sh
echo '{"tool_name": "Edit", "tool_input": {"file_path": "test_nights.py"}}' | python3 .claude/hooks/protect_paths.py; echo "exit status $?"
```

Créez sur GitHub un dépôt privé vide que vous pourrez supprimer ensuite. Poussez
ensuite la copie dessus. Remplacez `<url>` par l’adresse que GitHub affiche pour
le nouveau dépôt :

```sh
git remote add origin <url>
git push -u origin main
```

La tâche s’exécute sur le push vers `main` et échoue sur le 15 et le 17. Créez
ensuite une branche, lancez Claude Code dans `~/ci-me`, et demandez-lui de faire
passer le test sans limites, comme dans la première transcription. Vérifiez que
le hook arrête sa modification du test. Si l’agent modifie le test d’une autre
façon, par exemple avec une commande shell, c’est la limite du `matcher` vue
plus haut dans la leçon : remettez le fichier en place avec
`git checkout test_nights.py` et notez ce qu’a fait l’agent. Donnez-lui ensuite
les lignes en échec du journal de la tâche avec la consigne de cette leçon,
poussez sa correction, et ouvrez une pull request.

Un bon résultat : un hook qui a bloqué la modification du test, une exécution
arrêtée en cinq tentatives au plus, une pull request qui ne modifie que
`importer.py`, et une tâche qui passe dessus. Supprimez le dépôt quand vous avez
terminé. Répondez ensuite à une question : quelle règle de votre propre équipe
est écrite aujourd’hui, mais dépend de chaque session qui la lit ?
</Exercise>

<Recap>
1. Les hooks d’équipe s’exécutent à des moments fixes, par exemple avant qu’un agent modifie un fichier, et s’appliquent à chaque session du projet. Une instruction est un conseil que l’agent peut ignorer, et un hook s’exécute à chaque fois (@Claude Code best practices).
2. Un hook `PreToolUse` de Claude Code reçoit l’appel d’outil en JSON et le bloque en se terminant avec le code 2, et l’agent lit ce que le hook a écrit sur la sortie d’erreur standard. Le code 1 est une erreur du hook, après laquelle l’appel a lieu, et un `matcher` sur Edit et Write ne voit pas une commande shell qui écrit le fichier (@Claude Code hooks).
3. L’intégration à la CI lance les barrières déterministes sur chaque pull request, quel que soit l’auteur de la modification. La tâche et un relecteur décident si la modification peut être fusionnée, et l’agent corrige une tâche en échec à partir de son journal, dans les mêmes limites que toute boucle d’autovérification.
4. Figez chaque action d’un workflow sur un SHA de commit complet, et donnez à la tâche seulement les permissions dont elle a besoin (@GitHub docs workflow-syntax).
5. Une règle qui doit tenir à chaque fois va dans un hook ou dans un contrôle de CI. Une remarque de revue qui revient une deuxième fois va dans les instructions du projet, ou dans un contrôle quand un script peut la trouver.
</Recap>

<Habit id="move-a-rule-into-a-check">
La prochaine fois que vous écrivez « toujours » ou « jamais » dans une consigne ou dans un fichier d’instructions du projet, demandez-vous si un hook ou une étape de CI pourrait vérifier cette règle à la place.
</Habit>
