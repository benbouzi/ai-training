Dans cette leçon, nous menons une session complète avec un agent de code.
Nous l’ouvrons dans un petit dépôt et nous lui demandons d’expliquer le code.
Nous lui montrons un test qui échoue et nous le laissons faire une
modification. Puis nous lisons le diff avant de l’accepter. Le dépôt est un
exemple fourni avec ce cours, donc rien de ce que vous faites ici ne peut
toucher votre propre travail.

Un agent de code est un agent qui travaille dans votre terminal ou votre
éditeur avec les outils d’un programmeur : il lit et modifie des fichiers, et
il lance des commandes. Claude Code en est un exemple, et il en existe
d’autres. Les étapes de cette leçon fonctionnent avec n’importe lequel, et
les notes qui nomment Claude Code s’adressent à ceux qui l’utilisent. Partout
où le texte dit « votre agent de code », utilisez celui que vous avez
installé. Si c’est Claude Code, le court cours de l’éditeur explique son
installation et les commandes que cette leçon laisse de côté. Lisez-le après
cette leçon (@Academy claude-code-101). Si vous bloquez, le tuteur du site
peut vous donner des indices sur cette leçon dans votre propre agent.
[Étudier avec le tuteur](/guides/tutor/) explique comment l’installer.

## L’exemple

L’exemple est une commande de liste de tâches d’environ soixante-dix lignes de
Python. Il se trouve dans le dépôt du cours, sous
`site/examples/coding-with-agents/first-session/fixture-repo/`. Copiez ce
dossier hors du dépôt du cours, dans votre dossier personnel, et travaillez
dans la copie. Le dépôt du cours a ses propres fichiers d’instructions pour
agents, et un agent lancé à l’intérieur peut les lire à la place de ceux de
l’exemple. Faites de la copie un dépôt git avec un commit, pour que git puisse
vous montrer ce qui a changé et le remettre en place.

Le programme a besoin de Python 3.9 ou plus récent, et de rien d’autre. Sur
un Mac, le `python3` fourni avec le système suffit, tout comme son `git`. Sur
un Mac neuf, la première commande `git` ou `python3` peut ouvrir une fenêtre
d’Apple qui propose d’installer ses outils de développement pour le terminal
(les Xcode Command Line Tools). Acceptez et attendez la fin de
l’installation. Supprimez ensuite `~/fixture-repo` s’il existe, et relancez
les commandes ci-dessous depuis le début.

Ces commandes récupèrent le dépôt du cours dans votre dossier personnel, en
copient l’exemple et font de la copie un dépôt. Si vous avez déjà un clone du
cours, sautez la ligne `git clone` et mettez le chemin de votre clone dans la
ligne `cp`.

```sh
cd ~
git clone https://github.com/schubergphilis/ai-training.git
cp -R ai-training/site/examples/coding-with-agents/first-session/fixture-repo ~/fixture-repo \
  && cd ~/fixture-repo \
  && git init -q \
  && git add . \
  && git commit -qm "fixture as shipped"
```

Les `&&` entre les commandes arrêtent la suite quand l’une d’elles échoue,
donc git ne tourne jamais dans le mauvais dossier. Si git vous demande qui
vous êtes, suivez son message, puis relancez
`git commit -qm "fixture as shipped"` dans `~/fixture-repo`.

Lancez ces commandes une seule fois. Ensuite, `git checkout -- .` dans la
copie remet chaque fichier dans son état d’origine. Attendez-vous à le faire
au moins une fois. Pour repartir de zéro, supprimez `~/fixture-repo` et
relancez les commandes à partir de la ligne `cp`.

Le dossier contient cinq fichiers : `todo.py`, le programme ; `test_todo.py`,
ses tests ; `todos.json`, une liste de trois éléments committée ;
`README.md` ; et `AGENTS.md`, quatre lignes d’instructions pour l’agent.
Lancez le programme avant de lancer l’agent. Vous voulez savoir à quoi
ressemble « ça marche » avant que quelqu’un d’autre le modifie.

Les exemples de cette leçon ne sont pas notés. Chacun est une commande que

chaque build. Les questions de contrôle viennent plus tard et portent sur la
session, parce que c’est le travail avec l’agent que cette leçon enseigne.

## Lancer l’agent et lui demander d’expliquer

Lancez votre agent de code depuis votre copie de `fixture-repo`. Le dossier
de départ est le monde de l’agent : il y lit et modifie des fichiers, et il y
lance des commandes. Le lancer un niveau trop haut lui donne tout votre
dossier personnel.

Vérifiez un réglage avant votre premier message. Cette leçon est construite
autour du moment où l’agent vous demande votre accord avant de modifier un
fichier, et certains agents démarrent dans un mode qui ne demande pas. Les
versions récentes de Claude Code démarrent en mode automatique (auto mode) :
les modifications de fichiers dans le dossier de travail passent sans
demande, et un second modèle examine la plupart des autres actions à votre
place. Le mode qui demande avant chaque modification s’y appelle Manual, et
`claude --permission-mode default` démarre une session dans ce mode. Dans une
session déjà ouverte, Maj+Tab passe du mode automatique à Manual, et dans
l’extension VS Code, l’indicateur de mode en bas de la zone de saisie fait de
même (@Claude Code permission modes). La partie sur les modes de permission,
plus loin dans cette leçon, explique les autres choix.

Votre premier message n’est pas une tâche. C’est une question, et elle sert à
vérifier que l’agent regarde le même code que vous.

<Prompt model="illustrative" recorded="illustrative">
Explique ce que fait ce dépôt et comment les éléments s’articulent. Ne
modifie rien.
</Prompt>
<Response>
C’est une petite liste de tâches en ligne de commande. `todo.py` enregistre
les éléments dans `todos.json` (ou dans le fichier indiqué par `TODO_FILE`) et
propose trois commandes : `add`, `list` et `done`. `test_todo.py` couvre les
trois opérations avec `unittest`. `AGENTS.md` demande de n’utiliser que la
bibliothèque standard et dit de ne pas modifier `todos.json`. La fonction
`done` reçoit de la ligne de commande un numéro d’élément qui commence à 1,
mais elle l’utilise directement comme indice de la liste, ce qui ressemble à
une erreur de décalage d’une unité.
</Response>

Les transcriptions de cette leçon sont des illustrations : elles montrent à
quoi ressemble un bon échange, sans reproduire les mots d’un modèle précis.
Votre agent formule les choses autrement, et il repérera ou non l’erreur de
décalage d’une unité (off-by-one) sans qu’on le lui demande. Les deux cas
conviennent, parce que vous allez lui donner la preuve.

Remarquez ce que l’agent a lu sans qu’on le lui demande : `AGENTS.md`. La
plupart des agents de code chargent un fichier d’instructions de projet au
démarrage. Les lignes de ce fichier fixent les règles de toute la session, et
vous n’avez pas eu à les répéter. Claude Code lit `AGENTS.md` quand il n’y a
pas de `CLAUDE.md` dans le dossier de départ ni dans un dossier au-dessus.
C’est le cas pour votre copie de l’exemple, et ce n’est pas le cas dans le
dépôt du cours, qui a un `CLAUDE.md` à sa racine (@Claude Code memory).

Beaucoup d’agents de code ont un mode en lecture seule, souvent appelé mode
plan, dans lequel l’agent lit, cherche et lance des commandes pour explorer,
sans rien modifier. Il convient à cette première question. Vous obtenez
l’explication, et l’agent n’agit pas dessus avant que vous l’ayez vérifiée
(@Academy claude-code-101).

Vous avez maintenant une preuve concrète : le fichier qui contient le bug, le
test qui échoue et la mauvaise sortie. C’est le contexte dont l’agent a
besoin. Une consigne sans ces éléments envoie l’agent les chercher, et il
risque de trouver autre chose. Cette recherche a un coût : chaque fichier que
l’agent ouvre en cherchant reste dans la mémoire de la session. Une consigne
courte finit donc par consommer plus de cette mémoire qu’une consigne précise
(@Academy claude-code-101).

## Donner le bon contexte

Repensez à la consigne que vous avez écrite dans *Déléguer une tâche à un
agent* : objectif, contexte, limites, critères d’achèvement (done-criteria). Pour un agent de
code, le contexte est fait de fichiers et de commandes, les limites disent
quels fichiers il peut toucher, et le critère d’achèvement est en général un
test.

Avant de l’écrire, décidez de ce qui doit y figurer. Une partie de la preuve
que vous avez réunie est exactement ce dont l’agent a besoin. L’agent lit une
autre partie plus vite que vous ne pourriez la taper, et une dernière partie
n’a rien à voir avec la tâche.

## La première modification et la demande d’autorisation

Envoyez votre consigne réparée. L’agent lit `todo.py`, propose une
modification et s’arrête. Avant d’écrire le fichier, il vous demande votre
accord.

<Prompt model="illustrative" recorded="illustrative">
Corrige l’erreur de décalage d’une unité dans `done()` de `todo.py` :
`done 1` marque le deuxième élément. Le test qui échoue est
`test_done_marks_the_numbered_item` dans `test_todo.py`. Fais-le passer sans
modifier le test. Ne modifie que `todo.py`. Ne touche pas à `todos.json`.
Terminé quand `python3 -m unittest -q` affiche OK.
</Prompt>
<Response>
Le bug est sur la première ligne de `done()` : `index = number` devrait être
`index = number - 1`. Le contrôle des bornes juste en dessous suppose déjà un
indice qui commence à zéro, donc il n’a pas besoin de changer.

Je voudrais modifier `todo.py` (1 ligne). J’autorise ?
</Response>

Cette question est la demande d’autorisation (permissions prompt). Dans le
mode qu’utilise cette leçon, un agent de code demande avant de modifier un
fichier ou de lancer une commande qui fait plus que lire, et votre réponse est
le moment où votre jugement entre dans la session. Posez la question du rayon
d’impact, comme dans *Pourquoi la sécurité des agents est différente* : une
modification d’une ligne dans un fichier que vous pouvez restaurer avec
`git checkout` a un rayon d’impact à peu près aussi petit que possible.
Approuvez-la.

Certains agents proposent de ne plus demander jusqu’à la fin de la session.
Refusez pour l’instant. La demande est la pause pendant laquelle vous lisez
ce qui va se passer, et cette leçon sert à prendre l’habitude de lire.

## Les modes de permission

La demande à laquelle vous venez de répondre est un réglage parmi d’autres
d’un contrôle plus large. La plupart des agents de code vous laissent choisir,
au début d’une session ou en cours de route, ce que l’agent peut faire sans
demander. Les noms varient d’un agent à l’autre, et l’éventail des choix est
à peu près le même (@Academy claude-code-in-action).

- **Lecture seule.** L’agent lit des fichiers, cherche et lance des commandes
  pour explorer, et il ne modifie rien. Il propose des modifications et vous
  décidez de la suite. Selon l’agent, une commande qui fait plus que lire
  s’arrête ou non pour une demande dans ce mode. C’est le mode plan du début
  de cette leçon.
- **Demander avant chaque action.** Le mode que vous avez utilisé jusqu’ici.
  Chaque modification attend votre réponse, ainsi que chaque commande, sauf
  un ensemble intégré de commandes qui ne font que lire. Vous avez vu cet
  ensemble à l’œuvre pendant l’étape d’explication, quand l’agent lisait des
  fichiers et cherchait sans demander.
- **Accepter les modifications, demander avant les commandes.** Les
  modifications de fichiers dans le dossier de travail passent sans demande,
  ainsi que les commandes courantes de gestion de fichiers sur des chemins de
  ce dossier. Dans Claude Code, cet ensemble comprend la suppression d’un
  fichier et sa modification sur place par un éditeur de flux, donc
  « accepter les modifications » couvre davantage que l’écriture dans un
  fichier. Les autres commandes s’arrêtent toujours pour demander
  (@Claude Code permission modes).
- **Sauter tous les contrôles.** L’agent modifie et lance tout ce qu’il
  décide, et vous le découvrez après coup.

Certains agents ajoutent des modes entre les deux derniers, comme une liste de
commandes approuvées à l’avance qui tournent sans demande, ou un contrôle
automatique qui compare chaque action à votre demande à votre place. Avant
d’en utiliser un, lisez ce que la documentation de votre agent dit qu’il
demande encore. Vérifiez aussi dans quel mode démarre votre agent. Dans Claude
Code, cela dépend de la version, de l’endroit où vous le lancez (un terminal,
un éditeur ou le navigateur) et de vos réglages. Dans les anciennes versions,
cela dépendait aussi de votre abonnement (@Claude Code permission modes).

Chaque mode fixe ce que l’agent peut faire avant que vous ayez l’occasion de
dire non. En lecture seule, c’est ce que l’agent lit, donc le pire cas est
qu’il répète une chose qu’il n’aurait pas dû voir. Avec la demande activée,
c’est une action : la modification ou la commande que vous avez approuvée.
Accepter les modifications l’étend à chaque fichier du dossier de travail.
C’est acceptable dans un dépôt sous gestion de versions, parce que `git diff`
vous montre ce qui a changé et que `git checkout -- .` remet en place les
fichiers suivis, et la partie suivante fait de cette relecture une habitude.
Connaissez la limite de cette remise à zéro : un fichier supprimé par l’agent
et jamais committé ne revient pas. Sauter tous les contrôles l’étend à tout ce
que le shell peut atteindre, c’est-à-dire, sur votre propre machine, chaque
fichier qui vous appartient, comme le disait *Pourquoi la sécurité des agents
est différente*. N’utilisez ce mode que dans un bac à sable, c’est-à-dire un
conteneur ou une machine virtuelle créé pour la session, sans accès à
internet, sans rien dedans qui vous manquerait, et sans aucun identifiant. La
documentation de l’éditeur dit la même chose sur l’isolation et l’accès à
internet (@Claude Code permission modes).

Choisissez le mode tâche par tâche, comme vous avez dimensionné la consigne.
Une question ou un plan demande la lecture seule. Une première modification
dans un projet, ou toute modification dans un projet que vous ne connaissez
pas, garde la demande activée, parce que la demande est l’endroit où vous
apprenez comment cet agent se comporte dans ce code. Une modification d’un
type que vous avez déjà relu, dans un arbre de travail que git peut
restaurer, peut accepter les modifications, et vous lisez alors tout le diff
à la fin, à l’endroit où vous auriez lu chaque demande. Le mode décide de ce
que vous voyez avant que cela se produise. Il ne dit rien de la qualité du
comportement de l’agent.

en lecture seule et demandé à l’agent d’expliquer le bug, et il a proposé une
correction d’une ligne. Vers quel mode passez-vous pour faire la
modification ?
</Scenario>

## Relire le diff

L’agent dit qu’il a terminé. Il dit peut-être même que les tests passent. Ne
le croyez sur parole ni pour l’un ni pour l’autre. Regardez ce qui a changé.

```sh
git diff
```

```diff
-    index = number
+    index = number - 1
```

Lancez ensuite le contrôle que vous avez nommé dans la consigne. Le critère
d’achèvement était le vôtre, donc c’est vous qui le lancez.

```sh
python3 -m unittest -q 2>&1 | tail -1
```

```text
OK
```

Le cours ne vérifie pas cette sortie, parce que c’est votre agent qui a
produit la modification. C’est ce que vous devriez voir si la correction est
celle ci-dessus. Si vous voyez autre chose, relisez le diff avant de demander
davantage à l’agent.

<Pitfall title="Accepter un diff que vous n’avez pas lu">
Un ingénieur demande à un agent de corriger un test qui échoue, voit « tous
les tests passent » dans la réponse, et accepte. L’agent avait changé la
valeur attendue du test pour qu’elle corresponde à la sortie boguée. Les tests
passaient bien. La règle : le résumé de l’agent est une affirmation, le diff
est la preuve, et un test qui passe ne prouve quelque chose que si vous
vérifiez aussi que le test n’a pas bougé. Lisez chaque ligne que l’agent a
modifiée, à chaque fois.
</Pitfall>

## Les sessions et le contexte

Tout ce que vous avez dit et tout ce que l’agent a lu dans cette session se
trouve dans sa fenêtre de contexte (context window), la mémoire de travail de l’agent. La
fenêtre de contexte explique comment l’agent a pu répondre une fois à
« explique ce dépôt », puis corriger le bug sans relire les tests. Les tests
étaient déjà dans le contexte.

C’est aussi la raison pour laquelle les sessions doivent se terminer. Le
contexte a une taille fixe, et à mesure qu’il se remplit, les premiers
éléments disparaissent ou sont résumés. Une longue session qui dérive d’une
tâche sans rapport à une autre fait chacune moins bien. L’habitude à prendre :
une tâche, une session. Quand vous avez relu le diff et que les tests
passent, terminez la session et ouvrez-en une nouvelle pour la tâche
suivante.

La plupart des agents résument la session pour vous quand le contexte est
presque plein, et beaucoup vous laissent demander un résumé plus tôt. Le
résumé garde ce que l’agent juge important, qui n’est pas toujours ce dont
vous avez besoin ensuite. Quand vous en demandez un, dites ce qu’il doit
garder : la tâche, les fichiers touchés, et le contrôle qui reste à lancer
(@Academy claude-code-in-action). Dans Claude Code, la commande `/compact`
suivie de ce sur quoi se concentrer demande ce résumé
(@Claude Code how it works).

<Recap>
1. Lancez l’agent dans le dossier qui constitue le monde de la tâche, et demandez-lui d’expliquer avant de lui demander de modifier.
2. Trouvez d’abord la preuve vous-même : le fichier, le test qui échoue, la mauvaise sortie. Mettez-les ensuite dans la consigne, avec des limites et un critère d’achèvement.
3. La demande d’autorisation est le moment où votre jugement entre en jeu. Pesez le rayon d’impact (blast radius), et gardez la demande activée.
4. Choisissez le mode de permission tâche par tâche : la lecture seule pour une question, la demande pour une première modification dans un projet, l’acceptation des modifications seulement là où git peut restaurer ce que vous n’avez pas lu, et le saut de tous les contrôles seulement dans un bac à sable.
5. Le résumé de l’agent est une affirmation. Le diff est la preuve, et c’est vous qui lancez le contrôle que vous avez nommé.
6. Donnez à chaque tâche sa propre session. Réinitialisez l’exemple et repartez à neuf.
</Recap>
