Un agent de code a besoin d’une clé d’API, ou d’une connexion qui joue le
même rôle, pour atteindre son modèle. La clé vous est facturée, et quiconque
la détient peut dépenser sur votre compte, en votre nom. Dans cette leçon,
nous prenons un agent d’exemple dont la clé se trouve dans un fichier de
réglages qu’il peut lire et committer, et nous sortons la clé des fichiers
qu’il peut lire, en deux étapes. Nous passons ensuite un petit détecteur de
secrets (secret scanner) sur l’exemple et sur la transcription de la session,
et nous terminons par la règle à suivre pour une clé que vous pensez
divulguée.

L’exemple est un petit programme qui tient lieu de votre agent de code. Il
n’appelle jamais de modèle. Il fait la seule chose dont parle cette leçon :
trouver une clé au démarrage et dire d’où elle vient. Les noms de réglages
qu’il utilise sont proches de ceux de Claude Code, et le texte indique à quel
vrai réglage correspond chaque étape, vérifié dans la documentation de
l’éditeur à la date donnée en fin de leçon (@Claude Code settings). Les autres
agents de code ont les trois mêmes emplacements pour une clé, sous d’autres
noms. Toutes les clés de l’exemple sont fausses. Vous n’avez besoin de votre
vraie clé pour aucune étape.

## Où l’exemple garde sa clé aujourd’hui

L’exemple se trouve dans le dépôt du cours, sous
`site/examples/coding-with-agents/keys-and-secrets/fixture-repo/`. Copiez ce
dossier ailleurs, ou travaillez dans un clone du dépôt du cours, et placez-vous
dedans. Le dépôt du cours ignore tous les fichiers `.env`, donc le fichier de
secrets de l’application est committé sous le nom `env.sample`. Lancez
`cp env.sample .env` une fois avant de commencer. `git checkout -- .` remet en
place chaque fichier suivi.

Le dossier contient `agent.py`, l’agent d’exemple, `vault.py`, qui remplace
dans cette leçon l’outil en ligne de commande d’un gestionnaire de mots de
passe, `scan.py`, le détecteur, un fichier `.env` avec deux faux secrets
d’application, un `transcript.txt` issu d’une session précédente, et
`.agent/settings.json`, le fichier de réglages de l’agent. Ouvrez ce fichier.

```json
{
  "env": {
    "AGENT_API_KEY": "sk-fake-lesson-key-0000-0000-0000-c0de"
  },
  "permissions": {
    "deny": []
  }
}
```

Le bloc `env` définit une variable d’environnement pour chaque session, et ici
il définit la clé. Lancez l’agent, et il vous le dit.

## Première étape : la clé devient une variable d’environnement

Supprimez le bloc `env` de `.agent/settings.json`. Le fichier contient alors
`{"permissions": {"deny": []}}`. Donnez maintenant la clé à l’agent par votre
shell. Où le shell la trouve-t-il ? Dans votre gestionnaire de mots de passe.
La plupart des gestionnaires de mots de passe ont un outil en ligne de
commande qui vous demande de déverrouiller le coffre et affiche un secret.
`vault.py` remplace cet outil dans la leçon. Il affiche la fausse clé, et la
leçon fonctionne sans gestionnaire de mots de passe. Le détecteur ne signale
jamais `vault.py`, parce que le script assemble la clé à partir de morceaux à
l’exécution et qu’aucun fichier ne contient la chaîne entière.

<Predict id="run-agent-env" title="Lancer l’agent avec la clé dans l’environnement"
  answer={`key sk-fake-...c0de from environment variable AGENT_API_KEY
deny rules: none`} run="coding-with-agents/keys-and-secrets/key_from_environment.py">
Définissez la variable pour cette seule commande à partir de la sortie du
coffre, et lancez l’agent.

```sh
AGENT_API_KEY="$(python3 vault.py)" python3 agent.py
```
</Predict>

L’agent fonctionne de la même façon, et aucun fichier du dépôt ne contient la
clé. Pour Claude Code, la variable est `ANTHROPIC_API_KEY`. Quand elle est
définie, il n’y a pas de connexion par le navigateur : Claude Code affiche la
clé qu’il a trouvée et vous demande de la confirmer
(@Claude Code authentication). Créez cette clé comme clé personnelle dans la
Claude Console et enregistrez-la dans le gestionnaire de mots de passe dès
que la console l’affiche. Une clé personnelle agit en votre nom et cesse de
fonctionner quand vous quittez l’organisation. Une clé partagée agit au nom
d’une seule personne pour tous ceux qui la détiennent, et elle cesse de
fonctionner pour tout le monde quand cette personne part
(@Claude docs authentication).

Définir la variable dans le fichier de démarrage de votre shell (`.zshrc`,
`.bashrc`) met la clé dans un autre fichier en texte clair, et chaque
programme que vous lancez peut la lire. La ligne ci-dessus interroge le
coffre à chaque fois. Cela fait une demande de plus par session, et c’est
l’étape qui garde la clé hors de tout fichier.

## Deuxième étape : un assistant de clé, et des règles d’interdiction pour les fichiers qui restent

La deuxième modification supprime la demande sans faire revenir le fichier.
Au lieu que vous alliez chercher la clé pour la lui remettre, l’agent lance
lui-même la commande du coffre au démarrage. Modifiez `.agent/settings.json`
ainsi :

```json
{
  "keyHelper": "python3 vault.py",
  "permissions": {
    "deny": ["Read(./.env)", "Edit(./.agent/settings.json)"]
  }
}
```

deny rules: Read(./.env), Edit(./.agent/settings.json)`} run="coding-with-agents/keys-and-secrets/key_from_helper.py">


Dans Claude Code, le réglage s’appelle `apiKeyHelper` : une commande shell qui
renvoie la clé, lancée au démarrage puis de nouveau après cinq minutes par
défaut (@Claude Code authentication). Le fichier de réglages contient alors le
nom d’une commande, qu’on peut committer sans risque, et le gestionnaire de
mots de passe contient la clé.

Les règles d’interdiction (deny rules) couvrent les secrets qui restent dans
le dépôt parce que l’application en a besoin. `.env` contient en général un
mot de passe de base de données ou un jeton (token) de messagerie, et un agent de code
le lit aussi facilement que n’importe quel autre fichier. Une règle
d’interdiction `Read(./.env)` empêche les outils de fichiers de Claude Code de
l’ouvrir, et la documentation de l’éditeur cite une limite qui compte ici :
la règle couvre les outils intégrés et les commandes de fichiers que l’outil
reconnaît, comme `cat` et `head`, et elle ne couvre pas un script qui ouvre le
fichier lui-même. Pour un contrôle qui tienne face à tous les processus, la
même page renvoie au bac à sable, qu’une leçon ultérieure de ce cours traite
(@Claude Code permissions). La règle `Edit` sur le fichier de réglages empêche
l’agent de modifier sa propre liste d’interdictions. Claude Code traite déjà
une écriture sous `.claude/` comme un chemin protégé pour lequel les modes
habituels demandent une autorisation, et une règle d’interdiction
`Edit(./.claude/settings.json)` est la forme explicite de la même décision
(@Claude Code permission modes). L’agent d’exemple affiche les règles sans
les appliquer, parce que les appliquer est le travail du vrai outil.

Dans une règle `Read`, Claude Code lit un chemin qui commence par `./`, ou
sans préfixe comme `/` ou `~/`, comme relatif au dossier dans lequel Claude
Code démarre. Il lit ces motifs comme git lit `.gitignore`, donc un nom sans
dossier s’applique dans chaque dossier sous le dossier de départ.
`Read(.env)` et `Read(**/.env)` bloquent les mêmes fichiers : chaque `.env`
du dossier de départ ou d’un dossier en dessous, et aucun dans un dossier
parent (@Claude Code permissions). Quand Claude Code démarre à la racine de
votre clone du dépôt du cours, le `.env` de l’exemple est cinq dossiers plus
bas. Utilisez alors `Read(**/.env)`, parce que ce motif indique la profondeur
dans la règle elle-même.

Une entrée `.gitignore` fait un autre travail. Elle garde `.env` hors des
commits, et elle ne fait rien contre la lecture du fichier par l’agent, parce
que l’agent lit le dossier de travail, sans passer par l’historique du dépôt.

<Pitfall title="L’agent a lu .env et l’a gardé">
Un ingénieur demande à un agent d’ajouter un test pour le client de
messagerie. L’agent lit `.env` pour connaître le format de la configuration,
et il écrit le vrai jeton de messagerie dans le nouveau fichier de test comme
valeur d’exemple. Le diff est au vert, le test passe, et le jeton est committé
avec le test. La règle : un secret que l’agent peut lire est un secret qu’il
peut écrire n’importe où. Interdisez la lecture avant le début de la session,
et analysez le diff avant de committer.
</Pitfall>

## Analyser l’exemple et la transcription

Vous avez déplacé la clé à la main, et c’est une main qui oublie un fichier.
Un détecteur de secrets est un programme qui lit chaque fichier à la
recherche de chaînes qui ressemblent à une clé ou à un mot de passe, et qui
signale chacune avec un nom de fichier et un numéro de ligne. Les vrais
détecteurs connaissent des centaines de formats d’éditeurs et vérifient aussi
l’historique git. gitleaks en est un, et c’est un logiciel libre (@Gitleaks).
`scan.py` le remplace dans la leçon, avec les faux formats de l’exemple et les
deux motifs dont part tout détecteur : une affectation de mot de passe, et une
longue chaîne d’apparence aléatoire après un préfixe qui ressemble à une clé.

`transcript.txt` contient la clé. Lors d’une session précédente, quelqu’un a
demandé à l’agent comment il était configuré, l’agent a lu son fichier de
réglages et cité la clé dans sa réponse, et la transcription l’a gardée. Une
transcription est un fichier comme un autre. Elle peut finir dans un dossier
de journaux, ou quelqu’un peut la coller dans un signalement de bug. À partir
de maintenant, considérez cette clé comme exposée.

## Une clé que vous pensez divulguée

La question de la transcription a une seule réponse : révoquer d’abord,
enquêter ensuite. Une clé divulguée est vite utilisée, et une rotation coûte
peu. Dans la Claude Console, la page des clés a une action **Disable**
(désactiver), réversible, et une action **Delete** (supprimer), définitive, et
le conseil de l’éditeur pour une clé en laquelle vous n’avez plus confiance est
de la désactiver ou de la supprimer (@Claude docs authentication). Créez une
nouvelle clé, enregistrez-la dans le gestionnaire de mots de passe, et
relancez l’agent par l’assistant. Rien d’autre ne change dans votre
installation, parce que rien d’autre ne contenait la clé. Cherchez ensuite
comment la fuite s’est produite, pour qu’elle ne se produise qu’une fois.

La même page conseille une date d’expiration à la création d’une clé. Une clé
qui expire dans trente jours limite la durée pendant laquelle une copie
divulguée fonctionne, et elle ne dispense pas de garder la clé hors des
fichiers (@Claude docs authentication).

<Recap>
1. La clé d’un agent de code vous est facturée. Utilisez une clé personnelle, jamais une clé partagée, et gardez-la dans un gestionnaire de mots de passe (@Claude docs authentication).
2. Une clé ne va jamais dans un fichier que l’agent peut lire et committer. Le fichier de réglages partagé est les deux à la fois. Transmettez la clé par une variable d’environnement définie à partir du gestionnaire de mots de passe, ou laissez un assistant de clé la récupérer au démarrage (@Claude Code authentication).
3. Interdisez à l’agent la lecture des secrets qui restent dans le dépôt, comme `.env`. `.gitignore` garde un fichier hors des commits et ne fait rien contre sa lecture par l’agent (@Claude Code permissions).
4. Passez un détecteur de secrets sur le dossier de travail et sur la transcription, et lisez chaque ligne du rapport.
5. Une clé qui apparaît là où elle ne devrait pas est révoquée d’abord, et l’enquête vient ensuite (@Claude docs authentication).
</Recap>
