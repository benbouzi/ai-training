Dans cette leçon, vous recevez un signalement de bug qui dit « échoue
parfois », et vous le transformez en cause confirmée avant qu’un agent de code
modifie une ligne. Le programme est un petit import nocturne qui additionne les
exports de ventes de huit magasins. Le cours le garde comme exemple, pour que
tout le monde débogue le même code et les mêmes données. Voici le signalement.

```text
L’import nocturne des ventes a échoué le mardi 15 et le jeudi 17, et il a
bien tourné le 14 et le 16. Personne n’a modifié le code. Je pense que le
téléchargement des taux de change est parfois en retard la nuit et laisse
un rates.json à moitié écrit. Vous pouvez demander à l’agent de rendre le
téléchargement plus fiable ?
```

Le signalement contient un symptôme, deux dates et une théorie. Un agent à qui
l’on remet ce signalement reçoit une théorie à partir de laquelle travailler et
une demande de correction, et la correction qu’il écrit vise la théorie. Exiger
une cause reproduite et expliquée avant tout correctif évite que la correction
devienne un second bug (@Brilliant VER).

## Reproduire d’abord

« Parfois » veut dire que vous ne savez pas encore de quoi dépend l’échec. La
première étape consiste à relancer le cas en échec, de la même façon, et à voir
s’il échoue à chaque fois. L’exemple garde les exports de chaque nuit dans
`nightly/nights/<date>/`, un fichier CSV (comma-separated values, valeurs
séparées par des virgules) par magasin, et la tâche nocturne lance
`python3 importer.py nights/<date>/*.csv` depuis `nightly/`. Le script du cours
lance cette commande trois fois pour chacune des quatre nuits et affiche le
résultat de chaque exécution, avec le total pour une nuit qui passe.

## Lire ce que le système a enregistré

fait, au-delà de ce que son code dit qu’il devrait faire : le journal qu’il
écrit, les fichiers qu’il lit, la sortie et le code de sortie. Le code vous dit
ce qui devrait se passer, et le journal vous dit ce qui s’est passé
(@Brilliant VER). L’import écrit une ligne de journal par étape. Placez le
journal d’une nuit en échec à côté de celui d’une bonne nuit.

## Diviser par deux ce qui reste

Isoler un défaut consiste à le réduire jusqu’à sa cause par étapes, où chaque
étape change une seule chose et donne une seule observation. Avec huit fichiers
suspects, le plus rapide est de les diviser par deux. Lancez l’import sur la
moitié des fichiers. Si cette moitié passe, la mauvaise ligne est dans l’autre
moitié, et si elle échoue, la mauvaise ligne est dans celle-ci. Chaque
exécution écarte la moitié de ce qui reste, donc huit fichiers demandent trois
exécutions, et une quatrième confirme le dernier. Le motif shell
`store-0[1-4].csv` choisit quatre fichiers par leur nom.

```sh
cd nightly
python3 importer.py nights/2026-09-15/store-0[1-4].csv
python3 importer.py nights/2026-09-15/store-0[5-6].csv
python3 importer.py nights/2026-09-15/store-05.csv
python3 importer.py nights/2026-09-15/store-06.csv
cd ..
```

Notez ce que chaque exécution a écarté, une ligne par exécution : les magasins
1 à 4 sont écartés, les magasins 7 et 8 sont écartés, le magasin 5 est écarté,
et le magasin 6 échoue seul. La division par deux fonctionne le mieux quand
l’échec a une seule cause. Si les deux moitiés avaient échoué, la note le
montrerait tout de suite, et vous diviseriez chacune par deux.

store-06.csv est maintenant assez court pour être lu.

```text
date,store,currency,amount
2026-09-15,store-06,GBP,449.30
2026-09-15,store-06,GBP,642.20
2026-09-15,store-06,GBP,"1,250.00"
2026-09-15,store-06,GBP,432.53
```

La quatrième ligne a un montant de mille ou plus, que le système du magasin
écrit entre guillemets et avec une virgule. Lisez `read_rows` dans
`importer.py` avec cette ligne en tête : elle découpe chaque ligne à chaque
virgule, donc `"1,250.00"` devient deux champs et la ligne en a cinq. Cette
cause explique tout le signalement : les nuits en échec sont les nuits avec une
grosse vente, et l’heure n’y est pour rien. La condition est maintenant
précise. L’import échoue quand un export contient un montant de 1 000 ou plus.

La même division par deux fonctionne sur les commits comme sur les fichiers.
Quand un défaut est apparu entre une version qui marchait et une version qui ne
marche pas, `git bisect` fait une recherche par dichotomie sur les commits
entre les deux. Il extrait un commit à la fois, vous le marquez bon ou mauvais,
et il s’arrête sur le commit qui a introduit le défaut (@Git docs git-bisect).

tout ce qu’ont trouvé la reproduction et la division par deux : la commande qui
échoue, le fichier et la ligne, la raison, ce qui a été écarté, et ce que veut
dire « terminé ». La transcription est une illustration, sans reproduire les
mots d’un modèle précis.

<Recap>
1. Reproduisez le défaut avant que quiconque modifie le code. Relancez l’entrée en échec et écrivez les étapes, et « échoue parfois » devient une condition précise et le test que la correction doit passer (@Brilliant VER).
2. L’observation d’un système en marche consiste à lire ce qu’il a enregistré, le journal, la sortie et le code de sortie, à côté d’une exécution qui a marché. Le journal montre jusqu’où est allée l’exécution en échec, et une théorie sur une étape que l’exécution a terminée est écartée.
3. Isoler un défaut consiste à diviser les suspects par deux : une modification, une observation, et une note de ce qui a été écarté. La même division sur les commits s’appelle `git bisect` (@Git docs git-bisect).
4. Donnez à l’agent une consigne avec la cause reproduite et expliquée et un critère d’achèvement tiré de la reproduction, et vérifiez la correction en lançant vous-même ces étapes.
</Recap>

<Habit id="rerun-before-you-fix">
La prochaine fois qu’un signalement de bug dit qu’une chose échoue parfois, relancez trois fois le cas en échec et écrivez les étapes avant d’ouvrir le code ou de demander une correction à un agent.
</Habit>
