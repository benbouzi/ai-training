Pendant qu’un agent travaille sur une tâche, vous l’attendez. Une deuxième
session d’agent peut utiliser ce temps pour une autre tâche, et une troisième
pour une troisième. Faire tourner des sessions parallèles multiplie ce qui est
fait, et multiplie aussi les façons dont le travail tourne mal. Deux agents
peuvent modifier le même fichier. Une session peut attendre pendant une heure
une réponse que vous avez oublié de donner. Organiser ce genre de travail et le
surveiller est une compétence à part entière (@Brilliant BLD).

Dans cette leçon, vous faites tourner deux sessions côte à côte sur un petit
projet. Le projet est le module de livraison d’une boutique en ligne, dans le
dépôt du cours sous `site/examples/coding-with-agents/parallel-sessions/shop/`.
`shipping.py` contient une fonction, `quote`, qui donne le prix d’un colis en
euros (EUR) : 4,00 plus 1,50 par kilo entamé. `test_shipping.py` la teste,
`README.md` la documente, et `python3 check.py` lance les tests et chaque
exemple `>>>` du README. La leçon a deux tâches. La modification de l’API
(interface de programmation, application programming interface) fait facturer
à `quote` 0,75 par demi-kilo entamé. La tâche de documentation ajoute au README
une section d’utilisation avec des exemples.

## Donner à chaque session son propre worktree

Des sessions qui tournent dans un même dossier partagent tous les fichiers, donc
la modification à moitié faite d’un agent se retrouve dans l’exécution des tests
de l’autre. Les worktrees de git règlent ce problème. Un worktree est un dossier
de travail supplémentaire du même dépôt, avec sa propre branche et ses propres
fichiers. Tous les worktrees d’un clone partagent un seul historique, et un
commit fait dans l’un d’eux est visible tout de suite dans les autres. Git garde
quelques éléments par worktree, comme `HEAD` (la branche extraite) et l’index
(ce qui est indexé pour le prochain commit). Il partage le reste, y compris
chaque branche et chaque étiquette. Par défaut, git refuse d’extraire une
branche dans un nouveau worktree quand un autre worktree l’a déjà extraite
(@Git docs git-worktree).

Voici les commandes, lancées dans le dossier du projet `shop` sur `main`.
Chaque `add` crée une nouvelle branche à partir de `main` et l’extrait dans un
nouveau dossier à côté de `shop` :

```sh
git worktree add -b api-half-kilo ../shop-api
git worktree add -b docs-usage ../shop-docs
git worktree list
```

Une fois le travail fusionné, `git worktree remove ../shop-api` supprime le
dossier (@Git docs git-worktree). La branche reste jusqu’à ce que vous la
supprimiez.

## Tenir une note par session

Vous pouvez suivre de près une seule session à la fois. Pendant que vous lisez
le diff de l’une, l’autre peut échouer à son contrôle ou s’arrêter pour vous
poser une question. Tenez une note écrite, une ligne par session, avec le
worktree et sa branche, la tâche, le moment où vous la regardez ensuite, et si
elle attend votre réponse :

```text
shop-api   api-half-kilo  prix par demi-kilo entamé       point à 10:40  attend ma réponse : non
shop-docs  docs-usage     section Usage dans README.md    point à 10:40  attend ma réponse : oui, question sur la phrase du 0 kg
```

Mettez la ligne à jour chaque fois que vous regardez une session. Une session
qui indique « attend ma réponse : oui » passe en premier, parce qu’elle ne fait
rien tant que vous n’avez pas répondu. Quand la note a plus de lignes que vous ne
pouvez en vérifier dans le temps que prennent les sessions, vous en faites
tourner trop.

## Savoir ce que les worktrees partagent

`git stash` met de côté des modifications non committées dans une pile, le
stash. Git range l’entrée la plus récente du stash dans la référence
`refs/stash` et les plus anciennes dans le journal de cette référence
(@Git docs git-stash), et chaque référence sous `refs/` est partagée par tous les
worktrees du clone (@Git docs git-worktree). Il y a donc un seul stash pour
toutes les sessions.

<Pitfall title="Deux sessions qui n’ont jamais touché le même fichier">
Un développeur faisait tourner deux sessions dans deux worktrees d’un même
clone. La session de l’API a mis sa propre modification dans le stash pour
essayer quelque chose, et plus tard la session de documentation y a mis son
README à moitié fait. Quand la session de l’API a lancé `git stash pop` pour
récupérer sa modification, git a appliqué l’entrée la plus récente, la
modification de la documentation, dans le worktree de l’API. Aucun conflit de
fusion et aucune erreur ne l’ont montré. Dites à chaque session de ne pas
toucher au stash et de committer son travail en cours à la place.
</Pitfall>

Le reste de ce que partagent les sessions demande une décision avant qu’elles
démarrent. Donnez à chaque session sa propre copie de ce qu’elle peut avoir par
worktree, comme l’installation des dépendances et un fichier de base de données
de test. Quand une session doit lancer un serveur, choisissez-lui un port.
Laissez de côté ce qui n’existe qu’une fois : le stash, la branche `main`, dans
laquelle vous seul fusionnez, et un serveur de développement sur un port fixe.
Pour ce dernier, dites aux agents de lancer le build ou le contrôle, sans
démarrer le serveur. Claude Code partage aussi les approbations de permissions
entre worktrees. Dans une session en worktree, une réponse « Yes, and don’t ask
again » (oui, et ne plus demander) pour une commande enregistre la règle dans
les réglages de l’extraction principale. La règle s’applique alors dans chaque
worktree du dépôt, sauf sous Windows et dans les autres cas que nomme la page
de l’éditeur (@Claude Code worktrees).

## Intégrer dans un ordre fixé

Des branches qui avancent côte à côte s’éloignent l’une de l’autre, et plus
elles vivent longtemps, plus elles sont difficiles à fusionner. Intégrez
souvent, et dans un ordre que vous choisissez avant de commencer : la
modification dont les autres dépendent passe en premier. Ici, la documentation
décrit l’API, et la branche de l’API est fusionnée dans `main` en premier. La
session de documentation fait ensuite un rebase de sa branche sur le nouveau
`main`. Un rebase rejoue les commits propres à la branche, un par un, au-dessus
du nouveau point de départ, et s’arrête au premier conflit (@Git docs git-rebase).

Les deux tâches modifient des fichiers différents, donc le rebase n’a aucun
conflit. Cela ne veut pas dire que la documentation est encore juste. La
session de documentation a écrit son exemple pour l’ancien prix, et c’est le
contrôle qui le découvre. La session relance donc le contrôle après chaque
rebase.

## Comment ce cours est construit

Beaucoup de pages de ce cours sont écrites par des sessions d’agent qui tournent
côte à côte, et la page du dépôt sur l’orchestration décrit comment
(@AI Training orchestration) :

- Une session de coordination prend les tickets prêts et lance une session de
  construction par ticket. Chaque session de construction travaille dans son
  propre worktree, dans un dossier à côté du dépôt, sur une branche nommée
  d’après son ticket.
- Le prompt de chaque session de construction nomme les fichiers qu’une autre
  session de construction modifie aussi, comme la bibliographie commune, pour
  que chacune sache où sa modification peut entrer en collision avec une autre.
- Aucun agent ne lance `git stash` dans aucun worktree, parce que tous les
  worktrees du clone partagent un seul stash. Un hook du dépôt bloque la
  commande, et les agents committent leur travail en cours ou l’enregistrent
  sous forme de patch à la place.
- Les sessions de construction ne démarrent pas le serveur de développement du
  site. Un serveur resté actif depuis une session précédente garde son port et
  sert d’anciennes pages, et une session de construction vérifierait alors le
  mauvais contenu.
- La session de coordination fait le rebase des branches approuvées sur une
  branche d’intégration, une à la fois dans l’ordre où elles ont été
  approuvées, et lance le contrôle complet sur le résultat avant d’ouvrir une
  seule pull request. Quand une branche entre en conflit, la coordination
  arrête le rebase et renvoie la seconde branche à sa session de construction,
  sans résoudre le conflit elle-même. La table des sources fait exception :
  quand deux branches y ajoutent des lignes, la coordination garde les lignes
  des deux. La bibliographie commune n’arrête jamais un rebase, parce que git
  fusionne ce fichier en gardant les lignes des deux côtés. Quand deux branches
  ajoutent la même entrée, le contrôle après les rebases trouve l’entrée en
  double, et la coordination retire une des copies.

Faites votre propre projet à partir des fichiers du cours. Vous pourrez ensuite
faire tourner deux vraies sessions côte à côte sans qu’elles se prennent leurs
fichiers ou leur stash. Vérifiez que `~/shop`, `~/shop-api` et `~/shop-docs`
n’existent pas encore. Ensuite, depuis la racine de votre clone du dépôt du
cours, lancez :

```sh
cp -R site/examples/coding-with-agents/parallel-sessions/shop ~/shop
cd ~/shop
printf '__pycache__/\n' > .gitignore
git init --initial-branch=main
git add .
git commit -m "The shipping module"
git worktree add -b api-half-kilo ../shop-api
git worktree add -b docs-usage ../shop-docs
```

Lancez une session d’agent dans `~/shop-api` et une dans `~/shop-docs`, et
donnez-leur les deux consignes de cette leçon. Écrivez la note d’une ligne de
chaque session avant d’appuyer sur Entrée, et mettez-la à jour chaque fois que
vous regardez une session. Quand les deux ont committé, fusionnez la branche de
l’API dans `~/shop` avec `git merge --ff-only api-half-kilo`, et donnez à la
session de documentation la consigne du rebase. Fusionnez la branche de
documentation quand son contrôle passe. Supprimez ensuite les deux worktrees
avec `git worktree remove`. Si git refuse, lancez `git status` dans ce worktree
pour voir quels fichiers un agent y a laissés.

commits de documentation après lui, un `README.md` dont les exemples passent

qu’ont fait les sessions. Supprimez `~/shop` quand vous avez terminé. Répondez

<Recap>
1. Les sessions parallèles utilisent le temps que vous passeriez à attendre. Donnez à chacune un worktree sur sa propre branche, avec une tâche qui modifie d’autres fichiers que les autres.
2. Les worktrees d’un même clone partagent l’historique et chaque référence sous `refs/`, y compris le stash. Chaque worktree a son propre dossier de fichiers, son `HEAD` et son index (@Git docs git-worktree). Un nouveau worktree n’a ni fichiers ignorés ni dépendances installées tant que vous ne l’avez pas préparé (@Claude Code worktrees).
3. Tenez une ligne par session : worktree et branche, tâche, prochain point, et si elle attend votre réponse. Répondez d’abord à une session qui attend.
4. Intégrez dans un ordre fixé, la modification dont les autres dépendent en premier. Les autres sessions font un rebase et relancent le contrôle, parce qu’un rebase sans conflit peut quand même laisser un exemple périmé.
5. Donnez à chaque session sa propre copie de ce qu’un worktree peut contenir, et dites à chaque session de ne pas toucher à ce qui n’existe qu’une fois, comme le stash, `main` et un port fixe.
</Recap>

<Habit id="note-before-the-second-session">
Avant de lancer une seconde session d’agent à côté d’une session en cours, écrivez sa ligne dans votre note : branche, tâche, prochain point, et si elle attend votre réponse.
</Habit>
