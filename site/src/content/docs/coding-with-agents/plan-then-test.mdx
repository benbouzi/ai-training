Dans cette leçon, nous corrigeons un bug avec un agent de code, en deux
temps. Dans le premier temps, l’agent peut lire et ne peut pas modifier : il
trouve où est le bug et écrit les étapes qu’il compte suivre, et nous
corrigeons l’une d’elles avant qu’un fichier change. Dans le second temps, il
écrit un test qui échoue à cause du bug, puis il modifie le code jusqu’à ce
que le test passe, et nous lisons le diff. Le bug se trouve dans un exemple
fourni avec ce cours, et il s’étend sur trois fichiers, la taille de
modification à partir de laquelle quelques minutes de planification font
gagner plus qu’elles ne coûtent.

L’éditeur de Claude Code enseigne ce rythme pour son propre outil : lire le
code, faire un plan, et seulement ensuite modifier
(@Claude Code best practices). Son court cours suit la même boucle
(@Academy claude-code-101). Quand cette leçon nomme une touche ou une option
de Claude Code, elle le dit, et la source est vérifiée à la date donnée en fin
de leçon. Les autres agents de code ont un mode en lecture seule sous un autre
nom, et le rythme est le même.

## Mettre l’agent en mode plan

Le mode plan est un mode en lecture seule pour l’agent : il lit des fichiers,
cherche et lance des commandes pour explorer, et il ne modifie rien. À la
place d’un diff, vous recevez un plan, une liste écrite des étapes qu’il
compte suivre, et les modifications attendent votre approbation. Dans Claude
Code, `Shift+Tab` (Maj+Tab) fait défiler les modes de permission jusqu’à ce que
la barre d’état indique que le mode plan est actif, et
`claude --permission-mode plan` démarre une session dans ce mode. Un préfixe
`/plan` met un seul prompt en mode plan. `Shift+Tab` de nouveau en sort sans
rien approuver (@Claude Code permission modes).

Lancez votre agent de code en mode plan depuis `fixture-repo`, et donnez-lui
la preuve que vous avez réunie. La consigne a les mêmes parties qu’avant :
l’objectif, le contexte, ce qu’il peut toucher, et la façon de savoir que
c’est terminé. La seule partie nouvelle est que vous demandez un plan, et que
vous lui demandez de nommer la cause avant la correction.

## Corriger le plan tant que cela coûte peu

L’agent est toujours en mode plan, donc le corriger coûte une phrase.
Dites-lui quelle étape retirer et pourquoi, et redemandez le plan. Dans Claude
Code, la demande qui suit un plan terminé propose de l’approuver, de
l’approuver en relisant chaque modification, ou de continuer à planifier, et
c’est la dernière option que vous voulez ici (@Claude Code permission modes).
La même page cite un raccourci, `Ctrl+G`, qui charge le plan dans votre
éditeur pour que vous le modifiiez là. Une phrase dans la conversation fait
le même travail pour une correction d’une étape.

Le plan correspond maintenant à la cause. Approuvez-le, et choisissez l’option
qui vous demande encore votre accord avant chaque modification. Vous savez
quelles doivent être les deux modifications, et les demandes vous permettent
de vérifier que ce sont bien ces deux-là que vous obtenez.

<Pitfall title="Une modification sûre d’elle dans le mauvais module">
Un ingénieur saute le plan et donne à l’agent la consigne de « faire en sorte
que `clear` retire tous les éléments faits ». L’agent lit d’abord `render.py`,
parce que la sortie vient de là, et modifie `list_items` pour laisser de côté

plus d’élément fait. Le bug est toujours dans `store.py`, le fichier contient

positions dans le fichier, donc `done 3` marque ce qui est troisième dans le
fichier. La règle : pour une modification que vous ne savez pas situer dans un
seul fichier, demandez d’abord la cause et les étapes, et lisez les étapes au
regard de la cause avant qu’aucune ne s’exécute.
</Pitfall>

## Le test qui échoue d’abord

La première étape du plan approuvé est un test, et l’agent l’écrit avant de
toucher à `store.py`, parce qu’un test écrit après la correction vérifie ce que
fait le code corrigé, quoi que ce soit. Un test écrit avant doit décrire le
comportement voulu, et il doit échouer, ce qui prouve qu’il regarde bien le
bug. Les conseils de l’éditeur pour la consigne d’un bug suivent le même
ordre : demander un test qui échoue sur le bug avant toute correction, et
seulement ensuite la correction (@Claude Code best practices).

L’agent crée `test_clear.py` et demande l’autorisation pour le nouveau
fichier. Lisez-le avant d’approuver.

```python
class ClearTests(unittest.TestCase):
    def test_remove_done_removes_every_done_item(self):
        items = [
            {"text": "Buy milk", "done": False},
            {"text": "Call the plumber", "done": True},
            {"text": "Renew the passport", "done": True},
            {"text": "Water the plants", "done": False},
        ]
        removed = store.remove_done(items)
        self.assertEqual(removed, 2)
        self.assertEqual([item["text"] for item in items], ["Buy milk", "Water the plants"])
```

La liste a ses éléments faits côte à côte, parce que c’est le cas que le bug
saute. Un test avec un seul élément fait passerait aujourd’hui et ne
prouverait rien. Approuvez le fichier, et lancez la suite vous-même.

Lisez ensuite le diff. C’est la seconde preuve, et le test qui passe ne prouve
quelque chose que si le diff a touché ce que disait le plan.


```diff
-    removed = 0
-    for item in items:
-        if item["done"]:
-            items.remove(item)
-            removed += 1
-    return removed
+    kept = [item for item in items if not item["done"]]
+    removed = len(items) - len(kept)
+    items[:] = kept
+    return removed
```

`git status` nomme deux fichiers : `store.py` modifié, `test_clear.py`
nouveau. `render.py` n’est pas dans la liste, `todos.json` non plus. Le diff
construit d’abord la liste des éléments gardés et la réaffecte dans la même
liste, donc `todo.py`, qui garde une référence à cette liste, voit le
changement. La version de votre agent utilisera peut-être une autre
construction. Ce qui compte, c’est qu’elle modifie `remove_done` et rien
d’autre.

## Quand un test vaut mieux qu’une spécification

Un test qui échoue convient à une modification dont le comportement voulu
tient dans une assertion : une correction de bug, ou une modification
délimitée de ce que fait une fonction ou une commande. Le test est précis,
l’agent peut le lancer sans vous, et le réussir est une preuve. Il ne convient
pas à une modification où la question porte sur la conception : quels modules
existent, quelle est l’interface entre eux, à quoi ressemblent les données.
Pour celles-là, vous écrivez d’abord la spécification et l’agent travaille à
partir d’elle, et ce cours a sa propre leçon sur le
[travail à partir d’une spécification, par petits incréments](/coding-with-agents/spec-driven-increments/).
Les deux méthodes travaillent ensemble. Une fonctionnalité guidée par une
spécification a des tests pour chacun de ses incréments, et une correction
guidée par un test a une spécification d’une ligne, la phrase qui dit ce que
veut dire « corrigé ».

<Recap>
1. Pour une modification que vous ne savez pas situer dans un seul fichier, lancez l’agent en mode plan : il lit et propose, et il ne modifie rien tant que vous n’avez pas approuvé (@Claude Code permission modes). Passez-vous du plan quand toute la modification tient en une courte phrase (@Claude Code best practices).
2. Lisez le plan au regard de la cause qu’il nomme, et corrigez ou retirez une étape qui n’en découle pas tant que la correction coûte une phrase.
3. Le test qui échoue vient avant la correction. Il doit échouer sur le code actuel, sinon il ne regarde pas le bug.
4. L’agent implémente jusqu’à ce que le test passe. Vous lancez le contrôle vous-même, et vous lisez le diff pour voir qu’il n’a touché que ce que disait le plan.
5. Un test convient à une correction de bug ou à une modification de comportement délimitée. Une question de conception part d’une spécification, et les deux méthodes travaillent ensemble.
</Recap>
