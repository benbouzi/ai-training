Dans cette leçon, nous lisons deux sessions qu’un agent de code a menées sur
le même petit dépôt, et nous trouvons l’erreur unique qu’il a faite dans les
deux. Nous corrigeons cette erreur une fois pour toutes, par une ligne dans le
fichier que l’agent lit au début de chaque session. Nous ouvrons ensuite une
nouvelle session et nous vérifions qu’elle suit la ligne sans qu’on le lui
dise. Les deux dernières parties portent sur la façon de garder une session
assez légère pour que l’agent continue de suivre le fichier, et sur la façon
de consigner une décision là où la session suivante la trouve.

Ce fichier contient les **instructions de projet**, `AGENTS.md` ou `CLAUDE.md`
à la racine du dépôt. La façon d’en écrire un à partir de rien, et ce qui doit
y figurer, sont le sujet de
[la leçon de Personnaliser des agents sur AGENTS.md](/customizing-agents/instructions/).
Cette leçon commence là où celle-là s’arrête : le fichier existe, et vous êtes
l’ingénieur qui mène des sessions avec lui et remarque ce qu’il omet de dire.

Le fichier fonctionne parce que l’agent ancre son travail dans ce qui se trouve
dans son contexte, comme
[la leçon sur la récupération](/concepts/retrieval/#lancrage-et-ce-quil-ne-corrige-pas)
l’a montré pour un modèle de conversation. Une règle du fichier d’instructions
se trouve dans le contexte de chaque session. Une correction tapée lors d’une
session précédente n’y est pas. Quand cette leçon nomme une fonctionnalité de
Claude Code, elle le dit, et les pages de l’éditeur sont vérifiées à la date
donnée en fin de leçon.

## Le fichier que l’agent lit en premier

L’exemple est le programme de liste de tâches de
[*Dire à l’agent où est la tâche et où elle s’arrête*](/coding-with-agents/scoping-and-referencing/),
après sa modification `undo`. `docs/SPEC.md` spécifie maintenant deux
commandes de plus que personne n’a construites : `rename <n> <text>` et
`remove <n>`. Le dépôt se trouve dans le dépôt du cours, sous
`site/examples/coding-with-agents/project-instructions/fixture-repo/`. Copiez
ce dossier à un endroit à part et placez-vous dedans. Donnez ensuite un commit
à la copie, pour que `git status` puisse montrer ce qu’une session a modifié :

```sh
git init -q && git add -A && git commit -qm start
```

Pour réinitialiser, supprimez la copie et copiez de nouveau. Lisez ensuite le
fichier d’instructions.

Le fichier, en anglais comme le reste de l’exemple, a cinq règles :
uniquement Python 3 et sa bibliothèque standard, des tests `unittest` lancés

critères de la leçon de Personnaliser des agents, et il est court.

La plupart des agents de code chargent ce fichier avant votre premier message.

`AGENTS.md` quand le dépôt n’a pas de `CLAUDE.md`, et dans une session
interactive affiche une ligne qui nomme le `AGENTS.md` chargé
(@Claude Code memory). Sa commande `/context` montre ce qui se trouve dans la
fenêtre de contexte (context window), donc vous pouvez confirmer que le fichier y est
(@Claude Code best practices). Les autres agents ont leurs propres noms de
fichiers et leur propre façon de le montrer. Avec n’importe quel agent, vous
pouvez vérifier ce qu’il a retenu du fichier en le lui demandant avant le début
de la tâche, par exemple « Que dit le fichier d’instructions sur
`todos.json` ? ». Un agent qui cite la dernière règle a très probablement lu le
fichier, et dans Claude Code, `/context` le montre avec certitude.

Un agent peut avoir le fichier dans son contexte et faire quand même ce que le
fichier devait empêcher. Les sessions ci-dessous montrent comment.

## La corriger une fois, dans le fichier

Une erreur que l’agent fait dans deux sessions est un fait sur le projet que le
fichier d’instructions n’énonce pas encore. Le type de fait qui a sa place dans
ce fichier est décrit dans
[la leçon de Personnaliser des agents](/customizing-agents/instructions/#what-belongs-in-it),
et cette partie porte sur le moment d’en ajouter un. La documentation de Claude
Code donne un déclencheur semblable pour son propre fichier d’instructions :
une erreur que l’agent a déjà faite, ou une correction que vous avez déjà
donnée lors d’une session précédente (@Claude Code memory). Le cours
d’ingénierie des agents dit la même chose d’`AGENTS.md` : commencez petit, et
ajoutez une ligne quand vous voyez un agent répéter une erreur (@AEC-15).

Une correction dans la consigne suivante répare une session. La ligne dans le
fichier atteint chaque session suivante, y compris celles d’un coéquipier,
parce que le fichier est dans le dépôt. La correction va donc dans le fichier,
et elle tient en une ligne.

La ligne doit être assez précise pour que vous puissiez vérifier l’agent par
rapport à elle. La règle existante dit quoi ne pas faire avec des mots que
l’agent a lus de façon étroite. La correction nomme les deux façons dont le
fichier change et dit quoi faire à la place. La documentation de Claude Code
lie la fiabilité avec laquelle l’agent suit une règle à sa précision et à sa
brièveté (@Claude Code memory). Remplacez la dernière ligne de `AGENTS.md` par
celle-ci, en anglais comme le reste du fichier :

```md
- Never change `todos.json`, by hand or by running `todo.py`. To try a command, copy the list first: `cp todos.json /tmp/todos.json`, then run `TODO_FILE=/tmp/todos.json python3 todo.py ...`.
```

La ligne dit de ne jamais modifier `todos.json`, ni à la main ni en lançant
`todo.py`, et donne la marche à suivre pour essayer une commande : copier
d’abord la liste, puis lancer le programme avec `TODO_FILE` qui pointe vers la
copie.

<Pitfall title="Le fichier qui gagnait une ligne à chaque erreur">
Pendant un an, une équipe ajoute une ligne à son fichier d’instructions après
chaque erreur et n’en retire jamais. Le fichier grossit jusqu’à trois pages,
dont certaines lignes portent sur du code qui n’existe plus, et deux se
contredisent. L’agent commence à enfreindre des règles qui sont dans le
fichier, et l’équipe met ces règles en valeur, ce qui allonge encore le
fichier. La documentation de Claude Code nomme cet échec : un fichier trop long
voit la moitié de ses règles ignorées, et dans un long fichier, une règle que
l’agent continue d’enfreindre est un signe qu’il faut élaguer
(@Claude Code best practices). Le cours d’ingénierie des agents ajoute qu’une
ligne périmée égare davantage l’agent qu’une ligne manquante (@AEC-15). La
règle : chaque fois que vous ajoutez une ligne, supprimez celles dont l’agent
n’a plus besoin pour bien faire et celles qui ne décrivent plus le projet.
</Pitfall>

## Garder la session légère

Le fichier d’instructions est chargé une fois, au début. Ce qui vient après
dans la session entre dans la même fenêtre de contexte : les fichiers que
l’agent lit, les sorties des commandes et vos corrections. À mesure que cette
fenêtre se remplit, l’agent suit moins bien les instructions données plus tôt,
et la documentation de Claude Code le dit pour son propre outil
(@Claude Code best practices). Le fichier que vous venez de corriger est dans
le contexte, et quarante sorties d’outils le sont aussi après lui.

La dégradation du contexte (context rot) est la baisse de la qualité avec laquelle l’agent
suit ses instructions à mesure que la fenêtre de contexte se remplit.
**Éviter la dégradation du contexte** consiste à garder le contexte léger pour
que l’agent continue de suivre ses instructions et de garder l’objectif en
vue. Ces habitudes gardent une session légère.

- Une tâche par session. Quand `rename` est terminé et committé, ouvrez une
  nouvelle session pour `remove`. Claude Code a `/clear` pour cela, et sa
  documentation conseille d’effacer le contexte entre des tâches sans rapport
  (@Claude Code best practices).
- Des résumés à la place des journaux bruts. Collez les trois lignes d’un test
  en échec qui comptent, ou demandez à l’agent un court compte rendu d’un long
  journal.
- Désignez les fichiers par leur chemin au lieu de les coller. L’agent lit un
  fichier quand il en a besoin.
- Quand l’agent ignore une règle qu’il suivait il y a une heure, ou que vous
  avez corrigé deux fois la même chose, compactez ou recommencez. Claude Code
  compacte la conversation tout seul près de la limite, et `/compact` avec des
  instructions le fait quand vous le choisissez. Sa documentation conseille
  une nouvelle session avec un meilleur prompt après deux corrections sans
  effet (@Claude Code best practices).

Le fichier d’instructions rend un redémarrage peu coûteux. Claude Code relit
sur le disque le fichier d’instructions racine après `/compact`, et une
instruction donnée seulement dans la conversation peut se perdre dans le
résumé (@Claude Code memory). Une règle du fichier revient dans la session
suivante. Une règle tapée dans la conversation ne revient pas. Le cours
d’Anthropic *Claude Code in action* a un module sur le pilotage des longues
sessions pour aller plus loin (@Academy claude-code-in-action).

## Consigner la décision là où l’agent la lit

Le fichier d’instructions contient aussi les raisons de la structure du
projet, au moins l’endroit où les trouver. Supposons que la session `remove`
ait proposé de déplacer la liste de `todos.json` vers une base de données
SQLite, et que vous ayez dit non : un seul fichier JSON (JavaScript Object
Notation) garde le programme dans la bibliothèque standard, et le diff de
`todos.json` montre chaque changement en revue. Cette raison se trouve
maintenant dans une transcription, et la prochaine session qui trouvera le
fichier JSON lent proposera de nouveau la base de données.

Écrivez la décision dans le dépôt et désignez-la depuis le fichier. Une ligne
dans `AGENTS.md` suffit pour la désigner :

```md
- The list stays one JSON file. Read `docs/decisions/` before you change how `store.py` saves it.
```

Cette ligne dit que la liste reste un seul fichier JSON, et demande de lire
`docs/decisions/` avant de changer la façon dont `store.py` l’enregistre. La
dernière leçon de cette partie,
[*Rester l’ingénieur qui comprend le système*](/coding-with-agents/keeping-understanding/),
montre en entier le dossier des décisions et un fichier de décision. Ce qui
compte ici, c’est la direction : une décision que vous voulez voir respectée
par chaque session va dans un fichier que la session charge ou vers lequel on
la dirige, parce que la transcription de la session où vous l’avez prise
n’est dans le contexte de personne.

<Exercise stretch="Faites la même chose dans un de vos propres dépôts. Lisez côte à côte vos deux dernières sessions d’agent, trouvez une chose que l’agent a ratée dans les deux, et corrigez-la par une ligne dans le fichier d’instructions. Menez vous-même les deux sessions. Réinitialisez la copie de l’exemple,
lancez-y votre agent de code, et donnez-lui la consigne de la session 1 tirée de
`sessions/session-1.txt`. Quand il a terminé, enregistrez son rapport et la
sortie de `git status --short`. Réinitialisez la copie, ouvrez une nouvelle
session, et faites de même avec la consigne de la session 2. Comptez un quart
d’heure.

Placez côte à côte les deux rapports et les deux listes d’état, et trouvez la
chose qui a mal tourné dans les deux. Ce sera peut-être `todos.json`, comme sur
cette page, ou autre chose que fait votre agent, comme une mauvaise commande de
test ou un fichier modifié dont la tâche n’avait pas besoin. Écrivez la ligne
qui le corrige, assez précise pour être vérifiée. Supprimez la copie et copiez
de nouveau l’exemple. Ajoutez ou modifiez cette ligne dans son `AGENTS.md`,
committez-la avec la commande ci-dessus, puis ouvrez une nouvelle session avec
la consigne de la session 2. Vérifiez de nouveau `git status --short`.

Un bon résultat : l’état de la nouvelle session ne montre plus l’erreur, la
consigne était mot pour mot celle d’avant, et `AGENTS.md` diffère de
l’original d’une ligne. Supprimez la copie quand vous avez terminé. Répondez
ensuite à une question : si votre agent n’a fait aucune erreur dans les deux
sessions, qu’avez-vous vérifié pour en être sûr, et qu’ajouteriez-vous au
fichier si une troisième session en faisait une ?
</Exercise>

<Recap>
1. Le fichier d’instructions de projet est chargé au début de chaque session, donc une règle qui s’y trouve atteint chaque session ultérieure, et une correction dans la conversation en atteint une (@Claude Code memory).
2. Une erreur qui se répète se voit quand vous placez deux sessions côte à côte. Corrigez-la une fois, par une ligne dans le fichier (@AEC-15).
3. Écrivez la ligne de façon à pouvoir vérifier l’agent par rapport à elle : nommez l’action de l’agent et ce qu’il faut faire à la place.
4. Un long fichier voit ses règles ignorées. Quand vous ajoutez une ligne, supprimez celles dont l’agent n’a plus besoin (@Claude Code best practices).
5. Gardez le contexte léger : une tâche par session, des résumés à la place des journaux bruts, et compactez ou recommencez quand l’agent cesse de suivre des règles qu’il suivait plus tôt.
6. Consignez une décision dans le dépôt et désignez-la depuis le fichier d’instructions, parce que la session suivante ne lit jamais la transcription où vous l’avez prise.
</Recap>

<Habit id="two-sessions-one-line">
La prochaine fois que vous corrigez un agent de code, vérifiez si vous avez fait la même correction lors d’une session précédente, et si c’est le cas, mettez-la dans le fichier d’instructions sous forme d’une ligne.
</Habit>
