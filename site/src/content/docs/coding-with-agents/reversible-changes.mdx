Dans cette leçon, l’agent committe un par un, sur une branche, les trois
incréments de la spécification des dates d’échéance, puis nous retirons celui
du milieu avec une seule commande. Le but de l’exercice est la limite entre
les commits. Une modification sur une branche, dans des commits assez petits
pour être annulés un par un et sans aucune étape impossible à annuler, peut
être confiée sans risque à un agent. Le pire résultat coûte une annulation
(revert). La seconde moitié de la leçon traite des modifications qui ne
s’annulent pas de cette façon, les données et le schéma, puis des messages de
commit et de la description de pull request qui permettent à un relecteur de
voir ce qu’a fait l’agent et ce qui a été vérifié.

La leçon précédente a livré l’incrément 1 de la spécification et s’est
arrêtée. Ici, l’agent fait les trois, et les commits sont la trace du travail.
Le cours garde des scripts qui appliquent les incréments à une copie pour
vous, et chaque exemple ci-dessous nomme son script.

## Un commit par incrément, sur une branche

Partez d’une nouvelle copie de l’exemple de *Travailler à partir d’une
spécification, par petits incréments*, avec son `SPEC.md`, et faites de la
copie un dépôt git avant que l’agent y touche : `git init`, un commit avec le
programme tel qu’il est, un commit avec la spécification, et une branche

modification réversible d’un coup. La supprimer, ou la laisser non fusionnée,

agents de code committent quand on le leur demande, et la consigne doit le
demander. Livrés à eux-mêmes, la plupart des agents modifient jusqu’à la fin
de la tâche et vous laissent un seul arbre de travail qui contient toutes les
modifications (@Brilliant INC).

## L’étape qu’une personne regarde avant son exécution

Tout ce qui précède est réversible parce que c’est du texte dans un dépôt. Une
annulation le défait, et la branche le délimite. Certaines étapes qu’un agent
peut faire n’ont pas d’annulation, et ce sont celles qu’il faut repérer dans
le plan avant leur exécution. Dans un dépôt de code, ce sont les commandes git
qui jettent du travail. `reset --hard` abandonne chaque modification non
committée d’un fichier suivi, et `clean -f` supprime les fichiers non suivis.
Aucune des deux n’a de retour possible, parce que rien n’a jamais été
committé. Les commits que `reset --hard` ou `branch -D` laissent derrière eux
sont moins perdus qu’il n’y paraît. Git les garde un moment dans le reflog de
`HEAD`, qui enregistre chaque commit vers lequel `HEAD` a pointé
(@Git docs git-reflog). Un reset laisse aussi l’ancien sommet sous
`ORIG_HEAD`, et la documentation de `reset` montre le chemin du retour
(@Git docs git-reset). `push --force` écrase une branche sur le dépôt distant,
où aucun de vos reflogs ne s’applique. Hors du dépôt, les étapes sans
annulation sont un fichier supprimé qui n’était pas suivi, une table
supprimée, un e-mail envoyé, un paiement effectué, un déploiement sur un
système que d’autres personnes utilisent. La consigne ci-dessus exclut
nommément les commandes git. La règle générale est qu’une étape sans retour
possible est l’étape que vous lisez avant son exécution, et que l’agent fait
tout le reste sans vous attendre (@DLAI-5).

La question à poser pour chaque étape est : « si c’est faux, qu’est-ce qui
l’annule, et combien de temps cela prend-il ? » Quand la réponse est « un
revert, en une minute », l’agent peut faire l’étape. Quand c’est « rien » ou
« une restauration depuis la sauvegarde de la nuit dernière », c’est à vous
d’approuver l’étape.

<Pitfall title="Le renommage qui a emporté les données">

seconde migration écrite sous pression. Une modification de schéma n’a pas
d’annulation propre. Son chemin du retour est une modification que vous
concevez avant son exécution.
</Pitfall>

## Des modifications de données avec le chemin du retour écrit

Le code est stocké dans le dépôt, et un revert ramène l’ancienne version en une
seconde. Les données sont stockées dans une base de données, un fichier ou un
index, et elles n’ont pas d’historique si vous n’en gardez pas un. Quand une
modification touche les données, l’annulation du code ne suffit pas, parce que
l’ancien code rencontre les données sous leur nouvelle forme. Une modification
de données se conçoit donc avec son chemin du retour écrit avant son
exécution, et cette description fait partie de la modification que le
relecteur lit.

La conception habituelle consiste à ajouter avant de retirer. La migration
ajoute la nouvelle colonne, et le code commence à écrire dans les deux
colonnes. Ensuite, un remplissage rétroactif (backfill) copie l’ancienne
colonne dans la nouvelle pour chaque ligne écrite avant cela, et le code
commence à lire dans la nouvelle. La suppression de l’ancienne colonne est une
modification séparée, quelques jours plus tard, une fois que le nouveau code a
tourné en production et que plus rien ne lit l’ancienne. Après chacune de ces
étapes, la version précédente du code fonctionne avec la table actuelle, donc
une annulation du code reste une simple annulation. L’exemple de liste de
tâches suit la même règle en miniature : la spécification dit qu’un élément
sans champ `due` reste valide, donc le premier incrément a ajouté un champ que
certains éléments ont et d’autres non, et un `todo.py` plus ancien lit
toujours le fichier.

Moins coûteuse encore est une modification qu’on peut désactiver. Un drapeau de
fonctionnalité (feature flag) ou un réglage de configuration désactivé par
défaut permet de livrer le nouveau code dans le même déploiement que l’ancien,
et désactiver le nouveau comportement demande un changement de réglage, sans
aucun déploiement. Quand l’agent propose une modification dont l’annulation est
« revert puis redéploiement », demandez si elle pourrait être « basculer
l’interrupteur ». Livrez le nouveau classement derrière un drapeau, activez-le
d’abord pour l’équipe, et le chemin du retour devient une modification de
configuration. Le drapeau est retiré plus tard, dans son propre commit, une
fois que l’ancien chemin n’a plus d’appelants.

## Le message de commit et la description de pull request

Les commits sont sur la branche, et un relecteur les lit maintenant. Deux
textes portent la modification jusqu’à l’équipe : les messages de commit et la
description de pull request. Un message de commit dit ce qui a changé et
pourquoi, en une ligne sur laquelle un lecteur de `git log` peut agir. Les
messages de la branche le font : `feat: overdue command with TODO_TODAY` dit au
lecteur ce qu’ajoute le commit et comment il choisit le jour, et une
annulation de ce commit s’explique d’elle-même. Un message comme
`update todo.py` dit où se trouve le diff et rien que le diff ne dise mieux.

La description de pull request est l’endroit où se fixe l’attention du
relecteur. Elle nomme la spécification que suit la modification, et le
relecteur vérifie au regard du document à partir duquel l’agent a travaillé.
Elle dit ce qui a été vérifié et comment, critère par critère. Le relecteur
sait alors ce qui a été vérifié et ce qui lui reste. Et elle dit ce qu’a fait
l’agent et ce que vous avez fait, parce qu’un relecteur lit un diff autrement
quand il sait qu’une machine l’a écrit et qu’une personne a vérifié les
critères. Cette dernière ligne est l’information dont le relecteur a besoin
pour passer son temps là où aucune personne n’a encore regardé. Demandez à
l’agent de la rédiger à partir des commits et de la spécification, puis
lisez-la au regard de ce que vous avez fait.

<Recap>
1. Une modification est réversible quand elle est sur une branche, dans des commits assez petits pour être annulés un par un, et qu’aucune de ses étapes n’est impossible à annuler. C’est ce qui permet de laisser un agent essayer sans risque (@Brilliant INC).
2. Demandez un commit par incrément dans la consigne, et excluez nommément les commandes git qui jettent l’historique. L’étape sans retour possible est celle que vous lisez avant son exécution (@DLAI-5).
3. Une modification de données ou de schéma se conçoit avec son chemin du retour écrit avant son exécution : ajouter et remplir d’abord, supprimer plus tard, et préférer un interrupteur qui désactive la modification à une annulation qui demande un déploiement.
4. Le message de commit dit ce qui a changé et pourquoi. La description de pull request nomme la spécification, dit ce qui a été vérifié et comment, et dit ce qu’a fait l’agent et ce que vous avez fait. Le relecteur passe alors son temps là où personne n’a encore regardé.
</Recap>
