Vous demandez à un agent de code pourquoi l’application n’arrive pas à joindre
sa base de données. Il ouvre `.env` pour vérifier les réglages de connexion, et
le mot de passe de la base est maintenant dans le résultat de l’outil. Claude
Code lit les fichiers du dossier de travail sans vous demander d’abord
(@Claude Code permissions), donc il ne vous a rien demandé. Le résultat de
l’outil fait partie de ce que l’agent envoie au fournisseur du modèle avec sa
requête suivante. Un bac à sable ne change rien à ce trafic
(@Claude Code isolation). Le mot de passe a quitté votre machine, et personne
n’a décidé de l’envoyer.

[Garder les clés d’API hors de portée de l’agent](/coding-with-agents/keys-and-secrets/)
portait sur les secrets qui entrent dans l’agent : quelle clé il détient et où
elle est gardée. Cette leçon porte sur ce qui peut sortir. Nous comparons les
façons de contenir un agent de code et nous voyons pourquoi les contrôles qui
comptent le plus tiennent encore quand l’agent a été convaincu de faire autre
chose. Nous configurons ensuite le bac à sable intégré de Claude Code avec une
liste d’autorisation réseau, et vous prévoyez quelles commandes cette liste
laisse passer.

## Les façons de contenir un agent

Un bac à sable est l’environnement dans lequel l’agent tourne, configuré pour
qu’une commande fausse ou hostile n’atteigne que ce que vous y avez mis. Chaque
type échange du travail de mise en place contre du contrôle :

| Approche                                    | Pour                                                                                                                                                                      | Contre                                                                                                                                                                       |
| ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Le bac à sable intégré de l’agent           | Il est fourni avec l’agent, et sur macOS il n’y a rien à installer                                                                                                        | Seules les commandes shell que lance l’agent sont à l’intérieur. Les hooks, les serveurs MCP (Model Context Protocol) et les propres outils de fichiers de l’agent restent sur votre ordinateur |
| L’environnement d’isolation de l’éditeur (sandbox runtime) | Les hooks et les serveurs MCP sont aussi à l’intérieur de la limite, parce que l’agent entier tourne dans l’isolation du système d’exploitation du bac à sable intégré. Docker n’est pas nécessaire | C’est une version bêta précoce, et sa façon de se configurer peut encore changer                                                                     |
| Un conteneur renforcé (Docker, Podman)      | Vous choisissez les montages, les secrets qui entrent et les hôtes qu’il peut joindre                                                                                     | Effort de mise en place moyen à élevé                                                                                                                                        |
| Un conteneur de développement renforcé (dev container) | L’éditeur le démarre et le gère, et l’exemple de l’éditeur est fourni avec un pare-feu qui bloque le trafic vers les hôtes qu’il ne liste pas                    | L’équipe garde à jour l’image et la liste du pare-feu. Son usage est une convention d’équipe, et un développeur peut toujours lancer l’agent sur la machine hôte              |
| Une machine virtuelle renforcée             | Un noyau à elle entre l’agent et votre ordinateur, ce qui sépare les deux davantage que toute autre option ici                                                           | Effort de mise en place élevé                                                                                                                                                |
| Un agent hébergé par l’éditeur dans le cloud | Rien à installer. L’éditeur fait tourner la machine isolée, et votre jeton de forge reste dans un proxy à l’extérieur, qui ne donne à l’agent qu’un accès limité au dépôt | Votre code est copié sur les machines de l’éditeur, et vous travaillez avec les contrôles de l’éditeur au lieu des vôtres. Il faut un abonnement                              |
| Aucune isolation, seulement les demandes d’autorisation | Rien à mettre en place                                                                                                                                        | L’agent a tous vos accès, et vous êtes le seul contrôle                                                                                                                      |

La comparaison de ces options par l’éditeur est la source de chaque ligne sauf
la dernière (@Claude Code isolation). Un conteneur peut aussi garder un
identifiant dans un second conteneur à côté de lui, un conteneur annexe
(sidecar), comme le fait le conteneur renforcé de la dernière partie
(@claude-docker).

Quel que soit votre choix, l’agent peut toujours modifier le code que vous
montez en écriture, et il peut toujours envoyer ce qu’il lit à n’importe quel
hôte que le réseau le laisse joindre (@Claude Code isolation). Un bac à sable
réduit le rayon d’impact (blast radius) d’une session. Ce que l’agent fait à l’intérieur
demande toujours votre relecture.

## Imposer hors de la frontière de confiance

La frontière de confiance est la ligne entre ce que l’agent décide seul et ce
que le harnais (harness), le système d’exploitation ou le réseau lui imposent. Une
instruction est du côté de l’agent. Claude Code charge CLAUDE.md au début de
chaque session (@Claude Code memory), mais une ligne de ce fichier est une
demande, et le modèle peut l’ignorer ou en être détourné.

Les contrôles de l’autre côté fonctionnent de deux façons. Une règle de
permission, un hook et votre réponse à la demande d’autorisation vérifient la
requête : Claude Code juge le texte de la commande avant que quoi que ce soit
tourne. Le bac à sable limite ce que le processus en cours peut atteindre, et
le système d’exploitation tient cette limite quoi que fasse la commande une
fois lancée (@Claude Code sandboxing).

L’injection de prompt (prompt injection) agit sur la requête. Du texte dans un fichier peut
convaincre l’agent de demander une commande que vos règles autorisent et que
vous approuvez parce qu’elle a l’air de routine, comme un petit script au nom
anodin. La vérification de la requête passe alors. Une limite sur le processus
en cours ne lit jamais ce texte, donc le texte ne peut pas la changer. C’est la
règle de cette leçon : pour les contrôles qui comptent le plus, limitez ce que
le processus en cours peut atteindre, avec des limites imposées là où rien de
ce que lit l’agent ne peut les changer. Une liste d’autorisation réseau et un
identifiant détenu par un conteneur annexe fonctionnent tous deux ainsi :

- **Une liste d’autorisation réseau imposée par le bac à sable ou un proxy.**
  L’agent peut lancer n’importe quelle commande, et une connexion vers un hôte
  absent de la liste échoue.
- **Un identifiant détenu par un conteneur annexe.** Les requêtes de l’agent
  sortent par le conteneur annexe, qui ajoute le vrai jeton au passage. L’agent
  ne voit jamais qu’un marqueur, donc il n’a aucun jeton à divulguer
  (@claude-docker).

## Configurer le bac à sable intégré

Le bac à sable de Claude Code couvre les commandes shell que lance l’agent et
chaque programme que ces commandes démarrent. Le système d’exploitation
l’impose : Seatbelt sur macOS, et bubblewrap sur Linux et WSL2 (le
sous-système Windows pour Linux), où vous installez d’abord `bubblewrap` et
`socat`. Il ne tourne pas sous Windows natif (@Claude Code sandboxing).

**Quels fichiers.** Par défaut, une commande dans le bac à sable n’écrit que
dans le dossier de travail, un dossier temporaire propre à l’utilisateur et
tout dossier que vous avez ajouté. Elle peut lire presque tout l’ordinateur, y
compris `~/.ssh` et `~/.aws/credentials`, tant que vous ne les listez pas sous
`sandbox.credentials` ou `sandbox.filesystem.denyRead`. Les commandes dans le
bac à sable héritent aussi de l’environnement avec lequel Claude Code a été
lancé, identifiants compris, sauf si `sandbox.credentials` les retire. Les
propres outils de fichiers de Claude Code ne tournent pas dans le bac à sable,
et ce sont les règles de permission qui les gouvernent. Pour le cas de `.env`,
la règle d’interdiction `Read(./.env)` de la leçon sur les clés bloque les
outils de fichiers. Une fois le bac à sable activé, Claude Code ajoute aussi les
règles d’interdiction `Read` aux blocages de lecture du bac à sable, donc un
script écrit par l’agent ne peut pas non plus ouvrir le fichier
(@Claude Code sandboxing). Utilisez `denyRead` pour un chemin que vous ne voulez
pas sous forme de règle de permission.

**Quels hôtes.** Le trafic réseau des commandes dans le bac à sable passe par
un proxy qui tourne hors du bac à sable. Aucun hôte n’est autorisé au départ,
et la première fois qu’une commande joint un nouvel hôte, Claude Code vous
demande (@Claude Code sandboxing). `allowedDomains` liste les hôtes qui passent
sans question. Une entrée comme `*.example.com` couvre les sous-domaines, un
suffixe `:443` limite une entrée à un port, et `deniedDomains` bloque un hôte
même quand une entrée autorisée le couvre (@Claude Code all settings). Avec
`strictAllowlist` à `true`, un hôte absent de la liste est bloqué au lieu de
faire l’objet d’une question. Claude Code ne lit ce réglage que dans vos
réglages utilisateur, dans les réglages gérés (managed settings) ou dans un
fichier passé avec `--settings`, et dans le `.claude/settings.json` d’un dépôt
il n’a aucun effet. Il demande Claude Code v2.1.219 ou plus récent
(@Claude Code sandboxing).

**Ce qui se passe quand le bac à sable ne peut pas lancer une commande.** Si le
bac à sable ne peut pas démarrer du tout, Claude Code affiche un avertissement
et lance les commandes sans lui, sauf si `failIfUnavailable` vaut `true`, ce
qui le fait refuser de démarrer. Quand une commande échoue dans le bac à sable,
l’agent peut la retenter hors du bac à sable, où s’applique la demande
d’autorisation habituelle, et `allowUnsandboxedCommands: false` supprime cette
nouvelle tentative (@Claude Code sandboxing). Par défaut, une commande qui
tourne dans le bac à sable tourne sans vous demander, et
`autoAllowBashIfSandboxed: false` rétablit la demande
(@Claude Code all settings).

Le dépôt du cours a un exemple pour cette leçon dans
`site/examples/coding-with-agents/sandboxing/`. Son `sandbox-settings.json`
utilise les mêmes noms de réglages que le fichier de réglages de la leçon
suivante et autorise un seul hôte :

```json
{
  "permissions": {
    "deny": ["WebFetch", "WebSearch"]
  },
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "autoAllowBashIfSandboxed": false,
    "allowUnsandboxedCommands": false,
    "network": {
      "allowedDomains": ["pypi.org"],
      "strictAllowlist": true
    }
  }
}
```

La liste d’autorisation ne couvre que les commandes dans le bac à sable. L’outil
de récupération web de Claude Code tourne dans Claude Code lui-même et suit ses
règles de permission (@Claude Code sandboxing), donc les règles d’interdiction
désactivent aussi les outils web. À côté des réglages, `commands.txt` contient
trois commandes qui essaient chacune de joindre un hôte différent :

```text
curl -sI https://pypi.org/simple/
curl -sI https://files.pythonhosted.org/
curl -s https://collect.example.invalid/upload
```

La dernière adresse se termine par `.invalid`, un nom réservé pour qu’il
n’appartienne jamais à un vrai serveur (@RFC 2606). Le `check_allowlist.py` de
l’exemple ne fait aucun appel réseau. Il lit les réglages, trouve l’hôte et le
port de chaque commande et applique les règles correspondantes ci-dessus.

<Pitfall title="La liste d’autorisation qui laissait tout sortir">
Un développeur ajoute `github.com` à `allowedDomains` pour que l’agent puisse
pousser ses branches, et se sent en sécurité parce que la liste est courte. Mais
n’importe qui peut créer un compte sur ce site et y recevoir des données. Le
proxy du bac à sable décide à partir du seul nom d’hôte et ne regarde pas
l’intérieur du trafic chiffré, et l’éditeur prévient qu’un domaine large comme
`github.com` peut devenir un moyen de faire sortir des données
(@Claude Code sandboxing). Autorisez l’hôte le plus étroit dont une commande a
besoin. Quand l’agent doit joindre un hôte large, faites passer son trafic par
un proxy à vous qui peut regarder à l’intérieur des requêtes, comme le décrit
la même page. Votre proxy décide alors quels hôtes passent, donc donnez-lui
aussi la liste d’autorisation.
</Pitfall>

vous demande si vous lui faites confiance (@Claude Code security). Répondez
Yes, puisque le dossier est la copie que vous venez de faire. Lancez `/sandbox`
et vérifiez que le bac à sable est actif. Demandez ensuite à l’agent de lancer
les commandes de `commands.txt` une par une et de dire ce que chacune a
affiché. Approuvez chaque commande à la demande, puisqu’elles ne font que lire

(@Claude Code sandboxing). Comptez environ cinq minutes.

Un bon résultat est un tableau avec une ligne par commande : l’hôte, ce que vous
aviez prévu, ce qui s’est passé, et le réglage qui en a décidé. Si une ligne
contredit votre prévision, trouvez dans vos propres fichiers le réglage qui
l’explique. Répondez ensuite à une question : quel hôte ajouteriez-vous pour un
vrai projet, et que pourrait y envoyer l’agent ?
</Exercise>

## Au-delà du bac à sable intégré

Les résumés ci-dessous renvoient chacun à leur source, pour le cas où le bac à
sable intégré ne suffit pas.

**Un conteneur renforcé avec un modèle de menace écrit.** Le dépôt public
[`schubergphilis/claude-docker`](https://github.com/schubergphilis/claude-docker)
fait tourner Claude Code dans un conteneur, et son README dit ce que cela
protège et ce que cela ne protège pas (@claude-docker). Hormis la propre
connexion de l’agent, un identifiant n’entre que si vous passez son option. Un
jeton de forge reste dans un conteneur annexe pendant la session, et l’agent
peut toujours s’en servir par le conteneur annexe tant que la session tourne. Le
modèle de menace prévient aussi que des outils comme `npx` et `uvx`
téléchargent et exécutent du code la première fois que vous les utilisez. Après
une session compromise, il dit de considérer que les données sont déjà sorties
et de faire tourner chaque identifiant entré dans le conteneur.

**Un modèle de confinement en couches.** Certaines équipes empilent des
contrôles venus de projets différents. Aucune source ne documente cet
empilement comme un tout :

| Couche                          | Ce qu’elle fait                                                                                                                    | Briques publiques                      |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------- |
| Isolation                       | Un conteneur par agent sur son propre réseau, avec seulement l’espace de travail monté                                             | Docker, Podman, dev containers         |
| Contrôle imposé hors de l’agent | Un proxy enveloppe autorise les hôtes et les commandes listés, et retire les secrets des résultats d’outils avant qu’ils aillent au modèle | mitmproxy, un petit proxy à vous   |
| Barrière de revue               | L’agent pousse vers un serveur git local, et une personne relit là avant que quoi que ce soit atteigne le vrai dépôt distant      | Forgejo, Gitea, un dépôt nu (bare)     |
| Hygiène de la chaîne d’approvisionnement | Une recherche de secrets avant chaque commit, et aucune version de paquet plus jeune qu’un âge fixé                       | Gitleaks, le `minimumReleaseAge` de pnpm |
| Observation                     | Des règles qui enregistrent les événements réseau, fichiers et processus autour du conteneur sans les bloquer                     | Tetragon, Falco                        |

Gitleaks cherche les secrets dans un dépôt (@Gitleaks), et le
`minimumReleaseAge` de pnpm retient une nouvelle version de paquet pendant une
durée fixée, un jour par défaut (@pnpm supply chain).

**Tourner avec toutes les demandes désactivées.** Dans Claude Code, c’est
`--dangerously-skip-permissions`, et rien ne remplace les demandes qu’il
supprime (@Claude Code sandboxing). Anthropic demande qu’une telle session
tourne là où ses outils de fichiers, ses serveurs MCP et ses hooks sont aussi
isolés, c’est-à-dire dans un conteneur, une machine virtuelle ou
l’environnement d’isolation de l’éditeur (@Claude Code isolation). Vérifiez une
telle exécution d’autant plus près que vous en avez peu regardé, comme le
conseille le cours de l’Academy *Claude Code in action*
(@Academy claude-code-in-action). Codex sépare l’endroit où les commandes
peuvent écrire du moment où l’agent vous demande, et désactive le réseau par
défaut (@Codex approvals). Ce sont trois décisions distinctes dans n’importe
quel agent, et une configuration peut être stricte sur l’une et souple sur une
autre.

**Le modèle n’apporte aucun garde-fou.** Pi, un agent de code open source, n’a
aucune étape d’approbation avant chaque appel d’outil (tool call). Sa documentation confie
la sécurité à ce qui limite ce que Pi peut atteindre, en général un conteneur,
une machine virtuelle ou un bac à sable autour de lui (@Pi security). Les
limites viennent du harnais et de l’environnement, quel que soit le modèle.

<Recap>
1. Un fichier que lit l’agent part chez le fournisseur du modèle avec la requête suivante, que le bac à sable soit actif ou non. Un bac à sable limite les fichiers qu’il peut lire et les hôtes vers lesquels il peut les envoyer (@Claude Code isolation).
2. Les façons de contenir un agent vont du bac à sable intégré, rapide à lancer et limité aux commandes shell, à l’environnement d’isolation de l’éditeur, aux conteneurs, aux conteneurs de développement et aux machines virtuelles, jusqu’à un agent hébergé par l’éditeur qui ne demande aucune mise en place et ne vous laisse que les contrôles de l’éditeur.
3. Une règle de permission, un hook ou une demande d’autorisation vérifient ce que demande l’agent, et un texte injecté peut orienter cette demande. Pour les contrôles qui comptent le plus, limitez ce que le processus en cours peut atteindre : une liste d’autorisation réseau imposée par un proxy, et des identifiants détenus par un conteneur annexe.
4. Dans Claude Code, `allowedDomains` liste les hôtes, `strictAllowlist` bloque les autres sans demander quand il vient de vos propres réglages ou d’un fichier de réglages passé, et `allowUnsandboxedCommands: false` avec `failIfUnavailable: true` empêche les commandes de l’agent de tourner hors du bac à sable (@Claude Code sandboxing).
5. Gardez un jeton dont l’agent a besoin dans un proxy ou un conteneur annexe qui l’ajoute à la sortie, et considérez que l’agent peut s’en servir pendant toute la session.
</Recap>

<Habit id="name-the-hosts-first">
Avant de laisser un agent lancer des commandes dans un nouveau projet, écrivez les hôtes dont ces commandes ont vraiment besoin, et vérifiez que votre liste d’autorisation nomme ces hôtes et rien de plus large.
</Habit>
