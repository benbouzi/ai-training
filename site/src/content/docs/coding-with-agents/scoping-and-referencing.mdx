Dans cette leçon, nous donnons deux fois la même petite tâche à un agent de
code. La première consigne tient en une phrase, et nous regardons quels
fichiers l’agent lit pour lui donner un sens. La seconde consigne dit où est la
tâche et où elle s’arrête : quels fichiers sont concernés, lesquels sont
interdits, quelle fonction imiter, quel test étendre et quelle commande prouve
que c’est terminé. Nous comparons ensuite les deux sessions selon les fichiers
qu’elles ont lus et le diff qu’elles ont produit.

La consigne est le contexte de l’agent, et l’agent ancre son travail dans ce
qu’il lit, comme [la leçon sur la récupération](/concepts/retrieval/) l’a
montré pour un modèle de conversation : une réponse repose sur le passage
qu’on lui a donné, et ce passage peut être le mauvais. Un agent de code qui
choisit ses propres fichiers peut aussi choisir les mauvais. L’éditeur de
Claude Code donne le même conseil pour son outil : dire quels fichiers sont
concernés, ce qui ne doit pas changer, et quel code existant le nouveau code
doit imiter (@Claude Code best practices), et son court cours a un module sur
la gestion du contexte (@Academy claude-code-101). Quand cette leçon nomme une
fonctionnalité de Claude Code, elle le dit, et la source est vérifiée à la date
donnée en fin de leçon.

Un agent qui part d’un grep ouvre `legacy/todo_v1.py` et le lit avec la même
attention que `todo.py`. La spécification, le fichier qui dit ce que doit faire
`undo`, est l’autre résultat, et l’agent de la transcription ne l’a pas
ouvert.

**Le cadrage d’une tâche** consiste à dire à l’agent où se trouve la tâche et
où elle s’arrête : quel module, quels fichiers sont concernés et lesquels sont
interdits. Il a deux effets visibles. L’agent lit moins, donc une plus grande
part de sa fenêtre de contexte (context window) reste disponible pour le travail, et les
conseils de l’éditeur citent comme échec courant une enquête sans cadre qui lit
des centaines de fichiers (@Claude Code best practices). Et la modification
reste là où vous l’avez placée. Une refonte bien intentionnée de `done`, ou une
colonne de plus dans le CSV, est une modification qui s’étend parce que rien
n’a dit à l’agent de s’arrêter.

## Désigner le fichier au lieu de le décrire

La seconde moitié de la correction consiste à **référencer des fichiers** :
nommer le fichier, la fonction ou le document exact que l’agent doit lire, pour
qu’il charge le bon contexte du premier coup. « La fonction qui marque un
élément comme fait » est une description, et l’agent doit chercher ce qui y
correspond, c’est ainsi qu’il est arrivé dans `legacy/`. Un chemin et une plage
de lignes sont une adresse, et il n’y a qu’une chose à une adresse.

<Predict id="run-reference" title="Lire ce que désigne la référence"
  answer={`16	def done(items, number):
  17	    index = number - 1
  18	    if index < 0 or index >= len(items):
  19	        return f"no item #{number}"
  20	    items[index]["done"] = True
  21	    return f"done #{number}: {items[index]['text']}"`} run="coding-with-agents/scoping-and-referencing/reference.py">
Affichez les lignes 16 à 21 de `todo.py` avec leurs numéros. La consigne de la
partie suivante désigne ces lignes.

```sh
awk 'NR >= 16 && NR <= 21 { print NR "\t" $0 }' todo.py
```
</Predict>

C’est l’exemple à imiter. Une consigne qui dit « ajoute `undo` à côté de `done`
dans `todo.py`, lignes 16 à 21, avec les mêmes arguments et les mêmes
contrôles » laisse à l’agent une seule chose à lire et un seul modèle à
suivre. Les conseils de l’éditeur pour Claude Code disent la même chose avec
leurs propres mots : désigner à l’agent un motif existant dans le code et
nommer un fichier qui en est un bon exemple (@Claude Code best practices).

Une consigne a le plus souvent besoin des mêmes références. L’**exemple à
imiter** est le code auquel le nouveau code doit ressembler, ici `done` dans
`todo.py`, lignes 16 à 21. Le **test à étendre** est le test à côté duquel le
nouveau doit se placer, ici `test_done_marks_the_numbered_item` à la ligne 21
de `test_todo.py`. La **spécification à suivre** est le document qui dit ce que
doit faire le résultat, ici la ligne `undo` de `docs/SPEC.md`. Chacune
remplace une recherche par une lecture.

Dans Claude Code, un `@` devant un chemin dans le prompt fait lire ce fichier à
l’agent avant qu’il réponde, donc `@todo.py` est une référence sur laquelle
l’outil agit, en plus d’une indication pour le modèle
(@Claude Code best practices). Avec un autre agent, écrivez le chemin. L’agent
le lit, et un chemin qu’il peut ouvrir est exact là où une description qu’il
doit faire correspondre est une supposition.

<Pitfall title="Le fichier plausible le plus proche">
Un ingénieur demande à un agent d’« ajouter une commande undo, comme celle de
l’ancienne version ». L’agent cherche `undo`, trouve `undone` dans
`legacy/todo_v1.py`, et construit la nouvelle commande sur ce fichier : l’ancien
nom, l’ancien message `reopened:`, et une fonction auxiliaire `mark` que le
`todo.py` actuel n’a pas. Les tests passent, parce que rien ne teste le
message, et la spécification qui dit `open #<n>: <text>` n’a jamais été lue. La
règle : quand il existe un fichier que l’agent doit imiter, nommez-le, sinon
l’agent imite le premier fichier qui lui ressemble, et le premier est souvent
le mauvais.
</Pitfall>

## Ajouter ce que le code ne montre pas, puis relancer

Reste ce qu’aucun fichier du dépôt ne dit. La limite propre à la tâche vient
en premier : `store.py`, `render.py` et `export.py` ne font pas partie de cette
modification, et `legacy/` ne fait partie d’aucune modification. Le fichier
d’instructions du projet, `AGENTS.md`, contient déjà la règle permanente sur
`legacy/`, et c’est là qu’a sa place une limite valable pour toutes les tâches
(@AEC-15). La limite de cette tâche va dans la consigne. Vient ensuite le
contrôle : la commande qui dit que la tâche est terminée, ici la suite de
tests.

Réinitialisez la copie, ouvrez une nouvelle session, et donnez la consigne
cadrée.
