Un agent de code a ajouté une zone de recherche à une petite application de
notes. La consigne était courte : un utilisateur tape une partie d’un titre et
voit ses propres notes qui correspondent. L’agent a écrit une fonction de
recherche et un petit contrôle d’administration, et la recherche marche quand
on l’essaie. Dans cette leçon, nous faisons la revue de sécurité du code d’un
agent : nous lisons cette modification comme le ferait un attaquant. Un
analyseur statique trouve une partie de ce qui ne va pas, et nous lisons le
code pour le reste. Nous donnons ensuite à l’agent la consigne d’une
correction, avec un test qui la prouve.

La carte des compétences *Coding with AI* de Brilliant range la sécurité et la
pensée adverse parmi ses domaines de compétences à part entière
(@Brilliant SEC). La question que cette leçon entraîne est celle de
l’adversaire : que se passe-t-il quand l’entrée est hostile ?

## La modification de l’agent

```sh

cd ~/security-review
```

`notes_search.py` est la modification de l’agent. La route qui appelle
`search_notes` passe le nom de l’utilisateur connecté comme `owner` et le texte
de la zone de recherche comme `term`. Voici la fonction entière, avec le
contrôle d’administration que l’agent a ajouté dans le même commit :

```python
ADMIN_PASSWORD = "notes-admin-2026"


def is_admin(password: str) -> bool:
    """Lets the admin page in when the password matches."""
    return password == ADMIN_PASSWORD


def search_notes(conn: sqlite3.Connection, owner: str, term: str) -> "list[str]":
    """Returns the titles of the owner's notes whose title contains term."""
    query = (
        f"SELECT title FROM notes WHERE owner = '{owner}' AND title LIKE '%{term}%' ORDER BY title"
    )
    try:
        rows = conn.execute(query).fetchall()
    except sqlite3.Error:
        return []
    return [row[0] for row in rows]
```

Elle se lit facilement et elle fait ce que demandait la consigne. Gardez-la
ouverte pendant que vous lisez la partie suivante.

## Les erreurs que les agents recopient

Un modèle apprend à écrire du code à partir d’une grande quantité de code
public, et le code public contient des bugs, y compris des bugs de sécurité.
Dans une étude de 2021, Pearce et ses collègues ont donné à GitHub Copilot 89
scénarios de programmation construits autour de types de faiblesses à haut
risque tirés de la liste Top 25 que publie la MITRE Corporation. Ils ont jugé
vulnérables environ 40 % des 1 689 programmes produits. Leur explication est
qu’un modèle entraîné sur du code que personne n’a vérifié a appris les motifs
exploitables qu’il contient (@Pearce 2022). Les modèles ont changé depuis cette
étude, et ils sont toujours entraînés sur du code public. La liste ci-dessous
est propre à ce cours, et recense des erreurs qu’on trouve dans une grande
partie de ce code :

- **Entrée non validée.** Une valeur venue d’un formulaire, d’un fichier ou d’une
  interface de programmation (API) est utilisée comme si elle était fiable :
  une quantité qui peut être négative, un nom de fichier qui peut contenir
  `../`.
- **Requêtes et commandes construites par concaténation de chaînes.** L’entrée
  est collée dans une requête SQL (Structured Query Language) ou une commande
  shell, donc elle peut changer ce que fait la requête ou la commande.
- **Secrets dans le code.** Un mot de passe, un jeton (token) ou une clé est écrit dans
  le code source, où chaque copie du dépôt l’a.
- **Réglages par défaut trop permissifs.** Un serveur écoute sur toutes les
  interfaces réseau, un mode de débogage reste actif, ou un fichier est créé
  lisible par tous.
- **Contrôles désactivés.** La vérification des certificats est désactivée pour
  faire disparaître une erreur, ou un test est sauté parce qu’il échouait.
- **Gestion d’erreurs qui masque les échecs.** Une exception est interceptée et
  remplacée par un résultat vide. Un échec ressemble alors à « rien trouvé ».

Chacune de ces erreurs raccourcit le code ou fait disparaître une erreur. Un
agent à qui l’on dit de terminer la tâche y recourt pour la même raison qu’une
personne pressée.

## Ce que trouve l’analyseur

Un analyseur statique lit le code source sans l’exécuter et signale des motifs
qui sont souvent des erreurs. Pour Python, Bandit est un analyseur gratuit sous
licence Apache-2.0 qui cherche les problèmes de sécurité courants (@Bandit).
Dans l’exercice de fin de leçon, vous installez Bandit et vous le lancez sur
votre propre copie de l’exemple. L’exécution enregistrée ci-dessous est à lire
maintenant, et sert aux lecteurs qui sautent l’installation. Le 27 septembre
2026, Bandit 1.8.6 tournant sous Python 3.9.25 a affiché ceci pour
`notes_search.py` dans une nouvelle copie de l’exemple, sans l’heure de
départ :

par gravité, et elle est sortie avec le code 1 parce qu’elle a trouvé des
problèmes. La colonne de la remarque B608 dépend de la version de Python : 3.9,
3.10 et 3.11 ont affiché `22:8`, et 3.12 et 3.13 ont affiché `22:10`.

Bandit a trouvé deux des erreurs classiques. B105 est un mot de passe dans le
code source, que Bandit repère parce que le nom de la variable contient
`password`. B608 est la requête construite à partir de chaînes. Bandit évalue
sa confiance dans cette remarque à Low (faible). Un contrôle de motifs ne peut
pas voir d’où viennent `owner` et `term`. Vous le pouvez, et ici, `term` vient
d’un utilisateur, donc la remarque est réelle.

Bandit n’a pas signalé le `except sqlite3.Error: return []`. L’un de ses
contrôles, B110, cherche un bloc `except` dont la seule instruction est `pass`
(@Bandit). Ce bloc renvoie une liste vide, ce qui masque l’erreur tout aussi
bien et ne correspond à aucune règle. Un analyseur trouve les motifs pour
lesquels quelqu’un a écrit une règle. Ce que le code veut dire pour cette
application, par exemple si une liste vide veut dire que rien n’a correspondu,
est une question à laquelle seul un lecteur peut répondre.

## Et si l’entrée était hostile

Posez maintenant la question à chaque endroit où des données entrent dans la
fonction, et là où va son erreur :

- `term` vient de la zone de recherche. Quiconque peut se connecter le contrôle
  entièrement.
- `owner` vient de la session de connexion. Il n’est fiable que tant que la
  route le prend dans la session, et une modification ultérieure qui le lirait
  dans l’adresse web (URL) le rendrait hostile aussi.
- L’erreur de base de données revient à l’utilisateur sous forme de liste vide,
  donc l’utilisateur ne peut pas distinguer un échec d’un « aucune
  correspondance ».

Prenez d’abord `term`. Supposons qu’Alice tape `%' OR owner != '` dans la zone
de recherche. La f-string la colle dans la requête, et la clause `WHERE`
devient `owner = 'alice' AND title LIKE '%%' OR owner != '%'`. En SQL, `AND`
lie plus fortement que `OR`.

## La revue et le rayon d’impact

La recherche tourne avec la connexion à la base de données de l’application.
Son rayon d’impact (blast radius) est tout ce que cette connexion peut lire ou modifier. Pour
un compte en lecture seule, ce sont toutes les notes de la base. Pour un compte
qui peut écrire, une requête construite par concaténation peut aussi supprimer
ou modifier des notes. Le temps que vous consacrez à une revue de sécurité suit
la même règle que toute décision de risque : regardez ce que le code peut
atteindre avant de décider combien de contrôle il demande.

L’injection SQL et l’injection de prompt (prompt injection) sont la même erreur à deux endroits.
Dans les deux cas, des données qui ne devraient qu’être lues sont placées à côté
d’instructions, et le lecteur ne peut pas les distinguer. La f-string de
l’agent met le texte de recherche d’Alice dans le SQL. Une page web qu’un agent
lit met son texte dans le prompt. La correction pour le SQL consiste à garder
données et instructions dans des canaux séparés, avec un paramètre fictif. Un
prompt n’a pas de tel canal, et c’est pourquoi il faut limiter les accès d’un
agent à la place.

<Recap>
1. Les agents apprennent à partir de code public, et ils en apprennent aussi les bugs de sécurité (@Pearce 2022). Cherchez les entrées non validées, les requêtes et commandes construites par concaténation, les secrets dans le code, les réglages par défaut trop permissifs, les contrôles désactivés, et la gestion d’erreurs qui masque les échecs.
2. Un analyseur statique comme Bandit trouve les motifs pour lesquels il a des règles. Lisez ses remarques, y compris celles de confiance Low, puis lisez le code pour ce qu’il ne peut pas savoir.
3. À chaque endroit où des données arrivent, demandez-vous ce qui se passe quand l’entrée est hostile, et suivez chaque `except` jusqu’à ce que voit l’utilisateur.
4. Donnez la consigne de la correction avec des paramètres fictifs et un test qui échoue sur l’ancien code, et lancez ce test sur les deux versions avant de l’accepter (@Python sqlite3).
5. Le rayon d’impact d’une injection est tout ce que peut atteindre la connexion du code, et l’injection SQL est la même erreur que l’injection de prompt : des données placées là où vont les instructions.
</Recap>

<Habit id="ask-what-if-hostile">
La prochaine fois que vous relisez la modification d’un agent qui lit des entrées utilisateur, trouvez chaque endroit où l’entrée arrive et demandez-vous ce qui se passe si elle est hostile avant d’approuver.
</Habit>
