## Écrire le contrôle sous forme de test

Un contrôle que vous seul pouvez lancer est lancé quand vous y pensez. Le guide
de l’éditeur de Claude Code dit que, sans contrôle que l’agent peut lancer,
c’est à vous de remarquer chaque erreur. Il conseille de donner à l’agent un
contrôle dont le résultat est réussi ou échoué. Une suite de tests en est un, et
un script qui compare la sortie à un bon résultat connu en est un autre.
L’agent peut alors relancer le contrôle après chaque modification et
s’arrêter une fois qu’il passe (@Claude Code best practices). Le cours de
l’Academy The AI-native SDLC playbook (SDLC désigne le cycle de vie du
développement logiciel) enseigne la même idée dans une leçon sur la boucle de
retour à donner à l’agent (@Academy ai-native-sdlc-playbook).

Pour l’import nocturne, le contrôle est `test_nights.py`, un court script
Python du dépôt du cours. Il lance l’import sur chaque nuit comme le fait la
tâche nocturne, et affiche une ligne par nuit. Il sort avec le code 0 quand
toutes les nuits passent, et avec le code 1 quand l’une échoue. Voici les nuits
qu’il connaît :

```python
# Each night, with the total it must print, or None when the total is not
# pinned yet.
NIGHTS = {
    "2026-09-14": "22975.95 EUR",
    "2026-09-15": None,
    "2026-09-16": "23257.33 EUR",
    "2026-09-17": None,
}
```

Le commentaire dit que chaque nuit est associée au total qu’elle doit afficher,
ou à `None` quand ce total n’est pas encore fixé. Une nuit passe quand l’import
sort avec le code 0 et analyse chaque ligne de données des exports de la nuit,
et, pour le 14 et le 16, quand il affiche le même total qu’avant. Le test compte
lui-même les lignes, une par ligne après l’en-tête. Ce décompte est là à cause
de la leçon précédente : une « correction » qui saute une ligne qu’elle ne sait
pas lire sort aussi avec le code 0, et c’est le décompte des lignes qui la
détecte.

Depuis la racine de votre clone du dépôt du cours, copiez l’import et le test à
un endroit à vous, et lancez-y le test.

```sh
cp site/examples/coding-with-agents/self-checking-loops/test_nights.py ~/loop-me/

python3 test_nights.py; echo "exit status $?"
```

## Donner la consigne de la boucle avec une limite

Une **boucle d’autovérification bornée** est une boucle dans laquelle l’agent
lance le contrôle, corrige et relance, avec une limite que vous fixez. La
consigne fixe deux limites. La première est un nombre de tentatives, après
lequel l’agent s’arrête et rend compte de ce qu’il a trouvé, que le contrôle
passe ou non. La seconde dit ce que l’agent peut modifier, et le contrôle
lui-même n’est pas sur cette liste. Sans ces limites, un agent à qui l’on dit
de continuer jusqu’à ce que le test passe peut continuer longtemps, et le
chemin le plus court vers un test qui passe consiste souvent à modifier le
test. Automatiser un contrôle est l’une des compétences de vérification de la
carte des compétences de Brilliant pour le code avec l’IA (@Brilliant VER).
Les limites sont ce qui permet de confier le contrôle à l’agent sans risque.

La transcription ci-dessous est une illustration, sans reproduire les mots d’un
modèle précis.


simple `git diff` laisse de côté les fichiers que l’agent a créés, donc
indexez d’abord tout avec `git add -A`, et comparez les fichiers indexés à
l’étiquette. Un nouveau fichier apparaît alors dans la liste comme un fichier
modifié.

## Les barrières et les seconds avis

Le test est l’une des **barrières déterministes** qu’un projet peut avoir. Une
barrière déterministe est un contrôle dont le résultat ne dépend du jugement de
personne : tests, vérification des types, outils d’analyse (linters), builds et
validation de schéma. Une barrière fiable donne la même réponse pour la même
entrée, et c’est pourquoi une équipe peut laisser une barrière en échec bloquer
une fusion. Les mêmes barrières peuvent aussi terminer la boucle d’un agent.
Dans Claude Code, un hook qui s’exécute quand l’agent est sur le point de
s’arrêter peut lancer le test et renvoyer l’agent au travail jusqu’à ce que le
test passe, dans une limite que fixe Claude Code (@Claude Code best practices).
Décider quand le travail d’un agent est terminé à partir de ce que rapporte une
barrière est aussi un thème du cours de l’Academy Claude Code in action
(@Academy claude-code-in-action).

La revue par un second modèle est un autre genre de contrôle. Un modèle neuf
qui lit le diff peut trouver ce qu’aucune barrière ne teste : un problème de
conception, un cas pour lequel personne n’a écrit de test, une modification
hors de la consigne. Mais sa réponse est un jugement. Il peut manquer ce que le
modèle qui a écrit a manqué, et son verdict peut changer d’une exécution à
l’autre. Le guide de l’éditeur ajoute qu’un relecteur à qui l’on dit de
chercher des problèmes a tendance à en trouver même dans un bon travail, donc
une personne pèse aussi ses remarques (@Claude Code best practices). Utilisez
le second modèle comme second avis à côté des barrières, et jamais à leur
place.

<Exercise stretch="Choisissez ensuite un contrôle que vous faites à la main dans votre propre projet, comme ouvrir une page ou lire un rapport, et écrivez-le sous forme d’une commande qui sort avec le code 1 quand le contrôle échoue.">
Utilisez la copie de `~/loop-me` créée plus tôt dans la leçon, et faites-en un
dépôt git avec un commit étiqueté si ce n’est pas encore fait. Lancez votre
propre agent de code dans `~/loop-me`, pour qu’il travaille sur la copie et pas
sur votre clone, et donnez-lui la consigne de cette leçon. Laissez-le tourner,
ce qui prend quelques minutes.

Vérifiez ensuite l’exécution vous-même. Lancez `git add -A`, puis
`git diff --cached --stat before-run`, et confirmez que `test_nights.py` n’est
pas dans la liste. Lancez `git diff --cached before-run -- test_nights.py` et
confirmez qu’il n’affiche rien. Lancez `python3 test_nights.py` et confirmez
qu’il affiche `4 passed, 0 failed`. Un test que l’agent pouvait modifier est un
test auquel vous ne pouvez pas vous fier, et ces commandes montrent s’il a
changé.

Un bon résultat a une exécution qui s’est arrêtée en cinq tentatives au plus,
une liste de fichiers modifiés qui contient `importer.py` et rien d’autre, et
un test que vous avez lancé vous-même et qui passe. Répondez ensuite à une
question : si l’agent s’était arrêté après cinq tentatives avec le test
toujours en échec, qu’auriez-vous voulu trouver dans son rapport ?
</Exercise>

<Recap>
1. Transformez un contrôle manuel en commande que l’agent peut lancer et lire, qui sort avec le code 0 en cas de réussite et nomme ce qui a échoué sinon. L’agent peut alors la relancer après chaque modification, et vous n’avez plus à remarquer vous-même chaque erreur (@Claude Code best practices).
2. Une boucle d’autovérification bornée a une limite de tentatives, après laquelle l’agent s’arrête et rend compte, et une règle qui met le contrôle lui-même en lecture seule.
3. Après l’exécution, indexez tout avec `git add -A` et comparez avec un commit d’avant l’exécution. La liste montre si le test a changé et quels fichiers l’agent a ajoutés. Lancez ensuite le test vous-même. Une règle qui interdit de modifier le test bloque les outils de fichiers de l’agent, les commandes de fichiers du shell qu’il reconnaît et les redirections vers le fichier. Un script lancé par l’agent peut quand même écrire le fichier (@Claude Code permissions).
4. Les barrières déterministes, comme les tests, la vérification des types, les outils d’analyse, les builds et les contrôles de schéma, donnent la même réponse pour la même entrée quand elles sont fiables, et peuvent bloquer une fusion. La revue d’un second modèle est un second avis à côté d’elles et ne les remplace jamais (@Claude Code best practices).
</Recap>

<Habit id="look-for-the-test-file">
La prochaine fois qu’un agent vous dit que les tests passent, cherchez un fichier de test parmi les fichiers qu’il a modifiés avant de lire le reste de la modification. Utilisez `git status` pour le travail qu’il n’a pas committé, et `git diff --stat` par rapport au commit de départ quand il a fait des commits.
</Habit>
