Un agent de code écrit des tests rapidement, et ils passent. Cela vous dit que
les tests sont d’accord avec le code, sans vous dire qu’ils remarqueraient un
code faux. Dans cette leçon, vous cassez volontairement un petit programme et
vous lancez les tests qu’un agent a écrits pour lui. Certains passent toujours,
et vous en réécrivez un pour qu’il vérifie ce que le programme doit faire. Vous
voyez pourquoi un test qui passe par la petite interface d’un module continue
de passer après une modification correcte à l’intérieur. Vous relisez ensuite
une modification que l’agent a faite sur le même programme, et vous trouvez la
documentation qu’il a laissée périmer.

Le programme est `shop/`, un module de tarification pour une petite boutique en
ligne, dans le dépôt du cours. Il additionne les lignes d’une commande et
ajoute les frais de port : 4,95 euros (EUR), ou rien pour une commande de
50,00 EUR ou plus.

```python
FREE_SHIPPING_FROM = 50.00
SHIPPING = 4.95


def shipping(amount):
    """Return the shipping cost for an order with this subtotal."""
    if amount >= FREE_SHIPPING_FROM:
        return 0.0
    return SHIPPING
```

## Casser le code volontairement

Avec un agent, les **tests** doivent prouver ce que fait le code pour ses
utilisateurs, et vous relisez les tests que l’agent écrit d’aussi près que le
code. Les agents produisent volontiers des tests, et certains peuvent passer
parce qu’ils répètent ce que le code fait déjà. Le cours de l’Academy The
AI-native SDLC playbook (SDLC désigne le cycle de vie du développement
logiciel) soutient que, quand un agent produit la plus grande partie du code
d’une équipe, la revue et les tests deviennent les étapes lentes
(@Academy ai-native-sdlc-playbook). Une façon rapide de relire un test est de
rendre le code faux et de voir si le test le remarque.

Depuis la racine de votre clone du dépôt du cours, copiez la boutique à un
endroit à vous, et lancez-y ses tests.

```sh

cd ~/shop
python3 test_pricing.py; echo "exit status $?"
```

<Pitfall title="Le test qui a appris la nouvelle réponse">
Un ingénieur a demandé à un agent d’ajouter des codes de réduction à un
paiement. Après la modification, un test qui vérifiait le total d’une commande
connue échouait d’un centime, parce que le nouveau code arrondissait deux
fois. L’agent a modifié l’assertion pour comparer les totaux à une décimale
près, et la suite est passée au vert pendant que chaque commande avec une
réduction affichait un total faux d’un centime. Une nouvelle valeur attendue
dans un test est une modification de ce que le programme promet. Relisez-la
comme une modification de la spécification, et rejetez-la si la consigne ne
l’a pas demandée.
</Pitfall>

## Garder les tests rapides et inchangés

Un agent relance les tests après chaque modification. Leur durée décide du
nombre de tentatives qui tiennent dans une boucle : une suite d’une seconde
peut tourner après chaque modification, et une suite de vingt minutes est
lancée une fois à la fin, ou sautée. L’exemple de fichier d’instructions du
guide de l’éditeur de Claude Code a une ligne pour cela. Il demande à l’agent
de préférer lancer des tests isolés à la suite entière, pour la vitesse
(@Claude Code best practices). Donnez à l’agent les tests rapides de la partie
qu’il modifie, et lancez la suite complète avant la fusion.

L’agent ne doit pas non plus modifier les tests pour obtenir un succès. Le
chemin le plus court pour faire passer une modification en échec consiste à
supprimer le test, à le sauter ou à assouplir son assertion, comme l’a fait
l’agent du piège. Quand un agent peut modifier les tests, le rayon d’impact (blast radius)
d’une mauvaise modification inclut le contrôle qui devrait la détecter. La
règle pour un agent est donc qu’il ne supprime ni n’affaiblit jamais un test.
Un test qu’il juge faux le fait s’arrêter et expliquer pourquoi, et la décision
vous revient.

Une règle dans les instructions du projet est une demande. Claude Code lit son
fichier d’instructions au début d’une session et l’utilise comme contexte, et
rien dans le fichier n’est imposé (@Claude Code memory). La règle rend un test
affaibli moins probable, et c’est la relecture des fichiers de test qui en
trouve un.

## Tester par une petite interface

Les **modules profonds** font beaucoup de choses derrière une petite interface.
John Ousterhout décrit l’interface d’un module comme ce que ceux qui
l’appellent doivent apprendre, et ce que le module fait pour eux comme ce
qu’ils reçoivent en échange. Il soutient qu’un bon module demande peu à ceux qui
l’appellent et fait beaucoup pour eux (@Ousterhout 2021). Un module superficiel
a une interface presque aussi grande que son code, donc ceux qui l’appellent
doivent savoir comment il fonctionne à l’intérieur.

L’interface de la boutique pour un prix est `total(lines)`. Un appelant passe
les lignes d’une commande et reçoit le montant à payer, sans connaître le
seuil, le prix du port ni l’arrondi. `subtotal` et `shipping` sont publiques
aussi, mais ce sont des fonctions auxiliaires que `total` appelle. La
réécriture de `test_total_adds_shipping` qui détecte un mauvais prix n’utilise
que `total` :

```python
assert total([(1, 30.00)]) == 34.95
```

Elle échoue quand le prix est faux, et elle continue de passer quand un agent
modifie correctement l’intérieur de `pricing.py`, par exemple en enregistrant
les prix en centimes. Le test que vous avez réécrit plus tôt,
`assert shipping(10.00) == 4.95`, énonce aussi le bon prix, mais il appelle une
fonction auxiliaire. Une modification correcte de ce que `shipping` reçoit ou
renvoie oblige ce test à changer aussi, et le test de `total` reste tel quel.

Les deux tests qui recopiaient le code avaient un autre problème : ils tiraient
leur valeur attendue du code, donc ils étaient d’accord avec un mauvais prix.
Un test qui passe par l’interface, avec une valeur tirée de la spécification,
n’a aucun des deux problèmes.

Un module profond aide aussi la session suivante. Un agent qui modifie la règle
des frais de port modifie `pricing.py` et ses tests et aucun autre code, parce
qu’aucun appelant ne connaît la règle. Un agent qui se contente d’appeler le
module n’a besoin de lire que son interface. Ousterhout appelle fuite
d’information (information leakage) le contraire du masquage d’une décision.
Quand le prix du port est écrit dans le code de plusieurs modules, un
changement de prix doit modifier chacun d’eux (@Ousterhout 2021). Un agent
peut faire fuir une décision dans une modification qui passe tous les tests,
donc relisez l’interface dans un diff. Quand une fonction reçoit de nouveaux
paramètres, demandez-vous ce que chaque appelant doit désormais savoir. Le
README et `docs/pricing.md` énoncent aussi le prix, et la partie suivante les
relit.

## La documentation fait partie de la modification

La **documentation** est l’explication écrite du comportement d’un système : le
README, les pages de `docs/`, et les commentaires et docstrings du code. Un
agent sait écrire une bonne documentation à partir du code, et il peut tout
aussi facilement modifier le code et laisser la documentation dire autre chose.
Traitez la documentation comme une partie de la modification. La consigne
nomme ce qu’il faut mettre à jour, les instructions du projet disent où se
trouve la documentation, et la revue la vérifie.

Le fichier d’instructions de la boutique, `AGENTS.md`, dit où se trouve sa
documentation. Le guide de Claude Code suggère qu’un fichier d’instructions
renvoie à la documentation détaillée sans la recopier
(@Claude Code best practices).

```text
- Run `python3 test_pricing.py` after every change, and read what it prints.
- Never delete a test or loosen an assertion to make a change pass. If a
  test looks wrong, stop and say why.
- Documentation is in three places: `README.md` for customers,
  `docs/pricing.md` for the full rules, and the docstrings in `pricing.py`.
  A change to a price or a threshold updates all three in the same change.
```

Ce fichier, en anglais comme le reste de l’exemple, demande de lancer les
tests après chaque modification, interdit de supprimer un test ou d’assouplir
une assertion, et dit que la documentation se trouve à trois endroits :
`README.md` pour les clients, `docs/pricing.md` pour les règles complètes, et
les docstrings de `pricing.py`. Un changement de prix ou de seuil met à jour les
trois dans la même modification.

<Exercise stretch="Choisissez ensuite un test qu’un agent a écrit dans votre propre projet, cassez volontairement la ligne de code qu’il concerne, et regardez si le test échoue.">
L’exercice prend une dizaine de minutes et vous laisse un test réécrit et une
courte liste de lignes périmées. Il entraîne les contrôles qui trouvent un test
incapable d’échouer et une documentation qui ne correspond plus au code.

Depuis la racine de votre clone, faites une nouvelle copie de la boutique pour
la première partie :

```sh
cp -R site/examples/coding-with-agents/tests-and-docs-that-hold/shop ~/shop-boundary
cd ~/shop-boundary
```

Dans `shipping`, remplacez `>=` par `>`. Avant de lancer les tests, notez
lesquels des cinq vous vous attendez à voir échouer. Lancez
`python3 test_pricing.py` et comparez. Pour chaque test qui passe, nommez un
bug de `pricing.py` qu’il ne détecterait pas. Réécrivez ensuite
`test_large_order_ships_free` pour qu’il échoue avec la casse en place et passe
sans elle.

Pour la documentation, revenez à la racine de votre clone, faites une nouvelle
copie et donnez-lui un commit étiqueté :

```sh
cp -R site/examples/coding-with-agents/tests-and-docs-that-hold/shop ~/shop-docs
cd ~/shop-docs
git init
git add .
git commit -m "Before the agent's change"
git tag before-change
```

Lancez votre propre agent de code dans `~/shop-docs`, pour qu’il travaille sur
la copie et pas sur votre clone, et donnez-lui la consigne de cette leçon. Une
fois qu’il a terminé, lancez ces commandes :

```sh
git add -A
git diff --cached --stat before-change
python3 test_pricing.py
grep -n "50.00" README.md docs/pricing.md pricing.py
```

Un bon résultat a une liste d’échecs attendus qui correspond à l’exécution, un
test réécrit qui échoue avec la casse et passe sans elle, et une revue qui nomme
chaque endroit listé par `AGENTS.md` qui donne encore l’ancien seuil, ou
confirme qu’aucun ne le fait. Répondez ensuite à une question : quel test de
votre propre projet casseriez-vous en premier, et pourquoi celui-là ?
</Exercise>

<Recap>
1. Relisez le test d’un agent en rendant volontairement le code faux et en le lançant. Un test qui passe encore donne au code une entrée qui n’atteint jamais la ligne cassée, ou tire sa valeur attendue du code qu’il teste, donc il recopie l’implémentation. Réécrivez-le avec une entrée qui atteint la ligne et la valeur que le programme doit produire, tirée de la spécification ou calculée à la main.
2. Donnez à l’agent les tests rapides de la partie qu’il modifie pour qu’il les lance dans sa boucle (@Claude Code best practices), et lancez la suite complète avant la fusion. L’agent ne supprime, ne saute ni n’assouplit jamais un test pour faire passer une modification. Quand un test lui paraît faux, il s’arrête et dit pourquoi.
3. Une règle du fichier d’instructions est du contexte pour l’agent, et rien ne l’impose (@Claude Code memory). Lisez le diff des fichiers de test pour confirmer qu’aucun test n’a été supprimé, sauté ou assoupli.
4. Les modules profonds font beaucoup derrière une petite interface (@Ousterhout 2021). Testez-les par cette interface, et cherchez dans le diff d’un agent une modification qui oblige les appelants à connaître ce que le module cachait.
5. La documentation fait partie de la modification. La consigne nomme ce qu’il faut mettre à jour, les instructions disent où se trouve la documentation, et la revue cherche à ces endroits ce que la modification a rendu périmé.
</Recap>

<Habit id="break-one-line-first">
La prochaine fois que la modification d’un agent arrive avec de nouveaux tests, modifiez une ligne de son code pour la rendre fausse, lancez les tests, et regardez lesquels le remarquent avant d’approuver.
</Habit>
