Dans cette leçon, nous regardons le moment qui sépare deux phases de travail,
par exemple la fin de la planification et le début de l’implémentation. Une
session de planification remplit sa fenêtre de contexte (context window) avec les fichiers
qu’elle a lus et les idées qu’elle a essayées, y compris celles que vous avez
écartées. Une fois le plan écrit, vous choisissez ce avec quoi la phase
suivante commence : la même session, une nouvelle session qui part du plan
écrit, ou un résumé de l’ancienne. Chaque choix garde des choses différentes,
et chacun a un coût différent. La page n’a pas de code à lancer.

La leçon s’appuie sur deux leçons précédentes.
[*Dire à l’agent où est la tâche et où elle s’arrête*](/coding-with-agents/scoping-and-referencing/#désigner-le-fichier-au-lieu-de-le-décrire)
a montré comment désigner un fichier à un agent par son chemin, et un fichier
de plan est le fichier que vous désignez à la phase suivante.
[*Diriger le résumé avant le compactage*](/customizing-agents/compaction/#what-the-summary-replaces-and-what-comes-back)
a listé ce que Claude Code remet en place après un compactage. Cette page
utilise cette liste pour comparer les options. Quand elle nomme une
fonctionnalité de Claude Code, elle le dit, et les pages de l’éditeur ont été
vérifiées à la date donnée en fin de leçon.

## Ce que contient une session avant que vous tapiez

Une nouvelle session ne démarre pas vide. Son **contexte de départ** est tout
ce qui se trouve dans la fenêtre de contexte avant votre premier message. Dans
Claude Code, ce sont le prompt système (system prompt), les instructions de `CLAUDE.md` ou
`AGENTS.md`, les notes de la mémoire automatique, les noms des outils des
serveurs MCP (Model Context Protocol) connectés et une description d’une ligne
de chaque skill (@Claude Code context window). Les autres agents chargent leur
propre ensemble, et la plupart chargent un fichier d’instructions.

Le contexte de départ reste dans la fenêtre pendant toute la session. Claude
Code envoie toute la conversation avec chaque requête qu’il fait
(@Claude Code costs), et le contexte de départ part avec elle. Un gros contexte
de départ prend de la place à la tâche dans chaque session, y compris les
courtes. Dans Claude Code, la commande `/context` montre ce qui remplit la
fenêtre, par catégorie (@Claude Code context window).

Pour le réduire, sortez de `CLAUDE.md` les instructions propres à un seul
déroulé de travail, par exemple la façon de lancer une migration de base de
données, et mettez-les dans une skill, qui ne charge son texte complet que
lorsqu’elle sert. Lancez aussi `/mcp` pour désactiver les serveurs que vous
n’utilisez pas (@Claude Code costs). La leçon
[*Écrire les instructions de projet que l’agent lit à chaque session*](/coding-with-agents/project-instructions/)
a donné une seconde raison de garder le fichier d’instructions court : l’agent
suit un fichier court de façon plus fiable qu’un long.

## Trois façons de commencer la phase suivante

Prenez une session de planification sur le programme de liste de tâches des
leçons précédentes. Vous avez demandé à l’agent une commande
`due <n> <date>`. Il a lu `todo.py`, `store.py` et les tests, et il a essayé
deux formats de date. Vous avez écarté les dates en texte libre, parce que la
liste doit pouvoir se trier par date. Dans la conversation, vous avez aussi
rappelé à l’agent de ne pas modifier `legacy/`. L’agent a écrit le plan dans
`PLAN.md` : cinq étapes, les fichiers à modifier et le test à écrire en
premier. Le plan est terminé, et l’implémentation vient ensuite. Voici ce avec
quoi chaque option la fait commencer.

**Continuer dans la même session.** La phase suivante a tout : chaque fichier
que l’agent a lu, chaque sortie de commande et chaque idée que vous avez
écartée, mot pour mot. Cet historique est aussi le problème. À mesure que la
fenêtre de contexte se remplit, l’agent suit moins bien les instructions
données plus tôt et fait davantage d’erreurs (@Claude Code best practices).
Chaque requête de la phase d’implémentation renvoie aussi toute la
conversation de planification (@Claude Code costs).

**Effacer, et partir du plan écrit.** Dans Claude Code, `/clear` démarre une
nouvelle session (@Claude Code costs). La phase suivante a le contexte de
départ, le dépôt avec ses modifications non committées et les fichiers que
vous lui désignez, et rien de la conversation. Une fois une spécification
terminée, la page des bonnes pratiques recommande une nouvelle session pour
l’implémentation (@Claude Code best practices). La page sur les coûts ajoute
que `/clear` ne coûte rien (@Claude Code costs). Ce que vous perdez, c’est tout
ce qui a été dit sans être écrit.

**Compacter, puis continuer.** `/compact` remplace la conversation par un
résumé. Ensuite, Claude Code relit sur le disque le `CLAUDE.md` de la racine du
projet, les notes de la mémoire automatique, et le plan du mode plan, qui est
le propre fichier de plan de Claude Code. Il relit aussi jusqu’à cinq des
fichiers que l’agent a lus ou modifiés, en commençant par les plus récemment
modifiés. Un `PLAN.md` que l’agent a écrit dans le dépôt fait partie de ces
fichiers, donc il ne revient que s’il est parmi les cinq. Ce qu’ont affiché
les commandes et les étapes de raisonnement de l’agent ne sont pas gardés mot
pour mot (@Claude Code context window). Quand un gros morceau de travail vient
ensuite, la page sur la fenêtre de contexte suggère `/compact` avec des
instructions qui nomment ce que le résumé doit garder
(@Claude Code context window). Le compactage d’une longue conversation est
lui-même une grosse requête, parce que l’agent la lit en entier pour écrire le
résumé (@Claude Code costs). Et un résumé peut perdre un détail dont
l’importance n’apparaît que plus tard (@Anthropic context engineering).

Deux autres options sont des variantes de celles-ci. Un fichier de passation
est un plan écrit pour une session qui n’est pas terminée : ce qui a été fait,
ce qui reste et ce qui a été décidé. Et un sous-agent (subagent) démarre avec son propre
contexte vide et rend un court résumé, donc une grosse recherche reste hors de
votre fenêtre (@Anthropic context engineering).

## Décider en fin de phase

**Décider en fin de phase** consiste à choisir ce avec quoi la phase suivante
commence quand une phase se termine. Les sources ne donnent pas de règle pour
cela, mais elles désignent une question : la phase suivante poursuit-elle le
même problème, ou en commence-t-elle un nouveau ?

Une implémentation qui suit un plan terminé est un nouveau problème. Elle a
besoin du plan, des fichiers que le plan nomme et des raisons de ses choix.
Elle n’a pas besoin de la conversation de planification, donc effacez, et
partez du fichier de plan. Une session de débogage au milieu d’un bug difficile
est l’autre cas. La même page des bonnes pratiques dit qu’un long historique
peut valoir la peine d’être gardé pendant que vous travaillez sur un problème
difficile (@Claude Code best practices). Entre les deux, l’article sur
l’ingénierie du contexte associe le compactage à un travail fait de longs
échanges sur un seul problème, et les notes dans un fichier à un travail qui
avance par étapes planifiées (@Anthropic context engineering).

Quel que soit votre choix, faites d’abord une étape : écrivez ce que la phase
suivante doit garder. Effacer perd toute la conversation, et compacter ne garde
que ce que le résumé énonce. Dans la session de planification ci-dessus, c’est
la raison pour laquelle vous avez écarté les dates en texte libre.
Ajoutez-la à `PLAN.md` et relisez le fichier. Effacez ensuite, et commencez la
nouvelle session avec une consigne qui le désigne :

```text
Implémente la commande due comme le décrit PLAN.md. Commence par l’étape 1, le test.
```

La règle sur `legacy/` que vous avez tapée dans la conversation il y a une
heure n’a besoin d’aucune ligne, parce qu’elle est déjà dans `AGENTS.md`, et
la nouvelle session charge ce fichier. Une règle qui n’existe que dans la
conversation a besoin d’une ligne dans un fichier, sinon elle disparaît.

<Pitfall title="La raison que le résumé a perdue">
À la fin d’une longue session de planification, un ingénieur lance `/compact`
et passe à l’implémentation. Le plan est dans le résumé, et la raison de
l’abandon des dates en texte libre n’y est pas, parce qu’elle a été dite une
seule fois dans la conversation une heure plus tôt. Une heure plus tard,
l’agent propose des dates en texte libre « pour garder la modification
petite », et l’ingénieur explique la raison une seconde fois. Un résumé garde
ce que son auteur juge important à ce moment-là, et un détail peut se révéler
important plus tard (@Anthropic context engineering). La règle : avant
d’effacer ou de compacter, mettez dans un fichier ce que la phase suivante doit
garder, et lisez le fichier.
</Pitfall>

<Exercise stretch="Faites la même chose à la fin de votre prochaine vraie session de planification. Avant de choisir, lancez /context, ou la façon dont votre agent montre son contexte, et notez à quel point la fenêtre est pleine. Jugez une fin de phase sur le papier. Une session vient de finir de planifier
une commande `tag <n> <word>` pour le programme de liste de tâches. En
quatre-vingt-dix minutes, elle a lu `todo.py`, `store.py` et les tests, et elle
a essayé deux façons d’enregistrer les étiquettes dans un script de brouillon.
Vous avez écarté l’enregistrement des étiquettes dans le texte de l’élément,
parce que la sortie de `list` ne doit pas changer. L’agent a écrit dans
`PLAN.md` un plan en quatre étapes, qui ne mentionne pas l’approche écartée.
Dans la conversation, vous avez aussi rappelé à l’agent de ne pas modifier
`legacy/`, ce que dit déjà `AGENTS.md`. La fenêtre est pleine aux deux tiers
environ. Écrivez trois lignes courtes : avec quoi l’implémentation commence et
pourquoi, ce que la nouvelle phase perd, et ce que vous ajoutez à un fichier
avant le changement. Dix minutes suffisent.

Un bon résultat : l’implémentation commence par une session effacée et
`PLAN.md`, parce que c’est un nouveau problème et que le plan est écrit. La
nouvelle phase perd l’exploration avec la sortie du script de brouillon, et
tout ce qui n’a été dit que dans la conversation. Avant le `/clear`, vous
ajoutez l’approche écartée et sa raison à `PLAN.md`. La règle sur `legacy/` n’a
besoin d’aucune ligne, parce que `AGENTS.md` la contient. Répondez ensuite à
une question : qu’est-ce qui, dans le travail lui-même, vous ferait continuer
dans la session à la place ?
</Exercise>

<Recap>
1. Le contexte de départ est tout ce qui se trouve dans la fenêtre avant votre premier message, et il part avec chaque requête, donc gardez-en hors ce dont la tâche n’a jamais besoin (@Claude Code context window) (@Claude Code costs).
2. En fin de phase, vous choisissez ce avec quoi la phase suivante commence. Elle peut garder tout l’historique ou un résumé, ou repartir de ce qui est dans des fichiers.
3. Continuer garde tout, et une fenêtre pleine fait moins bien suivre ses instructions à l’agent (@Claude Code best practices).
4. Effacer et partir du plan écrit convient à une phase qui commence un nouveau problème, comme l’implémentation après la planification (@Claude Code best practices).
5. Compacter garde un résumé et perd le détail, et c’est lui-même une grosse requête (@Claude Code costs).
6. Avant d’effacer ou de compacter, écrivez dans un fichier ce que la phase suivante doit garder, et relisez le fichier.
</Recap>

<Habit id="plan-file-before-clear">
À la fin de votre prochaine session de planification, ajoutez au fichier de plan les décisions prises dans la conversation avant d’effacer, et commencez l’implémentation dans une session qui désigne ce fichier.
</Habit>
