Jusqu’ici dans ce parcours, le modèle répondait à un prompt et s’arrêtait.
Dans cette leçon, nous observons un agent jouet. Le même type de modèle est
placé dans une boucle avec deux outils, et sa tâche est une question sur un
dossier de notes de réunion. Le jouet est assez petit pour être lu d’une
traite. Son « modèle » est un script avec une liste fixe de réponses. Chaque
exécution ci-dessous donne le même résultat à chaque fois, et vous n’avez rien
à installer ni à lancer. Vous lisez trois transcriptions. À la fin, vous
saurez associer chaque ligne de l’une d’elles à sa phase, et dire pourquoi
l’exécution s’est arrêtée.

## Un modèle dans une boucle avec deux outils

Un modèle reçoit du texte et produit du texte, une fois. Il ne peut ni ouvrir
un fichier ni regarder dans un dossier. Un **agent** est un logiciel construit
autour d’un modèle, qui, lui, le peut. Le logiciel appelle le modèle et lit sa
réponse. Quand la réponse demande un outil, le logiciel exécute cet outil et
renvoie le résultat au modèle sous forme de texte supplémentaire, puis il
rappelle le modèle (@AEC-01). Le modèle apporte le jugement sur ce qu’il faut
faire ensuite, et le logiciel apporte les mains.

Le jouet dispose de deux outils. Avant toute exécution, le modèle apprend ce
qu’ils sont, en texte brut. Chaque outil a un nom, une phrase qui dit ce qu’il
fait, et ses paramètres, c’est-à-dire les détails que le modèle doit remplir
quand il demande l’outil.

```text
list_dir: List the files in a directory. Parameter: path, the directory to list.
read_file: Return the text of one file. Parameter: path, the file to read.
```

(`list_dir` liste les fichiers d’un dossier dont le paramètre `path` donne le
chemin, et `read_file` renvoie le texte du fichier désigné par `path`. Les
descriptions sont en anglais, comme dans la plupart des outils réels.)

Ce texte est tout ce que le modèle sait des outils. Il ne voit jamais le code
qui se trouve derrière `list_dir`, et il n’en a pas besoin. Quand il veut la
liste d’un dossier, il écrit une demande qui nomme l’outil et remplit le
paramètre, et la boucle fait le reste (@Academy claude-platform-101). Un outil
dont la description est vague est mal utilisé, parce que cette phrase est tout
ce dont le modèle dispose.

Le dossier dans lequel travaille le jouet contient trois courtes notes de
réunion, du 14, du 21 et du 28 mars.

## Lire la transcription

La première tâche est une question sur les notes. La transcription ci-dessous
est la sortie du jouet, ligne pour ligne. Les lignes qui commencent par
`modèle :` sont ce que le modèle a produit, et celles qui commencent par
`boucle :` sont ce que le logiciel qui l’entoure a fait en réponse.

```text
tâche : Quelle note de réunion mentionne la livraison de juin ?
1. modèle : appelle list_dir avec le chemin "notes"
   boucle : a exécuté list_dir, résultat : 2026-03-14-lantern.txt, 2026-03-21-budget.txt, 2026-03-28-lantern.txt
2. modèle : appelle read_file avec le chemin "notes/2026-03-14-lantern.txt"
   boucle : a exécuté read_file, résultat : Projet Lantern, 14 mars. Livraison des cartes capteurs déplacée d’avril à juin. Ana confirme la date d’ici vendredi.
3. modèle : terminé. La note du 14 mars : la livraison des cartes capteurs passe d’avril à juin.
boucle : arrêt, le modèle a dit avoir terminé après 3 étapes
```

Lisez lentement l’étape 1, parce qu’elle contient toute l’idée. Le modèle n’a
pas listé le dossier. Il a écrit les mots `appelle list_dir avec le chemin "notes"`,
qui sont du texte comme n’importe quelle autre réponse. La boucle a reconnu ce
texte comme une demande, a exécuté le vrai outil `list_dir` sur le vrai
dossier, et a placé les trois noms de fichiers dans la conversation, comme la
prochaine chose que le modèle lit. À l’étape 2, le modèle, qui connaît
désormais les noms des fichiers, a demandé à lire celui dont le nom évoquait le
bon projet. À l’étape 3, il avait ce qu’il lui fallait et a écrit une réponse au
lieu d’une demande, et la boucle l’a vu et s’est arrêtée.

Le texte du modèle n’a atteint le dossier qu’à travers la boucle. Dans un vrai
agent, la boucle est aussi l’endroit où les permissions sont vérifiées et où
une demande peut être refusée. Quand on dit qu’un agent « a lu un fichier »,
c’est cet échange en deux lignes qui s’est produit.

## Observer, réfléchir, agir

La transcription a un rythme, et la **boucle d’agent** est ce rythme. Chaque
étape est un tour de boucle : un appel au modèle, sa réponse, et l’exécution
d’outil qui suit, s’il y en a une (@AEC-01). Un tour a trois phases :

- **Observer.** Le modèle lit ce qu’il a sous les yeux : la tâche au départ,
  puis le résultat du dernier outil.
- **Réfléchir.** Le modèle décide de ce qu’il fait ensuite et l’écrit, sous
  forme de demande d’outil ou de réponse. Dans la transcription, ce sont toutes
  les lignes `modèle :`.
- **Agir.** La boucle exécute l’outil demandé par le modèle et renvoie le
  résultat. Dans la transcription, ce sont toutes les lignes
  `boucle : a exécuté`.

Le modèle observe ensuite le résultat, et le tour recommence. L’étape 1 de la
transcription, c’est observer (la tâche), réfléchir (`appelle list_dir`), agir (la
liste revient). L’étape 2, c’est observer (les noms de fichiers), réfléchir
(`appelle read_file`), agir (la note revient). L’étape 3, c’est observer (la note)
et réfléchir (`terminé`), sans agir, parce que le modèle a produit une réponse et
qu’il ne restait rien à exécuter.

Cette distinction compte quand quelque chose tourne mal. Une réponse fausse
après la lecture correcte d’un fichier est un problème de réflexion, et la
correction se trouve dans le prompt ou dans le modèle. Une demande correcte qui
a renvoyé une erreur est un problème d’action, et la correction se trouve dans
l’outil. Un agent qui a lu le mauvais fichier a raisonné correctement sur une
mauvaise observation, et la correction passe souvent par une meilleure
description d’outil ou un meilleur nom de dossier. Nommer la phase vous dit où
chercher.

## Comment la boucle se termine

Une boucle sans fin est un défaut, et chaque agent a donc des règles d’arrêt.
Le jouet en a deux, et un vrai agent en ajoute une troisième (@AEC-01).

Le modèle dit qu’il a terminé. C’est la bonne fin, et la première transcription
la montre : le modèle a écrit une réponse au lieu d’une demande, et la boucle
s’est arrêtée après 3 étapes.

La limite d’étapes est atteinte. La boucle compte les étapes et s’arrête à un
nombre fixé, même quand le modèle n’a pas terminé. Cette limite vous protège
d’un modèle qui continue à demander des outils sans avancer, ce qui fait
grimper la facture et, avec des outils qui modifient des choses, continue à
les modifier. Voici le jouet sur une tâche avec une limite de 3 étapes, avec un
script qui liste deux fois le dossier puis lit le mauvais fichier.

```text
tâche : Qui confirme la date de livraison ?
1. modèle : appelle list_dir avec le chemin "notes"
   boucle : a exécuté list_dir, résultat : 2026-03-14-lantern.txt, 2026-03-21-budget.txt, 2026-03-28-lantern.txt
2. modèle : appelle list_dir avec le chemin "notes"
   boucle : a exécuté list_dir, résultat : 2026-03-14-lantern.txt, 2026-03-21-budget.txt, 2026-03-28-lantern.txt
3. modèle : appelle read_file avec le chemin "notes/2026-03-21-budget.txt"
   boucle : a exécuté read_file, résultat : Revue budgétaire, 21 mars. Les frais de déplacement sont sous le prévisionnel. Le budget de formation est approuvé.
boucle : arrêt, la limite de 3 étapes est atteinte, pas de réponse
```

La réponse se trouvait dans la note du 14 mars, et le script du modèle l’aurait
lue à l’étape 4. La boucle n’a pas permis d’étape 4. La transcription n’a pas de
ligne de réponse, parce que le modèle n’a jamais eu l’occasion d’en écrire une.
La dernière chose qu’il a faite, c’est demander à lire la note budgétaire. Une
limite qui arrête une exécution l’arrête toujours au milieu de quelque chose.

Une personne l’arrête. Dans un vrai agent, la boucle fait une pause et demande
l’autorisation avant une action difficile à annuler, et une personne peut
refuser, ou fermer la fenêtre à tout moment (@DLAI-11). Vu du modèle, un arrêt
de ce genre ressemble à la limite d’étapes : la dernière demande a été faite, et
aucune réponse ne suit.

<Pitfall title="Arrêtée au milieu">
Une équipe confie à un agent un dossier de quarante rapports de clients et une
tâche : lire chacun, écrire une ligne d’état dans `summary.txt`, et terminer
par le nombre de rapports qui demandent un rappel. L’agent dispose d’un outil
qui écrit dans un fichier, et d’une limite de 50 étapes, que l’équipe jugeait
généreuse. Lister le dossier prend une étape, et chaque rapport en prend deux
de plus, une lecture et une écriture : l’étape 50 est donc la lecture du
rapport 25, et la boucle s’arrête avant son écriture. `summary.txt` contient
24 lignes sur 40, pas de total, et aucune mention d’un manque. La personne qui
l’ouvre le lendemain matin voit un fichier d’apparence terminée, avec un
nombre de lignes qui se trouve être trop faible, et rien sur la page n’explique
pourquoi. La limite d’étapes a fait son travail en mettant fin à l’exécution,
et elle ne peut pas faire l’autre travail, celui de terminer la tâche. Une
exécution qui a atteint une limite doit être lue comme une exécution
interrompue. Regardez la dernière demande et ce qu’elle a fait à moitié, puis
décidez s’il faut relancer à partir de là ou jeter le résultat partiel.
</Pitfall>

Voici une troisième transcription, pour une autre tâche sur les trois mêmes
notes. Lisez-la une fois. Puis, sur papier ou dans une note, écrivez une ligne
par étape, sous la forme « étape, outil utilisé, phases », où les phases sont
observer, réfléchir et agir. L’étape 1 de la première transcription
s’écrirait « 1, list_dir, observer (tâche), réfléchir (demande), agir
(liste) ». Terminez par une ligne qui nomme la façon dont l’exécution s’est
terminée et comment vous le savez. Dix minutes suffisent.

```text
tâche : Combien de notes de réunion portent sur le projet Lantern ?
1. modèle : appelle list_dir avec le chemin "notes"
   boucle : a exécuté list_dir, résultat : 2026-03-14-lantern.txt, 2026-03-21-budget.txt, 2026-03-28-lantern.txt
2. modèle : appelle read_file avec le chemin "notes/2026-03-14-lantern.txt"
   boucle : a exécuté read_file, résultat : Projet Lantern, 14 mars. Livraison des cartes capteurs déplacée d’avril à juin. Ana confirme la date d’ici vendredi.
3. modèle : appelle read_file avec le chemin "notes/2026-03-21-budget.txt"
   boucle : a exécuté read_file, résultat : Revue budgétaire, 21 mars. Les frais de déplacement sont sous le prévisionnel. Le budget de formation est approuvé.
4. modèle : appelle read_file avec le chemin "notes/2026-03-28-lantern.txt"
   boucle : a exécuté read_file, résultat : Projet Lantern, 28 mars. Le pilote d’Utrecht passe en juillet. Bram rédige le guide d’installation court.
5. modèle : terminé. Deux des trois notes portent sur le projet Lantern : le 14 et le 28 mars.
boucle : arrêt, le modèle a dit avoir terminé après 5 étapes
```

Un bon résultat a cinq lignes, dont quatre nomment un outil et la cinquième
aucun, parce que l’étape 5 comporte une réflexion et aucune action. La ligne
de fin dit que le modèle a écrit une réponse, et désigne comme preuve la ligne
`terminé` et la dernière ligne de la boucle. En écrivant, remarquez que le modèle a
lu la note budgétaire alors que son nom donnait déjà la réponse. Un modèle dans
une boucle fait ce que lui dicte son jugement, une étape à la fois, et une
étape qu’il aurait pu sauter coûte autant qu’une étape nécessaire. À quel
endroit de cette transcription une meilleure description d’outil, ou un
meilleur nom de fichier, aurait-elle fait gagner une étape ?

</Exercise>

<Recap>

1. Un agent est un modèle placé dans une boucle avec des outils. Le modèle
   produit du texte, et quand ce texte est une demande, la boucle exécute
   l’outil et renvoie le résultat sous forme de texte supplémentaire. Le
   modèle n’exécute jamais rien lui-même (@AEC-01).
2. Un outil est décrit au modèle par son nom, son usage et ses paramètres, en
   texte brut, et cette description est tout ce dont dispose le modèle pour
   décider quand et comment le demander.
3. Chaque étape de la boucle se compose d’observer (lire la tâche ou le
   dernier résultat), réfléchir (écrire une demande ou une réponse) et agir
   (la boucle exécute l’outil). Nommer la phase vous dit d’où vient une
   erreur.
4. La boucle se termine quand le modèle écrit une réponse, quand la limite
   d’étapes est atteinte, ou quand une personne l’arrête. Une exécution qui
   s’est terminée sur une limite ou un arrêt a été interrompue au milieu d’une
   étape, et sa sortie doit être lue comme telle.

</Recap>
