Dans la leçon précédente, vous avez regardé un agent jouet avancer dans une
tâche étape par étape. Personne n’a rien tapé entre ces étapes, et pourtant le
modèle a été rappelé à chacune d’elles. Cette leçon ralentit la boucle jusqu’à
l’appel unique. Vous suivez un prompt à travers tous les appels qu’il a
déclenchés et vous voyez ce qui est envoyé au modèle à chaque fois et ce qui
revient. Vous apprenez ensuite pourquoi le modèle a besoin de tout
l’historique à chaque appel. À la fin, vous saurez lire le journal d’un agent
et compter les appels qu’un prompt a coûtés.

## Un prompt, trois requêtes

Voici de nouveau la première transcription de la leçon précédente.

```text
task: Quelle note de réunion mentionne la livraison de juin ?
1. model: call list_dir with path "notes"
   loop: ran list_dir, result: 2026-03-14-lantern.txt, 2026-03-21-budget.txt, 2026-03-28-lantern.txt
2. model: call read_file with path "notes/2026-03-14-lantern.txt"
   loop: ran read_file, result: Projet Lantern, 14 mars. Livraison des cartes capteurs déplacée d’avril à juin. Ana confirme la date d’ici vendredi.
3. model: done. La note du 14 mars : la livraison des cartes capteurs passe d’avril à juin.
loop: stopped, the model said it is done after 3 steps
```

Une personne a posé une question. Derrière elle, le logiciel qui entoure le
modèle a appelé le modèle trois fois, une fois pour chaque ligne `model:`.
Chacun de ces appels est une **requête au modèle** : le logiciel envoie au
modèle un paquet de texte, et le modèle renvoie une réponse
(@Claude docs messages). Une requête se termine quand sa réponse revient. Si la
réponse demande un outil, le logiciel l’exécute, et le résultat part vers le
modèle dans la requête suivante. Si la réponse ne demande rien, l’exécution est
terminée (@Claude Code agent loop).

Chaque requête, avec sa réponse et l’exécution d’outil qui suit, est un tour de
boucle, le même tour que vous avez découpé en observer, réfléchir et agir dans
la leçon précédente. L’étape 3 n’avait pas d’action, mais c’était quand même
une requête, parce qu’il fallait interroger le modèle avant qu’il puisse écrire
sa réponse.

Le logiciel qui envoie les requêtes et exécute les outils s’appelle le
**harnais**. La leçon précédente l’appelait la boucle. La leçon suivante montre
ce qu’il contient d’autre, et dans cette leçon il fait deux choses : il envoie
chaque requête, et il exécute les demandes d’outil qui reviennent.

## Une réponse, plusieurs appels d’outil

Une réponse peut demander plusieurs outils à la fois (@Claude Code agent loop).
Un modèle qui a besoin de trois fichiers peut demander les trois dans une même
réponse. Le harnais exécute alors les trois et renvoie les trois résultats
ensemble, dans une seule nouvelle requête. Le nombre d’appels d’outil et le
nombre de requêtes sont donc souvent différents.

Dans un journal, la règle de comptage est la suivante : après la première
requête, une nouvelle requête ne commence que lorsque le harnais a quelque
chose de nouveau à envoyer, c’est-à-dire les résultats des outils qu’il vient
d’exécuter. Des lignes du modèle sans ligne du harnais entre elles sont venues
dans la même réponse. Comptez les réponses, et vous aurez compté les requêtes.

## Ce que contient chaque requête

Une transcription montre ce que le modèle a écrit et ce que les outils ont
renvoyé. Elle ne montre pas ce que contenait chaque requête. Voici la même
exécution du jouet, écrite cette fois comme le journal du harnais lui-même, de
ce qu’il a envoyé. Ce journal a été écrit pour cette leçon afin de montrer le
contenu des requêtes, et un vrai harnais enregistre davantage de détails, comme
le texte exact de chaque partie.

```text
prompt : Quelle note de réunion mentionne la livraison de juin ?

requête 1
  le harnais envoie : instructions, descriptions d’outils (list_dir, read_file),
    historique : le prompt
  le modèle répond : call list_dir with path "notes"
  le harnais exécute list_dir, et le dossier renvoie 3 noms de fichiers

requête 2
  le harnais envoie : instructions, descriptions d’outils (list_dir, read_file),
    historique : le prompt, réponse 1, résultat 1
  le modèle répond : call read_file with path "notes/2026-03-14-lantern.txt"
  le harnais exécute read_file, et le dossier renvoie le texte de la note

requête 3
  le harnais envoie : instructions, descriptions d’outils (list_dir, read_file),
    historique : le prompt, réponse 1, résultat 1, réponse 2, résultat 2
  le modèle répond : done. La note du 14 mars : la livraison des cartes capteurs passe d’avril à juin.
  aucun outil n’a été demandé, le harnais arrête donc l’exécution
```

Chaque requête contient les instructions, les descriptions d’outils et
l’historique (@Claude Code agent loop) :

- **Les instructions.** Le texte permanent que le modèle lit avant la tâche, le
  prompt système vu plus tôt dans ce parcours. Il est le même dans chaque
  requête.
- **Les descriptions d’outils.** Le nom, l’usage et les paramètres de chaque
  outil, comme dans la leçon précédente. Elles aussi sont les mêmes à chaque
  fois.
- **L’historique.** Le prompt, suivi de chaque réponse écrite par le modèle et
  de chaque résultat revenu, dans l’ordre. C’est la partie qui grandit. La
  requête 1 a un élément dans son historique, la requête 2 en a trois, et la
  requête 3 en a cinq.

Dans la documentation de l’API Messages, l’historique est une liste de
messages qui alternent entre le côté de la personne et le côté du modèle, et un
résultat d’outil revient du côté de la personne, dans le message qui suit la
réponse qui l’a demandé (@Claude docs messages). C’est le harnais qui écrit
cette liste. La personne n’en a tapé que le premier élément.

## Le modèle ne garde rien d’une requête à l’autre

Regardez de nouveau la requête 3. Pour écrire sa réponse, le modèle a besoin
du texte de la note du 14 mars. Il a lu cette note dans la requête 2. Pourquoi
le harnais envoie-t-il donc la note une nouvelle fois ?

Parce que le modèle ne garde rien d’une requête à l’autre. C’est un **modèle
sans état** : chaque requête reçoit une réponse fondée sur ce que contient
cette requête et sur ce que le modèle a appris à l’entraînement, et sur rien
d’autre. La documentation de l’API Messages dit qu’une conversation de
plusieurs messages est sans état, et que l’appelant renvoie les messages
précédents avec chaque nouvelle requête (@Claude docs messages). Dans la
requête 3, le modèle ne « se souvient » de la note que parce que la note figure
dans l’historique envoyé par le harnais.

Les requêtes grossissent au fil de l’exécution. L’historique de chaque requête
contient tout ce qui s’est passé jusque-là. Une longue session envoie un long
historique à chaque appel. Le contexte continue de grandir au fil des tours
d’une session, et rien ne le vide entre les tours (@Claude Code agent loop).
Les leçons sur le coût des jetons, plus loin dans ce parcours, s’appuient sur
ce point.

C’est le harnais qui décide de ce que sait le modèle. Si le harnais omet
quelque chose de l’historique, le modèle ne l’a jamais vu, du point de vue de
cette requête. Quand une session devient trop longue, un harnais peut
remplacer la partie la plus ancienne de l’historique par un court résumé, et
un détail du début peut se perdre dans ce résumé (@Claude Code agent loop).

Ce qui ressemble à la mémoire de l’agent est du texte que le harnais garde et
renvoie. Effacez la conversation, et à partir de la requête suivante le modèle
n’en sait plus rien.

## Modèle, harnais, environnement

Chaque étape d’une exécution est faite par le modèle, le harnais ou
l’environnement. Le modèle choisit : il écrit une réponse, qui est soit une
demande d’outil, soit une réponse finale. Le harnais exécute : il envoie les
requêtes, vérifie si un appel d’outil est autorisé, et exécute l’outil.
L’**environnement** est ce sur quoi agissent les outils : les fichiers, les
programmes, les services et les données à la portée de l’agent. Quand un outil
s’exécute, le changement se produit dans l’environnement, et ce que renvoie
l’environnement est le résultat de l’outil.

Dans l’exécution du jouet, le modèle a choisi de lister le dossier, puis de
lire une note. Le harnais a envoyé trois requêtes et exécuté deux outils.
L’environnement était le dossier de notes, qui a renvoyé trois noms de fichiers
puis le texte d’une note.

La vérification des permissions fait partie du harnais. Quand le harnais
refuse un appel d’outil, rien n’atteint l’environnement, et le harnais renvoie
le refus au modèle comme résultat de cet outil (@Claude Code agent loop). Le
modèle lit le refus comme n’importe quel autre résultat. Le plus souvent, il
essaie autre chose, ou il indique à la personne que l’étape n’a pas pu être
faite.

Les trois parties échouent de façons différentes : nommer la partie vous dit
donc où chercher. Un mauvais choix de fichier relève du modèle. Un appel d’outil
qui aurait dû être refusé et ne l’a pas été relève du harnais. Un fichier
manquant ou périmé relève de l’environnement. L’environnement est aussi
l’endroit où une erreur fait ses dégâts, et c’est pourquoi une copie d’un
dossier est un endroit plus sûr pour un agent que le dossier lui-même.

<Pitfall title="La règle de la première heure">
Une personne commence une longue session avec un agent en disant « ne déplace
jamais rien dans le dossier d’archives ». L’agent respecte la règle toute la
matinée. L’après-midi, il déplace deux fichiers dans les archives. La personne
conclut que le modèle a oublié la règle, ou l’a ignorée. Ni l’un ni l’autre ne
s’est produit. La session s’était allongée, le harnais avait donc remplacé la
partie la plus ancienne de l’historique par un résumé, et ce résumé ne
contenait aucune ligne sur les archives (@Claude Code agent loop). À partir de
cette requête, la règle n’était plus du tout sous les yeux du modèle. Une règle
qui doit valoir pendant toute une session a sa place dans le fichier
d’instructions de l’agent, que le harnais ajoute à chaque requête. Un message du
début de la conversation peut, lui, finir dans un résumé qui l’omet
(@Claude Code agent loop).
</Pitfall>

note aussi que les instructions et les descriptions d’outils étaient les mêmes à

<Recap>

1. Un prompt adressé à un agent déclenche en général plusieurs requêtes au
   modèle. Chaque requête est un appel au modèle et reçoit une réponse, et une
   nouvelle requête suit chaque lot de résultats d’outil, jusqu’à ce qu’une
   réponse ne demande aucun outil (@Claude Code agent loop).
2. Une réponse peut demander plusieurs outils à la fois : comptez donc les
   requêtes d’après les réponses du modèle.
3. Chaque requête transporte les instructions, les descriptions d’outils et
   tout l’historique jusque-là, et seul l’historique grandit.
4. Le modèle est sans état. Il ne garde rien d’une requête à l’autre, et il ne
