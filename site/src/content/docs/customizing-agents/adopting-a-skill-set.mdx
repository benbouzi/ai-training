Un collègue recommande `workbench`, un jeu de huit skills pour le travail de
développement courant, des plans de tickets aux messages de commit. Le jeu est
publié sous forme d’un seul plugin, et votre équipe veut deux de ses skills. Dans
cette leçon, nous examinons le jeu comme vous examineriez une bibliothèque, et
nous prenons les deux skills. Nous comparons ensuite ce qu’elles changent dans
une session avec ce qu’elles ajoutent au contexte.

Le jeu est inventé pour le cours. Il se trouve dans le dépôt du cours, dans
`site/examples/customizing-agents/adopting-a-skill-set/workbench/`, à côté d’un
court script Python, `vet.py`, qui liste ce que contient chaque skill d’un jeu.
Le script ne fait que lire des fichiers, et rien dans cette leçon n’installe le
jeu ni ne lance ses scripts. Lancez les commandes depuis ce dossier, et
remplacez `<course-repo>` par le chemin de votre copie du dépôt du cours.

```sh
cd <course-repo>/site/examples/customizing-agents/adopting-a-skill-set
```

## Ce que vous prenez en charge avec un jeu de skills

**Les jeux de skills publiés** sont des collections de skills qu’un éditeur ou
un développeur maintient pour que d’autres les installent, souvent sous forme de
plugin. Les éditeurs de modèles, les fabricants d’outils et des développeurs
indépendants en publient tous. Un jeu de ce genre est une dépendance, et ses
skills agissent dans vos sessions. Elles changent chaque fois que l’auteur publie
une nouvelle version.

Un même jeu peut aussi contenir des skills sous des licences différentes. Le jeu
public d’Anthropic en est un exemple : beaucoup de ses skills sont sous licence
Apache 2.0, et ses skills de documents ont un code seulement consultable (source
available), donc vous pouvez les lire, mais elles ne sont pas open source
(@anthropics skills).

Une skill agit de plus de façons que son texte ne le laisse penser. Ses
instructions disent à Claude quoi faire, et les étapes peuvent dire à Claude de
lancer les scripts fournis avec la skill. L’en-tête d’une skill peut aussi avoir
un champ `allowed-tools`. Pendant que la skill s’exécute, Claude peut utiliser
les outils qu’il liste sans vous demander d’abord. L’auteur de la skill décide
donc d’une partie de vos permissions. Le champ prend effet même dans un dossier
que vous n’avez jamais marqué comme fiable, donc lisez-le dans chaque skill que
vous n’avez pas écrite (@Claude Code skills). Quand le jeu est un plugin, il peut
aussi apporter des hooks et des serveurs, et la leçon précédente les a lus.

Même quand rien n’y tourne, un jeu de skills a un coût. Un plugin activé ajoute
une courte entrée à chaque tour de chaque session : le nom et la description de
chaque skill que Claude peut lancer de lui-même. Claude ne lit le reste du
`SKILL.md` d’une skill que quand la skill sert (@Claude Code plugins). C’est la
première étape que [Ne charger que ce dont la skill a besoin](/customizing-agents/progressive-disclosure/)
a mesurée pour une skill, et un jeu a une entrée de ce genre par skill.

## Examiner le jeu comme une bibliothèque

Avant d’installer un jeu, cherchez ces réponses.

- **La licence.** Sous quelle licence est chaque skill que vous comptez utiliser ?
  Le format ouvert des skills a un champ `license` facultatif dans l’en-tête,
  pour un nom de licence ou le nom d’un fichier de licence à côté de la skill
  (@Agent Skills spec). Une skill qui n’a ni l’un ni l’autre ne vous donne aucune
  permission de la copier.
- **La maintenance.** Qui maintient le jeu, quand a-t-il changé pour la dernière
  fois, et comment ses modifications sont-elles publiées ? Un journal des
  modifications, des versions et un suivi des tickets répondent à l’essentiel.
  Notez la version ou le commit que vous avez lu.
- **Le contenu.** Que fait chaque skill ? Lisez chaque skill, chaque script et
  chaque ligne `allowed-tools` avant d’installer. La leçon précédente a fait de
  même pour les hooks et les serveurs d’un plugin.
- **Les alternatives.** Qu’est-ce qui ferait aussi le travail ? Un jeu de huit
  skills, c’est huit descriptions dans votre contexte et huit choses à tenir à
  jour. Quand vous en avez besoin de deux, copier ces deux-là ou écrire les
  vôtres peut coûter moins cher.

`vet.py` répond à la question de la licence et à une partie de la question du
contenu pour toutes les skills d’un coup. Chaque skill reçoit une ligne. Elle
montre la licence et le nombre de scripts, puis qui peut invoquer la skill et une
estimation des jetons (tokens) que son nom et sa description ajoutent à chaque session. Il
compte le même texte avec la même règle qu’`inventory.py` dans la leçon
précédente. Une skill que vous seul pouvez invoquer compte pour 0 jeton, parce
que sa description reste hors du contexte. Quand une skill a une ligne
`allowed-tools`, le script l’affiche à la fin de la ligne de cette skill.

## Prendre deux skills à la fois

Adoptez un jeu une ou deux skills à la fois, et utilisez-les un moment sur un vrai
travail avant d’en ajouter d’autres. Quand une seule chose a changé, un résultat
meilleur ou pire désigne la skill qui en est la cause.

Un plugin ne vous laisse pas choisir parmi ses skills. Le réglage
`skillOverrides`, qui masque une skill personnelle ou de projet ou la garde hors
du contexte, ne s’applique pas aux skills qui viennent d’un plugin. Vous les
gérez avec `/plugin`, en activant ou en désactivant le plugin entier
(@Claude Code skills). Quand un jeu publie chaque skill comme son propre plugin,
n’installez que les plugins dont vous avez besoin. Quand il publie un seul
plugin, comme `workbench`, copiez les deux skills dont la licence le permet dans
le dossier `.claude/skills/` du projet, et notez la version que vous avez copiée.
À partir de là, vous prenez les mises à jour à la main, après avoir lu le journal
des modifications.

Pour `workbench`, prenez `plan-ticket` et `review-diff`. Les deux sont sous
Apache-2.0, n’ont pas de scripts et ne préapprouvent aucun outil. Donnez leurs
noms à `vet.py` après le dossier du jeu, et il ne liste que ces deux-là, avec
leur coût à côté du coût du jeu entier.

contexte, et une skill dont la description est abandonnée est plus difficile à
rapprocher d’une demande pour Claude (@Claude Code skills).

Dans une vraie session, vérifiez deux choses après avoir ajouté les skills.

- **Ce qu’elles coûtent.** Lancez `/context` avant et après les avoir ajoutées.
  Sa ligne Skills montre la taille de la liste des skills que reçoit le modèle
  (@Claude Code skills).
- **Ce qu’elles changent.** Rassemblez deux ou trois vraies demandes, et lancez
  chacune dans une session neuve avec la skill active, puis de nouveau avec la
  skill réglée sur `"off"` dans `skillOverrides`. Quand Claude lance une skill,
  vous savez que sa description a correspondu. Seule la comparaison montre si le
  résultat s’est amélioré (@Claude Code skills).

Agissez ensuite selon ce que vous avez trouvé. Une skill qui n’a pas changé les
résultats coûte quand même du contexte et demande quand même des mises à jour,
donc supprimez son dossier. Quand vous lancez une skill vous-même de temps en
temps sans jamais avoir besoin que Claude la lance, donnez-lui
`disable-model-invocation: true` dans son en-tête, et sa description quitte le
contexte. Au bout de quelques semaines, `/skill-doctor` liste le contexte que
prend chaque skill et sa fréquence d’usage, et signale les skills que personne
n’a jamais invoquées (@Claude Code skills).

<Pitfall title="Huit skills pour deux">
Une développeuse installe tout le plugin `workbench` en portée utilisateur pour
avoir `plan-ticket`. Un mois plus tard, elle trouve un fichier
`~/.workbench/settings.json` dans son dossier personnel, avec la télémétrie
activée, et elle ne se souvient pas de l’avoir approuvé. La skill `setup-env` a
correspondu à la demande « prépare ce projet », et sa ligne `allowed-tools` a
permis à Claude de lancer `bootstrap.py` sans demander. Les messages de commit
ont aussi un aspect différent dans chaque projet, et on ne sait pas quelle skill
en est la cause. Un jeu apporte chacune de ses skills dans chaque session où il
est activé. Lisez la ligne `allowed-tools` et les scripts de chaque skill, et ne
prenez que les skills dont vous avez besoin, une ou deux à la fois.
</Pitfall>

<Exercise stretch="Après une semaine de vrai travail avec les deux skills, lancez /skill-doctor, retirez toute skill qui n’a changé aucun résultat, et seulement ensuite prenez-en une troisième dans le jeu.">
Choisissez vous-même un jeu de skills public, par exemple celui d’un éditeur de
modèles, d’un fabricant d’outils ou d’un développeur dont vous suivez le travail.
Examinez-le, prenez deux de ses skills dans une copie de brouillon d’un projet, et

que les skills peuvent changer avant de commencer. Leurs étapes peuvent modifier
des fichiers, lancer leurs scripts et lancer des commandes, et une ligne
`allowed-tools` permet à Claude d’utiliser les outils qu’elle nomme sans
demander, même dans un dossier que vous n’avez jamais marqué comme fiable
(@Claude Code skills). L’exercice utilise un clone neuf sans moyen de pousser, et

skill s’exécutent avec vos droits d’utilisateur, donc ils peuvent aussi modifier
des fichiers de votre dossier personnel. Les skills que vous choisissez doivent
aussi être sans danger hors du clone.


`vet.py` lit les skills dans `skills/<name>/SKILL.md`, et s’arrête avec un message
quand le jeu n’en a aucune à cet endroit. Si le jeu les range ailleurs, lisez les
dossiers à la main. Notez le commit en haut du journal. Choisissez deux skills
dont la licence permet la copie, relancez `vet.py` avec leurs noms, et lisez
chaque fichier de leurs dossiers, scripts compris. Les deux skills ne doivent
avoir aucune ligne `allowed-tools`, et chacun de leurs scripts ne doit modifier
que des fichiers du projet, comme `plan-ticket` et `review-diff` dans
`workbench`. Si aucune paire de skills du jeu ne passe, choisissez un autre jeu,
ou arrêtez-vous là et écrivez la partie examen de la note ci-dessous. Créez
ensuite la copie de brouillon et démarrez-y une session avec la mémoire
automatique désactivée, pour qu’un essai ne puisse pas laisser de notes au
suivant (@Claude Code memory). Remplacez `<project>` par le chemin d’un dépôt sur
lequel vous travaillez, et `<skill-a>` et `<skill-b>` par les noms des deux
skills.

```sh
rm -rf ~/skill-trial
git clone -q <project> ~/skill-trial
cd ~/skill-trial
git remote remove origin
CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 claude
```

Lancez `/context` et notez la ligne Skills, puis quittez. Copiez les deux skills,
démarrez une nouvelle session de la même façon, et relancez `/context`. La ligne
`cp` attend les skills dans `skills/<name>/`, donc changez les chemins si le jeu
les range ailleurs.

```sh
cd ~/skill-trial
mkdir -p .claude/skills
cp -R ~/set-read/skills/<skill-a> ~/set-read/skills/<skill-b> .claude/skills/
CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 claude
```

Pour chaque skill, lancez une vraie demande à laquelle elle est destinée dans une
session neuve, puis de nouveau dans une session neuve avec cette skill réglée sur
`"off"`. Le menu `/skills` fait ce réglage : sélectionnez la skill, appuyez sur
Espace jusqu’à ce qu’elle affiche `off`, et appuyez sur Échap pour enregistrer
(@Claude Code skills).

Un bon résultat est une note courte. Elle nomme le jeu, le commit que vous avez
lu, la licence de chaque skill prise, ce que chacun de leurs scripts et de leurs
lignes `allowed-tools` peut changer, la ligne Skills avant et après, et pour
chaque demande si la skill a changé le résultat. Elle se termine par ce que vous
feriez de chacune des deux skills : la garder, la rendre invocable par
l’utilisateur seulement ou la supprimer. Auriez-vous trouvé les mêmes réponses en
installant tout le jeu pour l’essayer ?
</Exercise>

<Recap>
1. Les jeux de skills publiés sont des dépendances qui agissent dans vos sessions
   et changent à chaque version. Un même jeu peut aussi mélanger les licences
   d’une skill à l’autre (@anthropics skills).
2. Examinez un jeu avant de l’installer : la licence de chaque skill, qui le
   maintient et comment il évolue, chaque skill, chaque script et chaque ligne
   `allowed-tools`, et la possibilité d’écrire vous-même les quelques skills dont
   vous avez besoin.
3. Chaque skill que Claude peut lancer de lui-même met son nom et sa description
   dans chaque session, qu’elle s’exécute ou non (@Claude Code plugins).
4. Prenez une ou deux skills à la fois. Les skills d’un plugin viennent ensemble,
   donc copiez des skills isolées quand la licence le permet (@Claude Code skills).
5. Vérifiez chaque skill avec `/context` et avec les mêmes demandes lancées avec
   la skill active puis désactivée. Supprimez une skill qui n’a rien changé.
</Recap>

<Habit id="two-skills-at-a-time">
La prochaine fois que vous trouvez un jeu de skills qui vous plaît, prenez deux
de ses skills et notez le commit que vous avez lu. N’en ajoutez une troisième
qu’après que l’une des deux premières a changé un résultat.
</Habit>
