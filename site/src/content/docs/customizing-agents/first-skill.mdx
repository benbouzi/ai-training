La règle de la leçon précédente disait qu’une procédure que l’agent sait déjà
faire, mais fait différemment à chaque fois, va dans une skill. Cette leçon en
écrit une. La procédure est la publication d’une version d’un petit paquet, et
le résultat est un dossier avec un fichier que tout agent qui lit le format
ouvert des skills peut charger et suivre (@AEC-17). Vous construisez le fichier
en trois passages. Le premier lui donne un nom et la phrase qui pousse l’agent à
le choisir. Le deuxième écrit les étapes et le contrôle qui dit que le résultat
est juste. Le troisième ajoute quoi faire quand une étape échoue.

La leçon lance trois courts scripts Python sur l’exemple, et le cours vérifie
leur sortie à chaque construction du site. L’agent entre en jeu dans l’exercice,
où vous lancez la skill terminée depuis une session, comme dans la première
leçon sur le code.

sous `site/examples/customizing-agents/first-skill/fixture-package/`. Copiez ce

des fichiers par un agent. Il contient `notes.py`, ses tests dans
`test_notes.py`, un `CHANGELOG.md` avec trois versions, et `release_check.py`.
Le contrôle lit la version dans `notes.py`, cherche un titre correspondant dans
le journal des modifications, lance les tests, et affiche une ligne. Cette ligne
est la dernière étape de la skill, donc lancez-le une fois maintenant pour voir
à quoi ressemble « juste ».

## Premier passage : le dossier et la description

Une skill est un dossier qui contient un fichier nommé `SKILL.md`, et le nom du
dossier est le nom de la skill (@Agent Skills spec). Claude Code lit les skills
de projet dans `.claude/skills/<name>/SKILL.md` et les skills personnelles dans
`~/.claude/skills/<name>/SKILL.md`, et une skill de projet est committée pour que
les agents de l’équipe la partagent (@Claude Code skills). Créez le dossier dans
votre copie du paquet :

```sh
mkdir -p .claude/skills/release
```

Le fichier commence par un en-tête YAML entre deux lignes `---`. La
spécification des skills exige deux champs. `name` fait au plus 64 caractères,
en lettres minuscules, chiffres et traits d’union simples, sans trait d’union au
début ni à la fin, et il doit être égal au nom du dossier. `description` fait au
plus 1024 caractères et dit ce que fait la skill et quand l’utiliser
(@Agent Skills spec). Tous les autres champs sont facultatifs.

La description fait plus de travail que sa taille ne le laisse penser. Au début
d’une session, Claude Code charge le nom et la description de chaque skill qu’il
voit. Le corps est chargé quand une tâche correspond à la description, ou quand
vous tapez vous-même `/release`. Le texte chargé reste dans la conversation aux
tours suivants, jusqu’à ce que le compactage le réduise (@Claude Code skills).
La description est donc le déclencheur, et elle doit nommer les demandes qui
doivent la charger (@Academy introduction-to-agent-skills). Écrivez ceci comme
fichier complet pour l’instant. La description est en anglais, comme le reste
du paquet : elle dit de publier une version du paquet de notes, et de s’en
servir quand on demande une publication, une montée du numéro de version ou
l’étiquetage d’une nouvelle version.

```markdown
---
name: release
description: Cut a release of the notes package. Use when asked to release, to bump the version, or to tag a new version.
---
```

Le cours garde à côté de l’exemple un petit script de vérification qui contrôle
les champs obligatoires selon les règles ci-dessus. Il lit deux skills : la skill
de publication du paquet de l’exemple, et `bad-skill/`, dont l’en-tête contient
`name: Release-Notes` et une `description` vide.

## Deuxième passage : quand, les étapes, le contrôle

Le corps est en Markdown, et la spécification ne le limite pas, à part la
recommandation de garder tout le fichier sous 500 lignes et de déplacer le
matériel de référence détaillé dans des fichiers à côté (@Agent Skills spec). Le
corps doit permettre à un agent qui n’a rien de votre contexte de suivre la
procédure sans demander. Pour écrire une bonne skill, il faut une ligne
d’ouverture sur le moment où l’utiliser, les étapes dans l’ordre avec les
commandes et les noms de fichiers exacts, et le contrôle qui dit que le résultat
est juste.

Ajoutez ceci sous l’en-tête :

```markdown
# Release the notes package

Use this when the user asks for a release of this package. A release is a
version bump, a changelog entry, passing tests, and a tag. Ask for the new
version if the user did not give one. Bump the last number for a fix, the
middle one for a feature.

## Steps

1. Run `python3 -m unittest -q`. The last line must be `OK`.
2. In `notes.py`, change the `__version__` line to the new version.
3. In `CHANGELOG.md`, add a `## <version>` heading under the title, above
   the previous release, with one bullet per user-visible change since
   that release. Read `git log` for the list. Don't invent changes.
4. Run `python3 release_check.py`. It must print `release <version>: ok`.
5. Commit with the message `release: <version>` and tag it
   `v<version>` with `git tag v<version>`.

## Done when

`python3 release_check.py` prints `release <version>: ok`, the commit is
on the branch and `git tag --list 'v*'` shows the new tag. Don't push.
Report the version, the tag and the changelog entry you wrote.
```

Le corps, en anglais comme le paquet, dit ceci. La skill sert quand
l’utilisateur demande une publication du paquet. Une publication, c’est une
montée de version, une entrée dans le journal des modifications, des tests qui
passent et une étiquette. L’agent demande la nouvelle version si l’utilisateur
ne l’a pas donnée, et augmente le dernier nombre pour une correction, celui du
milieu pour une fonctionnalité. Les étapes : lancer les tests, dont la dernière
ligne doit être `OK`. Changer la ligne `__version__` de `notes.py`. Ajouter au
journal un titre `## <version>` avec une puce par changement visible, tirée de
`git log`, sans inventer de changement. Lancer le contrôle, qui doit afficher
`release <version>: ok`. Committer et étiqueter. La section « Done when »
(terminé quand) reprend le contrôle, interdit le push, et demande de rapporter
la version, l’étiquette et l’entrée écrite.

Les commandes et les noms de fichiers de ce corps sont exacts. L’étape dit
`python3 -m unittest -q`, parce qu’un agent sur une autre machine qui lit
« lance les tests » choisit le lanceur qu’il devine. La dernière étape est un
contrôle que l’agent peut lancer, avec la ligne exacte qu’il doit afficher, donc
« terminé » est une ligne que l’agent lit. La section « Done when » répète ce
contrôle et ajoute la limite « Don’t push » (ne pas pousser), parce qu’une skill
de publication qui pousse est une skill de publication qu’un `git reset` ne peut
plus annuler.

## Troisième passage : quand une étape échoue

Le corps actuel suppose que chaque étape fonctionne. La première fois qu’un
agent le suit, l’une d’elles échouera. Les tests échouent à cause d’une
modification que quelqu’un a laissée à moitié faite, ou le contrôle affiche une
ligne `FAIL` parce que l’agent a monté la version et oublié le journal des
modifications. Une skill qui ne dit rien de ces cas laisse l’agent décider, et
parmi les décisions que prennent les agents à ce moment-là, il y a « modifier le
contrôle jusqu’à ce qu’il passe ».

L’exemple montre ce qu’affiche le contrôle après une telle publication à moitié
faite. Le script copie le paquet, passe la version à 0.4.0 comme le dit
l’étape 2, lance le contrôle, ajoute ensuite le titre du journal de l’étape 3 et
le relance.

Le contrôle nomme l’étape manquante, donc le rôle de la skill est de dire à
l’agent de lire la ligne et de corriger ce qu’elle nomme. Changez les étapes 1
et 4 ainsi :

```markdown
1. Run `python3 -m unittest -q`. The last line must be `OK`. If it is
   not, stop and report the failure. Never release with a failing test.
...
4. Run `python3 release_check.py`. It must print `release <version>: ok`.
   If it prints a `FAIL` line, fix what the line names and run it again.
   Don't edit `release_check.py`.
```

L’étape 1 dit maintenant de s’arrêter et de rapporter l’échec si la dernière
ligne n’est pas `OK`, et de ne jamais publier avec un test en échec. L’étape 4
dit de corriger ce que nomme une ligne `FAIL` et de relancer le contrôle, sans
modifier `release_check.py`. Chaque ligne d’échec a les mêmes trois parties : ce
que voit l’agent, ce qu’il fait, et la seule chose qu’il ne doit pas faire. La
troisième partie est celle que les auteurs oublient, et c’est elle qui empêche
l’agent de faire passer le contrôle en modifiant le contrôle. Votre `SKILL.md`
correspond maintenant, ligne pour ligne, à celui de l’exemple.

<Pitfall title="La description qui correspond à tout">
Une équipe écrit une skill pour mettre à jour le journal des modifications et la
décrit par « À utiliser quand on travaille sur le paquet de notes ». Pendant une
semaine, chaque session dans le paquet la charge, quelle que soit la tâche, et
l’agent se met à ajouter une puce au journal pour une faute de frappe corrigée
dans le README, parce que le corps chargé le demande. Le corps était bon. La
description correspondait à toutes les demandes, alors qu’elle était faite pour
une seule. Écrivez la description comme la liste des demandes qui doivent
charger la skill, et relisez-la une fois comme le ferait un inconnu, pour
vérifier qu’une demande portant sur autre chose n’y correspondrait pas.
</Pitfall>

un dépôt git, lancez `git init` et committez d’abord le paquet, pour que les
étapes 3 et 5 aient de quoi travailler.

Un bon résultat : l’agent a lancé les tests en premier,
`python3 release_check.py` affiche `release 0.4.0: ok`, `git tag --list 'v*'`
montre `v0.4.0`, et l’agent n’a pas poussé et n’a pas modifié `release_check.py`.
Où l’agent a-t-il hésité ou vous a-t-il demandé quelque chose ? Chaque question
de ce genre est une ligne qui manque à la skill, et la leçon sur le test d’une
skill apprend à trouver ces lignes.
</Exercise>

<Recap>
1. Une skill est un dossier nommé d’après la skill, qui contient un `SKILL.md`.
   Son en-tête demande `name` et `description`, et `name` doit être égal au nom
   du dossier (@Agent Skills spec).
2. La description est le déclencheur. Elle est dans le contexte à chaque tour,
   et le corps est chargé quand une tâche lui correspond ou que vous invoquez la
   skill, puis reste aux tours suivants jusqu’au compactage (@Claude Code skills).
   Nommez les demandes qui doivent la charger, et aucune autre.
3. Le corps dit quand utiliser la skill, donne les étapes dans l’ordre avec les
   commandes et les noms de fichiers exacts, et se termine par un contrôle que
   l’agent peut lancer, avec la ligne qui veut dire que le résultat est juste.
4. Chaque étape qui peut échouer dit ce que voit l’agent, ce qu’il fait, et ce
   qu’il ne doit pas faire. L’agent sait alors quoi faire à la première surprise.
5. Une skill est terminée quand l’agent de quelqu’un d’autre la suit depuis une
   session neuve sans demander. La leçon sur le test d’une skill la lance de
   cette façon.
</Recap>
