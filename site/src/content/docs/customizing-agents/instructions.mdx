Dans votre première session, vous avez donné du contexte à l’agent à la main,
des fichiers qui comptaient jusqu’à la commande de test et la branche à ne pas
toucher. Dans cette leçon, nous écrivons ce contexte une fois pour toutes, dans
un fichier que l’agent lit au début de chaque session. Nous regardons aussi ce
qui a sa place dans ce fichier et ce qui ne l’a pas, et ce qu’il faut faire
quand une règle écrite ne suffit pas.

Vous ne lancez rien dans cette leçon. Les exemples sont des contenus de
fichiers, et l’exemple est un petit projet fictif appelé `invoice-mailer` : un
service Python qui produit des factures en PDF et les envoie par SMTP. Vous
pouvez refaire chaque étape dans un dossier vide avec un éditeur de texte.

## Un fichier, lu avant tout le reste

La plupart des agents de code cherchent un fichier Markdown à la racine du dépôt
et le chargent dans leur contexte avant le premier message de l’utilisateur. La
convention dépend de l’outil : certains cherchent `AGENTS.md`, d’autres
`CLAUDE.md`, d’autres les deux. Claude Code, par exemple, lit `CLAUDE.md`. Il ne
lit `AGENTS.md` que s’il n’y a ni `CLAUDE.md`, ni `.claude/CLAUDE.md`, ni
`CLAUDE.local.md` dans le dossier où vous le lancez ou dans un dossier
au-dessus (@Claude Code memory). Le contenu est le même dans les deux cas, donc
l’habitude courante consiste à écrire `AGENTS.md` et à faire de `CLAUDE.md` un
lien symbolique vers lui, ou à donner à `CLAUDE.md` la seule ligne
`@AGENTS.md`, qui importe le fichier. Un `CLAUDE.md` qui demande seulement avec
des mots de lire `AGENTS.md` ne le fait lire que lorsque Claude décide de
l’ouvrir (@Claude Code memory).

Le fichier est la présentation que vous feriez à un prestataire compétent, le
matin de son premier jour. Il sait lire du code. Il ne peut pas savoir quelle
commande votre équipe lance avant de pousser, quel dossier est généré, ou quelle
correction en apparence évidente a déjà été essayée puis annulée deux fois.
C’est ce manque que le fichier comble.

Voici la plus petite version utile pour notre exemple, en anglais comme le reste
du projet. Elle dit ce que fait le service, avec quelle version de Python et
quel gestionnaire de paquets, puis donne la commande de test et la commande de
vérification et de mise en forme :

```markdown
# invoice-mailer

Renders invoices to PDF and sends them over SMTP. Python 3.13, uv.

## Commands

- Test: `uv run pytest`
- Lint and format: `uv run ruff check . && uv run ruff format .`
```

Un agent qui lit ces quelques lignes lance la bonne commande de test du premier
coup, sans hésiter entre `pytest`, `python -m pytest` et `make test`. Cela
suffit déjà à justifier le fichier.

## Ce qui a sa place dedans

Tout ce que contient le fichier devrait être quelque chose que l’agent ne peut
pas déduire du code, ou qu’il pourrait déduire mais se trompe assez souvent pour
que vous soyez lassé de le corriger. En pratique, cela fait quatre sortes de
contenu.

**Les commandes.** Comment installer, tester, vérifier le style, construire et
lancer. Une ligne chacune, avec l’appel exact. Si le projet a un lanceur de
tâches, nommez-le et dites qu’il fait foi.

**La structure.** Où se trouvent les choses, dossier par dossier, sans descendre au
niveau des fichiers. Quels dossiers sont générés et ne doivent pas être modifiés à la main.
Où va chaque sorte de nouveau code.

**Les conventions.** Les règles que suit le code et qu’un lecteur ne déduirait
pas d’un seul fichier : le format des messages de commit, le nommage des
branches, le nommage des tests, et les choix de style qui sont délibérés.

**Les règles qui suppriment une erreur récurrente.** C’est la catégorie la plus
précieuse, et la plus difficile à écrire à l’avance. Chaque fois que l’agent
fait deux fois la même erreur, ajoutez une ligne qui l’arrête. « N’ajoute pas de
nouvelles tentatives autour des appels SMTP. La file d’attente réessaie déjà »
est une bonne règle. Elle est précise, elle dit quoi faire à la place, et elle
existe à cause d’un vrai incident.

Construisez-en un maintenant. Cochez ce qui est vrai pour un projet que vous
connaissez, remplissez les champs courts, et lisez le résultat comme si vous
étiez l’agent qui le découvre.

Remarquez combien le résultat est court, même avec toutes les cases cochées.
C’est la cible. Le fichier d’un vrai projet grandit avec le temps, mais il
grandit d’une ligne à chaque leçon tirée.

Claude Code peut écrire un premier brouillon du fichier avec sa commande
`/init`, à partir de ce qu’il trouve dans le dépôt. Traitez ce brouillon comme
une liste de candidats, et supprimez chaque ligne que l’agent aurait pu trouver
lui-même. Le conseil de l’éditeur est proche de l’exercice de fin de leçon :
ajoutez au fichier quand l’agent répète une erreur, ou quand vous vous surprenez
à lui donner une correction déjà donnée dans une session précédente
(@Claude Code memory).

## Ce qui n’a pas sa place dedans

Le défaut habituel des fichiers d’instructions est leur longueur. Chaque ligne coûte du contexte à chaque tour de chaque session,
et un agent à qui l’on donne deux pages de prose en suit une partie et laisse
tomber le reste sans le dire.

Laissez de côté :

**Tout ce que l’agent peut lire dans le code.** La liste des dépendances est
dans le fichier de verrouillage. Les signatures des fonctions sont dans les
sources. Les routes de l’API sont dans le routeur. Renvoyer au fichier (« les
routes sont enregistrées dans `app/routes.py` ») convient. Copier son contenu ne
convient pas, parce que la copie devient périmée et que l’agent a alors deux
sources contradictoires.

**La prose longue.** Les essais d’architecture, l’histoire du projet, le
raisonnement derrière chaque décision. Si le raisonnement compte, mettez-le dans
un document de conception et faites un lien vers lui. L’agent le lit quand la
tâche le demande.

**L’évidence répétée.** « Écris du code propre. » « Suis les bonnes pratiques. »
« Vérifie que les tests passent. » Un agent compétent fait déjà tout cela, et ces
lignes n’apprennent rien sur votre projet. Elles diluent aussi les lignes qui
apprennent quelque chose.

<Pitfall title="Le fichier qui dit tout et ne change rien">
Une équipe écrit un `AGENTS.md` de deux pages dès le premier jour : vue
d’ensemble de l’architecture, philosophie du code, un paragraphe sur chaque
module. Trois semaines plus tard, l’agent committe toujours sur `main` et lance
toujours la mauvaise commande de test, parce que ces deux faits se trouvent au
septième et au onzième paragraphe. La règle : une ligne courte par fait, les
commandes et les règles strictes d’abord, et n’ajoutez au fichier que quand
quelque chose a mal tourné.
</Pitfall>

## Les instructions dans un monorepo

Un dépôt qui contient plus d’un projet a besoin de plus d’un fichier. La plupart
des outils lisent le fichier à la racine du dépôt, et aussi le fichier d’un
sous-dossier quand l’agent travaille sur des fichiers de ce sous-dossier. Claude
Code, par exemple, lit au démarrage de la session les fichiers d’instructions du
dossier où vous le lancez et de chaque dossier au-dessus. Il lit le fichier d’un
sous-dossier la première fois qu’il lit un fichier de ce sous-dossier. Aux deux
endroits, un `CLAUDE.md` l’emporte sur un `AGENTS.md`. Claude Code ne lit un
`AGENTS.md` que selon la règle ci-dessus, et celui d’un sous-dossier seulement si
ce sous-dossier n’a pas non plus son propre `CLAUDE.md`, `.claude/CLAUDE.md` ou
`CLAUDE.local.md` (@Claude Code memory).

Les outils diffèrent quand deux fichiers se contredisent. Le format AGENTS.md
dit que le fichier le plus proche du fichier modifié l’emporte
(@AGENTS.md format). Claude Code garde tous les fichiers dans son contexte, le
plus proche après celui de la racine, et quand deux règles se contredisent il
peut suivre l’une ou l’autre (@Claude Code memory). Traitez donc une
contradiction entre deux fichiers comme une erreur à corriger, sans compter sur
le fichier le plus proche pour s’appliquer.

La façon dont les outils lisent les fichiers donne un découpage naturel. Le
fichier racine contient ce qui est vrai partout : le lanceur de tâches, la
convention de commit, la règle des branches. Le fichier de chaque projet ne
contient que ce qui diffère : sa propre commande de test, son propre langage,
ses propres erreurs récurrentes.

```text
repo/
  AGENTS.md              # task runner, commit format, branch rule
  services/
    invoice-mailer/
      AGENTS.md          # uv run pytest; no SMTP retries
    web/
      AGENTS.md          # bun test; never edit generated/ by hand
```

Les commentaires de l’arbre reprennent le découpage : à la racine, le lanceur de
tâches, le format des commits et la règle des branches. Pour `invoice-mailer`,
`uv run pytest` et pas de nouvelles tentatives SMTP. Pour `web`, `bun test` et
ne jamais modifier `generated/` à la main.

Résistez à l’envie de copier les règles de la racine dans chaque fichier enfant
pour qu’il se lise seul. L’agent voit les deux, et la copie ne fait qu’ajouter
un second endroit à tenir à jour.

Vos préférences personnelles n’ont leur place dans aucun des deux fichiers.
Claude Code lit aussi un `~/.claude/CLAUDE.md` au niveau de l’utilisateur, dans
chaque projet et pour vous seul (@Claude Code memory). La façon dont vous aimez
qu’on vous explique une modification, ou le shell que vous utilisez, va là. Le
fichier partagé ne contient alors que ce dont toute l’équipe a besoin
(@Academy claude-code-101).

## Quand les instructions ne suffisent pas

Une instruction est une demande. L’agent la lit, la suit en général, et parfois
non, surtout tard dans une longue session, quand le fichier est loin en arrière
dans son contexte. Si vous ne pouvez pas vous permettre qu’une règle soit sautée
une seule fois, ne comptez pas sur de la prose pour elle. Un *hook* lance une
commande à vous à un moment fixe de la boucle de l’agent, par exemple avant un
appel d’outil (tool call) ou après une modification. Quand il s’exécute avant un appel
d’outil, il peut bloquer l’action net. Par exemple, avec un hook qui s’exécute
avant chaque commande shell, examine la commande que l’agent s’apprête à lancer
et se termine avec le code 2 quand elle correspond à un `git push` vers `main`,
le push n’a jamais lieu, aussi loin que soit le fichier d’instructions dans le
contexte. Dans Claude Code, le code de sortie 2 est celui qui bloque. Un hook qui
se termine avec 1 signale une erreur, et la commande s’exécute quand même
(@Claude Code hooks). « Ne jamais pousser sur `main` » dans `AGENTS.md` est un
conseil. Le hook l’impose. Un hook qui lance l’outil de mise en forme après
chaque modification fonctionne de la même façon pour une procédure que l’agent
oublie souvent. Le message qu’affiche un hook qui bloque revient à l’agent, qui
apprend ainsi pourquoi l’action a été refusée et peut changer de cap sans
réessayer la même action (@Claude Code hooks). Les hooks du fichier de réglages partagé du
projet, `.claude/settings.json` dans Claude Code, sont committés avec le code
(@Claude Code hooks). Toute personne qui clone le dépôt reçoit les mêmes
contrôles sans rien configurer (@Academy claude-code-101). Et quand une règle
est une procédure, une chose en plusieurs étapes que
l’agent devrait faire de la même façon à chaque fois, il vaut mieux la regrouper
dans une *skill* : un ensemble d’instructions nommé et autonome que l’agent ne
charge que quand la tâche le demande, pour qu’il n’occupe pas le contexte de
chaque session. Une leçon suivante de ce cours apprend à en écrire une.

<Exercise stretch="Ajoutez maintenant une règle de plus que le système impose : un hook d’agent qui bloque l’action, ou un contrôle de CI qui échoue quand la règle est enfreinte, et retirez la ligne équivalente d’AGENTS.md.">
Dans un dossier vide, créez un projet jetable : n’importe quel langage, une
commande de test qui fonctionne, un fichier source. Lancez-y un agent de code et
donnez-lui trois petites tâches sans aucun fichier d’instructions. Notez chaque
fois qu’il devine mal (commande de test, emplacement d’un fichier, style,
branche). Écrivez ensuite un `AGENTS.md` de quinze lignes au plus qui aurait
évité chaque mauvaise supposition. Supprimez l’historique git du projet et
refaites les trois mêmes tâches.

Un bon résultat : la seconde exécution ne fait aucune des mauvaises suppositions
de la première, et chaque ligne de votre fichier remonte à l’une d’elles. Une
ligne qui ne remonte à aucune est candidate à la suppression.
</Exercise>

<Recap>
1. L’agent lit `AGENTS.md` (ou `CLAUDE.md`, même contenu, convention d’un autre
   outil) au début de chaque session. C’est la présentation que vous feriez à un
   prestataire compétent le matin de son premier jour.
2. Mettez-y ce que l’agent ne peut pas lire dans le code : les commandes, la
   structure, les conventions, et une ligne pour chaque erreur qu’il refait.
3. Laissez de côté ce que le code dit déjà, la prose longue, et les règles qui
   s’appliquent à tous les projets du monde. Les fichiers courts sont suivis, les
   longs sont survolés.
4. Dans un monorepo, le fichier racine contient ce qui est partagé et le fichier
   de chaque projet ne contient que ce qui diffère. Empêchez-les de se
   contredire, parce que les outils diffèrent sur celui qui s’applique.
5. Une règle qui ne doit jamais être sautée va dans un hook, et une procédure
   que l’agent doit répéter va dans une skill.
</Recap>
