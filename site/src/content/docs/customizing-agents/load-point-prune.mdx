La leçon précédente a écrit un court `AGENTS.md` pour `invoice-mailer`, le
service Python fictif qui produit des factures en PDF et les envoie par SMTP. Un
an plus tard, le même fichier compte 57 lignes. Chaque ligne a été ajoutée pour
une raison, et l’agent suit maintenant le fichier moins bien qu’il ne suivait la
version courte. Dans cette leçon, nous le raccourcissons à nouveau. Nous
renvoyons à ce dont seules certaines tâches ont besoin, et nous coupons ce dont
aucune tâche n’a besoin.

Les fichiers de cette leçon se trouvent dans
`site/examples/customizing-agents/load-point-prune/` du dépôt du cours.
`AGENTS.long.md` est le long fichier, `AGENTS.pruned.md` en est une version
élaguée, et `docs/` contient les fichiers vers lesquels la version élaguée
renvoie. Ces fichiers sont en anglais, comme le reste du projet. Dans les
commandes ci-dessous, remplacez `<course-repo>` par le chemin de votre copie du
dépôt du cours. Les règles de chargement décrites ici sont celles de Claude
Code, vérifiées dans sa documentation à la date indiquée en fin de leçon.
D’autres agents chargent leurs fichiers autrement, et la méthode reste valable.

## Chaque ligne chargée est dans chaque session

Claude Code lit ses fichiers d’instructions au début de chaque session
(@Claude Code memory). Chacune de leurs lignes est dans le contexte de chaque
tâche, la correction d’une faute de frappe d’une ligne comme la publication
d’une version. La [leçon sur ce que coûtent les jetons](/concepts/what-tokens-cost/#la-règle-enfouie)
a montré ce que cela fait à une règle : elle est en concurrence avec tout
l’autre texte de la fenêtre, et une règle parmi beaucoup d’autres pèse moins
qu’une règle parmi peu. L’éditeur donne le même conseil pour les fichiers
d’instructions. Sa documentation dit que chaque ligne de plus consomme du
contexte et fait que l’agent respecte moins bien les règles (@Claude Code memory).

Pour chaque élément de guidage, le choix est de **charger ou renvoyer**.
Charger met le texte dans le fichier d’instructions, donc il est dans le
contexte que la tâche en ait besoin ou non. Renvoyer met dans le fichier une
ligne qui dit où se trouve le texte et quand le lire, et l’agent n’ouvre le
fichier que quand une tâche le demande. L’équipe d’ingénierie d’Anthropic décrit
le même partage pour les agents en général. Un agent peut garder une courte
référence, comme un chemin de fichier, et charger ce vers quoi elle pointe avec
un outil au moment où il en a besoin. Claude Code fonctionne ainsi : ses
fichiers d’instructions entrent dans le contexte au départ, et il trouve les
autres fichiers du projet avec des outils de recherche au fil du travail
(@Anthropic context engineering).

Chargez ce dont presque chaque tâche a besoin : la commande de test, la règle
des branches, l’erreur que l’agent refait. Renvoyez au reste. Les exemples de
l’éditeur de guidage à sortir du fichier sont une procédure en plusieurs étapes
et une règle qui ne compte que pour une partie du code. Claude Code a aussi deux
endroits pour ceux-là, qui se chargent moins souvent que le fichier
d’instructions. Une skill se charge quand vous l’appelez ou quand l’agent décide
qu’elle convient à la tâche, et un fichier de règle avec un champ `paths` ne se
charge que quand l’agent travaille sur des fichiers qui lui correspondent
(@Claude Code memory).

## Une importation charge quand même

Claude Code permet à un fichier d’instructions d’importer un autre fichier avec
une ligne comme `@docs/release.md`. L’importation n’est pas un renvoi. Au
démarrage de la session, Claude Code lit le fichier importé et met tout son
texte dans le contexte avec le fichier qui contient l’importation. L’éditeur le
dit clairement : une importation garde un long fichier bien rangé, sans le
rendre moins coûteux (@Claude Code memory). Un chemin sans le `@`, comme
`docs/release.md` dans une phrase, est du texte simple et n’importe rien, et
Claude Code ignore aussi un `@chemin` écrit dans un bout de code ou dans un bloc
de code (@Claude Code memory). L’agent ne lit un fichier nommé en texte simple
que s’il décide de l’ouvrir.

`startup.py`, dans le dossier de la leçon, compte les lignes que chaque version
du fichier met dans le contexte au début d’une session. Il suit la règle
d’importation ci-dessus, simplifiée. `AGENTS.pruned.md` renvoie à deux fichiers
avec des lignes comme « To cut a release, read `docs/release.md` and follow it
step by step » (pour publier une version, lire `docs/release.md` et le suivre
étape par étape). `AGENTS.imports.md` est le même fichier, avec chacune de ces
deux lignes remplacée par une importation.

```sh
cd <course-repo>/site/examples/customizing-agents/load-point-prune
python3 startup.py
```

## Un renvoi dit quand

Un renvoi ne fonctionne que si l’agent ouvre le fichier qu’il nomme, et l’agent
en décide à partir de la ligne de renvoi et de la tâche qu’il a devant lui.
L’éditeur donne un exemple de ce cas. Quand il y a un `CLAUDE.md`, un
`.claude/CLAUDE.md` ou un `CLAUDE.local.md` dans le dossier où vous lancez
Claude Code ou dans un dossier au-dessus, Claude Code ne charge pas `AGENTS.md`
de lui-même. Un `CLAUDE.md` qui demande dans une phrase de lire `AGENTS.md` ne le
fait alors lire que quand Claude décide de l’ouvrir (@Claude Code memory).
Écrivez donc le renvoi sous la forme d’une condition et d’un endroit : « Avant de
modifier un fichier de `templates/`, lis `docs/templates.md`. » La condition est
ce que l’agent compare à la tâche. Un simple « voir `docs/` » ne lui donne aucune
tâche à comparer, et « lis toujours `docs/release.md` d’abord » lui fait lire le
fichier dans chaque session, ce qui coûte autant que de le charger.

## Couper ce qui ne sert à rien

Renvoyer raccourcit le fichier. **Élaguer les instructions** le raccourcit
encore, en supprimant les lignes dont aucune tâche n’a besoin. Le test de
l’éditeur demande pour chaque ligne si l’agent se tromperait sur quelque chose
sans elle, et une ligne qui ne manquerait pas à l’agent disparaît
(@Claude Code best practices). Les lignes qui échouent à ce test entrent en
général dans l’une de ces catégories.

**Une règle que l’agent suit de toute façon.** « Écris du code propre, lisible
et bien documenté » décrit ce que fait l’agent sans cette ligne, tout comme une
ligne sur une convention que l’agent applique déjà, par exemple les annotations
de type dans un code qui en a partout.

**Un fait que le code dit déjà.** La configuration de l’outil de mise en forme
fixe le style des guillemets et la longueur des lignes, donc « utilise des
guillemets doubles » et « garde les lignes sous 100 caractères » la répètent.
La liste des dépendances et la version de Python sont dans `pyproject.toml`. Le
paragraphe sur les modules ne dit que ce que disent déjà les noms des dossiers.
Il ne nomme aucun dossier généré et ne dit pas où va le nouveau code, alors que
ce sont les parties d’une section sur la structure que le code ne montre pas.
Une copie d’un fait peut aussi devenir périmée pendant que le code change, et
l’agent a alors deux sources qui se contredisent.

**Une règle pour un problème qui a disparu.** « Garde la bibliothèque PDF sous
la version 52 » était juste quand le plantage a eu lieu. Le projet utilise la
version 62 depuis un an, et la ligne demande maintenant à l’agent de revenir à
une version antérieure.

**Une ligne qui en contredit une autre.** Le long fichier dit `uv run pytest`
sous Commands et `python -m pytest` sous Rules. Devant deux lignes qui se
contredisent, Claude peut choisir l’une ou l’autre (@Claude Code memory).
Résolvez une contradiction en gardant une seule version, et gardez aussi ce que
voulait dire la ligne coupée. La seconde ligne disait aussi *quand* lancer les
tests. Le fichier élagué le dit, à côté de la bonne commande.

Claude Code peut chercher certaines de ces lignes pour vous. `/doctor
prompt-audit` signale les instructions qui se contredisent ou qui nomment des
fichiers et des commandes qui n’existent pas, et il ne change rien tant que vous
ne le lui demandez pas (@Claude Code memory). L’audit trouve des candidats, et
c’est toujours vous qui tranchez pour chaque ligne.

## Observer les sessions après la coupe

Un passage d’élagage est une modification d’un prompt, et vous le testez comme
toute modification d’un prompt : lancez les tâches habituelles et regardez ce
que fait l’agent. L’éditeur vous demande d’entretenir le fichier comme vous
entretenez le code. Coupez-y des lignes à intervalles réguliers, et vérifiez
dans les sessions suivantes si l’agent agit différemment
(@Claude Code best practices). Quand une session tourne mal après la coupe, la
ligne coupée qui l’aurait empêché revient, et seulement cette ligne.

<Pitfall title="Renvoyer la règle dont chaque tâche a besoin">
Une équipe élague son fichier et déplace les règles de branches dans
`docs/git.md`, derrière la ligne « pour le nommage des branches, lis
`docs/git.md` ». Une semaine plus tard, l’agent committe une correction
directement sur `main`. La tâche était une petite correction, rien en elle ne
parlait du nommage des branches, et l’agent n’a pas ouvert le fichier. Gardez
dans le fichier d’instructions lui-même une règle qui s’applique à presque chaque
tâche. Le renvoi sert au détail dont seules certaines tâches ont besoin.
</Pitfall>

   tâche, et un long fichier est moins bien suivi qu’un court
   (@Claude Code memory).
2. Chargez ce dont presque chaque tâche a besoin, et renvoyez au reste avec une
   ligne qui dit quand lire le fichier et où il se trouve.
3. Une importation `@chemin` déploie le fichier dans le contexte au démarrage,
   donc elle range le fichier sans le rendre moins coûteux (@Claude Code memory).
4. Élaguez en vous demandant pour chaque ligne si l’agent se tromperait sur
   quelque chose sans elle. Coupez les règles que l’agent suit de toute façon,
   les faits que le code dit déjà, les problèmes qui ont disparu, et une ligne de
   chaque paire de lignes qui se contredisent (@Claude Code best practices).
5. Après une coupe, lancez les tâches habituelles et ne remettez que la ligne
   dont l’absence a causé une erreur.
</Recap>

<Habit id="delete-one-when-you-add-one">
Chaque fois que vous ajoutez une ligne à un fichier d’instructions, cherchez
dans le reste du fichier une ligne qui n’empêche plus aucune erreur. Si vous en
trouvez une, supprimez-la.
</Habit>
