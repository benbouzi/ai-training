Une collègue partage avec vous un plugin appelé `release-kit`. Il annonce une
skill, `release`, qui publie une version de la même façon dans chaque dépôt, et
c’est cette skill que vous voulez. À côté de la skill, le dossier du plugin
contient un sous-agent (subagent) qui écrit les notes de version, un hook qui s’exécute
avant chaque commande shell que lance l’agent, et une connexion à l’outil de
suivi des tickets de l’équipe. Dans cette leçon, nous lisons ce plugin élément
par élément et nous disons ce que fait chaque élément dans vos sessions. La leçon
se termine par une décision : l’installer, en copier la seule skill, ou y
renoncer.

Le plugin est inventé pour le cours. Il se trouve dans le dépôt du cours, dans
`site/examples/customizing-agents/plugins/release-kit/`, à côté d’un court
script Python, `inventory.py`, qui liste ce que contient le dossier d’un plugin.
Le script ne fait que lire des fichiers, et rien dans cette leçon n’installe le
plugin ni ne lance son hook. Lancez les commandes depuis ce dossier, et remplacez
`<course-repo>` par le chemin de votre copie du dépôt du cours.

```sh
cd <course-repo>/site/examples/customizing-agents/plugins
```

## Ce que regroupe un plugin

Les skills, les sous-agents, les hooks et les serveurs MCP (Model Context
Protocol) fonctionnent chacun seuls dans Claude Code, et une skill de
`~/.claude/skills/` atteint déjà tous vos projets. Un **plugin** est la façon
dont Claude Code distribue un ensemble de ces éléments réunis
(@Claude Code plugins). Vous recevez tout l’ensemble avec une seule commande
d’installation, et les mises à jour ultérieures viennent de la même source. Sur
le disque, un plugin est un dossier. Un fichier manifeste qu’il contient,
`.claude-plugin/plugin.json`, donne le nom du plugin et peut donner une version
et une description. Les plugins peuvent aussi contenir d’autres sortes
d’éléments que les quatre que lit cette leçon.

Pour installer un plugin, Claude Code doit savoir où le récupérer, et c’est une
**place de marché** (marketplace) qui le lui dit. C’est un dépôt git ou un dossier
local avec un fichier `.claude-plugin/marketplace.json`, qui liste des plugins et
leurs sources. Après avoir enregistré une place de marché, vous désignez un de ses
plugins sous la forme `plugin@marketplace` pour l’installer. La seule place de
marché que Claude Code enregistre de lui-même est la place officielle
d’Anthropic, lors de votre première session interactive (@Claude Code plugins).
Un catalogue que gèrent vos collègues ou votre employeur est une place tierce.
Savoir qui gère un catalogue ne vous dit pas ce que fait l’un de ses plugins,
donc vous examinez vous-même chaque plugin (@Claude Code plugin security).

La portée que vous choisissez à l’installation fixe où le plugin est actif. Avec
la portée utilisateur, il est actif dans tous vos projets sur cet ordinateur. La
portée locale le réserve à vous, dans un seul dépôt. La portée projet l’écrit dans
le `.claude/settings.json` committé du dépôt, ce qui l’active pour toute l’équipe
dans ce dépôt (@Claude Code plugins).

Que les fichiers installés restent ceux que vous avez lus dépend de l’auteur et de
la place de marché. Un auteur qui règle `version` dans le manifeste garde chaque
installation à cette version jusqu’à ce qu’il en règle une nouvelle
(@Claude Code plugin manifest). Une place de marché dont la mise à jour
automatique est activée remplace les fichiers installés en arrière-plan
(@Claude Code plugin security). La plupart des places de marché officielles
d’Anthropic ont la mise à jour automatique activée par défaut, et les places
tierces l’ont désactivée (@Claude Code plugin install).

Ce que vous coûte un plugin ne dépend pas de votre usage. Tant qu’il est activé,
Claude Code le charge dans chaque session (@Claude Code plugins). Chaque tour
contient les noms et les descriptions des skills, des commandes et des
sous-agents que Claude peut choisir de lui-même, c’est-à-dire l’étape que la
leçon précédente a mesurée pour une skill. Le texte complet d’une skill ou d’un
sous-agent attend que Claude s’en serve. Les serveurs du plugin tournent dans
chaque session et ses hooks réagissent à leurs événements. Les deux s’exécutent
avec les droits de votre compte utilisateur.

## Lire un plugin, élément par élément

Avant une installation, le menu `/plugin` de Claude Code montre ce qu’un plugin
va ajouter. Cette liste vous dit qu’un hook est présent, mais pas la commande
qu’il lance, et c’est pourquoi les étapes d’examen d’Anthropic vous renvoient aux
fichiers du plugin lui-même (@Claude Code plugin security). Pour le dossier d’un
plugin que vous avez cloné, la même page donne la commande
`claude --plugin-dir <directory> plugin details <name>`, qui liste ses éléments
sans démarrer de session. `inventory.py` fait un travail semblable pour les
éléments que lit cette leçon, et affiche aussi la commande de chaque hook et
l’adresse de chaque serveur. Sa dernière ligne estime les jetons (tokens) que les noms et
les descriptions ajoutent à chaque tour, avec la même règle que `measure.py` dans
la leçon précédente.

Lisez maintenant chaque élément dans le dossier du plugin, et notez ce qu’il fait
dans une session.

**La skill,** `skills/release/SKILL.md`, contient les cinq étapes de publication
et un contrôle qui dit quand la publication est terminée. Ses étapes lisent et
modifient le `CHANGELOG.md` du dépôt. Dans un plugin, le nom de commande d’une
skill commence par le nom du plugin, donc celle-ci est `/release-kit:release`
(@Claude Code plugin parts). La dernière ligne de l’inventaire estime la skill et
le sous-agent à environ 50 jetons par tour à eux deux, ce qui est peu.

**Le sous-agent,** `agents/release-notes.md`, est un agent auxiliaire. Claude lui
confie une tâche, et il y travaille avec ses propres instructions et son propre
contexte. Celui-ci écrit les notes de version à partir de `git log`. Son en-tête
liste `Read`, `Grep` et `Bash`, donc il peut lancer des commandes shell. Un
fichier de sous-agent sans ligne `tools` peut utiliser tous les outils permis aux
sous-agents (@Claude Code subagents). Lisez cette ligne dans chaque sous-agent
qu’apporte un plugin.

**Le hook** se trouve dans `hooks/hooks.json`. Personne n’a besoin de lancer la
skill de publication pour qu’il agisse, parce qu’il est actif dès qu’une session
charge le plugin (@Claude Code plugin parts). Son événement est `PreToolUse`, le
moment qui précède l’exécution d’un appel d’outil (tool call) par Claude Code. Son `matcher`,
un motif sur le nom de l’outil, est `Bash`, donc il ne s’exécute qu’avant les
commandes shell. Sans `matcher`, un hook s’exécute à chaque occurrence de son
événement, et un hook `PreToolUse` peut arrêter l’appel (@Claude Code hooks).
L’inventaire montre la commande. Pour savoir ce que fait le script, ouvrez
`scripts/changelog_guard.py`. Il bloque chaque `git commit` qui n’indexe pas
`CHANGELOG.md`, dans chaque dépôt où le plugin est activé.

**Le serveur** se trouve dans `.mcp.json`. C’est un serveur MCP à l’adresse
`tracker.example.com`, qui reçoit la valeur de la variable d’environnement
`TRACKER_TOKEN` comme jeton porteur (bearer token). Tant que le plugin est
activé, Claude a les outils de ce serveur, et Claude Code dialogue avec le
serveur pour lui. Si une entrée a une `command` et pas d’`url`, Claude Code lance
cette commande comme un processus sur votre propre machine
(@Claude Code plugin security). Le serveur peut faire sur l’outil de suivi ce que
permet ce jeton, donc les accès du jeton sont les accès que vous accordez.

**Ce plugin n’a pas de dossier `bin/`.** Dans un plugin qui en a un, le shell de
l’agent peut lancer chacun de ses fichiers par son nom, parce que Claude Code
ajoute le dossier au `PATH` de ce shell. Les étapes d’examen d’Anthropic disent
de lire tous ces fichiers (@Claude Code plugin security).

Vos règles de permission sont les règles d’autorisation et d’interdiction de vos
réglages qui décident quels appels d’outil Claude peut faire. Elles vérifient un
appel à l’un des outils MCP du plugin, et elles vérifient une commande shell qui
lance un fichier de `bin/`. Le bac à sable de Claude Code pour les commandes shell
ne couvre que le second cas, parce que le serveur derrière un outil MCP tourne
hors de lui. Les hooks et les processus des serveurs sont hors des deux. Ils
s’exécutent avec tous vos droits d’utilisateur, et aucune règle de permission ne
les voit (@Claude Code plugin security).

## L’installer, en copier une skill, ou y renoncer

Un plugin est une dépendance, et il mérite le même genre d’examen qu’un paquet
du fichier de verrouillage
([Relire ce que l’agent a ajouté comme dépendances](/coding-with-agents/dependency-review/)).
Proportionnez l’effort d’examen au risque, et comptez ce que le plugin vous
coûtera plus tard autant que ce qu’il vous apporte aujourd’hui. Pesez-le comme
[Instruction, skill ou outil ?](/customizing-agents/skill-or-tool-or-instruction/)
a pesé chaque option : par ce qu’il ajoute à la fenêtre de contexte (context window) à chaque
tour, et par ce qu’il ajoute aux éléments qui peuvent agir dans vos sessions.

- **Installez-le** quand vous voulez ce que font la plupart de ses éléments.
  Choisissez la portée la plus étroite qui convient, et relisez le plugin quand
  une mise à jour arrive.
- **Copiez-en une skill** quand une skill est tout ce que vous voulez et que la
  licence du plugin vous permet de la copier. Une skill fonctionne sans plugin
  (@Claude Code plugins). La copie va dans le `.claude/skills/` de votre projet
  et ne reçoit pas de mises à jour. Elle est à vous à partir de ce moment. Une
  skill qui appelle un script situé ailleurs dans le plugin a aussi besoin de ce
  script.
- **Renoncez-y** quand ce que coûtent ses éléments dépasse ce qu’ils font pour
  vous, ou quand vous ne pouvez pas lire ce qu’un élément exécute.

Pour `release-kit`, vous vouliez une skill. Votre équipe ne met à jour
`CHANGELOG.md` que quand elle publie une version. Le hook bloquerait tous les
autres commits dans chaque dépôt où le plugin est activé. Le serveur de suivi des
tickets a besoin d’un jeton, et vous n’utilisez pas cet outil de suivi. La skill
n’utilise que les fichiers de son propre dossier. Copiez donc la skill. Si
l’équipe décide plus tard que chaque commit a besoin d’une entrée dans le
journal, c’est une règle pour le dépôt, et elle va dans un hook des réglages du
dépôt lui-même.

<Pitfall title="Le hook venu avec la skill de publication">
Un développeur installe `release-kit` en portée utilisateur pour obtenir la skill
de publication. Son équipe ne met à jour `CHANGELOG.md` que quand elle publie une
version. Une semaine plus tard, les commits ordinaires de l’agent se mettent à
échouer avec un message sur `CHANGELOG.md`, et l’agent ajoute une entrée au
journal à chaque commit pour passer le contrôle. Le développeur cherche la cause
dans la skill de publication et n’y trouve rien, parce que la cause est le hook,
qui s’exécute avant chaque commande shell dans chaque projet. Le plugin a été
installé pour un élément et les a tous apportés. Lisez `hooks/hooks.json` et les
scripts qu’il nomme avant d’installer un plugin, et n’installez pas un plugin
pour une skill que vous pouvez copier.
</Pitfall>

<Exercise stretch="Faites la même lecture sur un second plugin public qui déclare un serveur MCP, et dites quels accès demande le serveur.">
Lisez le plugin `hookify` du dépôt public
[claude-code](https://github.com/anthropics/claude-code/tree/e1bb7b065bc29117ab5923f8772fee16a4630a0d/plugins/hookify)
d’Anthropic, au commit que nomme le lien, et décidez quoi en faire. Sachez ce
qu’il peut changer avant de commencer. Ses hooks s’exécutent à chaque appel
d’outil, avant et après, à chaque prompt que vous envoyez et chaque fois que
Claude s’arrête. Ils peuvent bloquer un appel d’outil et empêcher Claude de
s’arrêter, et sa commande `/hookify:hookify` fait écrire à Claude des fichiers de
règles dans le dossier `.claude/` du projet. L’exercice est une lecture, donc il
n’installe pas le plugin. Si vous décidez après la lecture de l’essayer,
installez-le en portée locale dans un dépôt de brouillon, jamais là où vous avez
un vrai travail. Une installation vient de la place de marché,
`claude-code-plugins`, donc elle récupère le hookify actuel de cette place de
marché, qui peut différer du commit que vous avez lu. Cette place de marché a un nom
officiel, et ces places ont la mise à jour automatique activée par défaut
(@Claude Code plugin install). Relisez la copie installée avant de vous en
servir, ou désactivez d’abord la mise à jour automatique pour cette place de
marché.

Ces commandes récupèrent seulement le dossier du plugin, dans `~/plugin-read`, et
lancent l’inventaire dessus. La première ligne supprime `~/plugin-read`, donc les
commandes fonctionnent aussi à un second essai.

Un bon résultat nomme une skill, quatre commandes, et un agent avec `Read` et
`Grep`. Il nomme quatre hooks sans `matcher`, sur `PreToolUse`, `PostToolUse`,
`Stop` et `UserPromptSubmit`, et aucun serveur. L’inventaire estime à 358 jetons
par tour les noms et les descriptions. Les scripts lisent des fichiers de règles
nommés `.claude/hookify.*.local.md` dans le projet, et certaines règles lisent la
transcription de la session. Ils affichent une décision qui peut refuser un appel
d’outil ou empêcher Claude de s’arrêter. Copier la skill n’est pas une vraie
option ici, parce qu’elle enseigne le format de fichiers de règles que seuls les
hooks du plugin lisent. Le `LICENSE.md` du dépôt réserve aussi tous les droits,
donc vérifiez la licence avant de copier un fichier qui en vient. Que vous
coûteraient les hooks dans une session où vous n’avez aucune règle ?

<Recap>
1. Un plugin distribue ensemble des skills, des sous-agents, des hooks et des
   serveurs MCP, et vous l’installez en général par son nom depuis une place de
   marché (@Claude Code plugins).
2. Un plugin activé coûte du contexte à chaque tour et lance ses hooks sur leurs
   événements, y compris dans des sessions qui ne s’en servent jamais
   (@Claude Code plugins) (@Claude Code plugin parts).
3. Vos règles de permission vérifient les appels que fait Claude aux outils d’un
   plugin. Les hooks et les processus des serveurs s’exécutent avec vos droits
   d’utilisateur, hors des règles comme du bac à sable
   (@Claude Code plugin security).
4. Lisez `hooks/hooks.json`, les scripts qu’il nomme, `.mcp.json` et `bin/` avant
   d’installer. L’écran d’installation de Claude Code nomme chaque hook sans
   montrer la commande qu’il lance (@Claude Code plugin security).
5. Pesez un plugin comme une dépendance : l’installer, en copier une skill quand
   la licence le permet, ou y renoncer.
</Recap>

<Habit id="read-the-hooks-first">
La prochaine fois que quelqu’un vous propose un plugin, ouvrez son
`hooks/hooks.json` avant de l’installer. Nommez chaque événement sur lequel il
s’exécute.
</Habit>
