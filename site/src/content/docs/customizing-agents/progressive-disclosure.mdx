La leçon précédente s’est terminée par une skill de publication lancée depuis une
nouvelle session dans un clone propre. Supposons que l’équipe ait ensuite eu une
publication qui a mal tourné, et que quelqu’un ait ajouté à la skill une section
sur la façon d’en annuler une. La section est utile, et elle sert une fois sur
beaucoup de publications. Cette leçon mesure ce que coûte cette section à toutes
les autres publications, la déplace dans un fichier séparé vers lequel la skill
renvoie, et mesure de nouveau.

La mesure est faite par un court script Python qui ne fait que lire des
fichiers, et le cours vérifie sa sortie à chaque construction du site. Il se
trouve dans le dépôt du cours, dans
`site/examples/customizing-agents/progressive-disclosure/`, à côté de deux
versions de la skill de publication, en anglais comme le paquet. Lancez les
commandes de cette leçon depuis ce dossier. Dans la ligne `cd`, remplacez
`<course-repo>` par le chemin de votre copie du dépôt du cours.

```sh
cd <course-repo>/site/examples/customizing-agents/progressive-disclosure
```

## Ce que lit l’agent, et quand

Un agent qui prend en charge le format ouvert des skills ne lit pas une skill
entière d’un coup. Il la lit par étapes, et la spécification en nomme trois
(@Agent Skills spec). Au démarrage, l’agent charge le `name` et la `description`
de chaque skill qu’il voit. Quand une tâche correspond à une description, il
charge tout le `SKILL.md` de cette skill. Les autres fichiers du dossier de la
skill ne sont chargés que quand une étape de `SKILL.md` y envoie l’agent. La
présentation des skills d’Anthropic décrit les trois mêmes étapes pour Claude
(@Claude docs agent-skills-overview). Concevoir une skill pour ce fonctionnement
s’appelle la **divulgation progressive** (progressive disclosure) : chaque étape
ne contient que ce dont l’agent a besoin à ce moment-là (@AEC-17).

Chaque étape a son propre coût. Le nom et la description sont dans le contexte à
chaque tour de chaque session, que la skill s’exécute ou non. Les deux documents
estiment cette étape à environ 100 jetons (tokens) par skill. La spécification recommande
de garder le corps sous 5000 jetons, et la présentation d’Anthropic donne le même
chiffre pour le corps (@Agent Skills spec) (@Claude docs agent-skills-overview).
Dans Claude Code, le corps reste dans la conversation aux tours qui suivent
l’exécution de la skill (@Claude Code skills). Comme l’a montré
[Comment fonctionne un modèle de langage](/concepts/how-models-work/), le modèle
relit tout ce qui précède chaque fois qu’il prédit un jeton, donc un corps encore
dans le contexte est relu à chacun de ces tours. Un fichier que l’agent n’ouvre
jamais ne coûte aucun jeton (@Claude docs agent-skills-overview).

## Mesurer la skill telle qu’elle est

Le dossier `grown/release/` contient la skill de publication de la leçon
précédente, avec la nouvelle section ajoutée. Elle s’appelle « When a release
goes wrong » (quand une publication tourne mal) et a cinq étapes numérotées. Une
publication que personne n’a encore poussée s’annule avec `git tag -d` et un
reset. Pour une publication poussée, l’agent laisse l’étiquette distante telle
quelle et fait une nouvelle publication corrective. La section se trouve entre
les étapes de publication et « Done when ». L’agent la lit à chaque publication.

Le script `measure.py` affiche une ligne par étape. Pour la première étape, il
compte les lignes `name` et `description` de l’en-tête. La deuxième étape est le
`SKILL.md` complet, et chaque autre fichier Markdown du dossier a sa propre
ligne. Il affiche ensuite deux totaux, l’un pour une exécution qui ne lit que
`SKILL.md`, l’autre pour une exécution qui lit tous les fichiers.

Les nombres sont des estimations. Le script utilise la même règle que le
compteur de [Ce que le modèle peut voir](/concepts/context-window/), environ
quatre caractères par jeton. Un mot de six caractères au plus compte pour un
jeton, et un mot plus long pour un jeton tous les quatre caractères. Chaque signe
de ponctuation compte pour un jeton à lui seul. Le Markdown contient beaucoup de
ponctuation, et la règle donne un nombre plus élevé pour une skill que pour de la
prose simple de même longueur. Le nombre exact pour un modèle vient du découpeur
en jetons (tokenizer) de l’éditeur. La règle est la même pour les deux versions
de la skill, donc c’est la différence entre elles qui compte ici.

Avant de le lancer, devinez la deuxième ligne. Le fichier fait environ deux pages
de Markdown, et le compteur de la leçon sur les concepts donnait 115 jetons pour
une demi-page de notes.

## Déplacer l’annulation dans un fichier de référence

La correction consiste à garder le chemin courant dans `SKILL.md` et à déplacer
le cas rare dans son propre fichier. La spécification suggère de garder
`SKILL.md` court et de déplacer le matériel détaillé dans des fichiers séparés,
référencés par un chemin relatif et à un seul niveau de `SKILL.md`
(@Agent Skills spec). Le guide d’Anthropic explique ce niveau unique. L’agent
peut ne lire qu’une partie d’un fichier qu’il atteint par un autre fichier de
référence (@Claude docs best-practices).

Faites une copie de la skill agrandie pour travailler dessus. La première ligne
supprime `~/skill-copy`, donc les commandes fonctionnent aussi à un second essai.
Le dossier de la copie s’appelle `release`, parce que le nom du dossier d’une
skill doit être égal à son `name`.

```sh
rm -rf ~/skill-copy
mkdir ~/skill-copy
cp -R grown/release ~/skill-copy/release
```

Dans `~/skill-copy/release/`, créez `rollback.md` avec le titre et la ligne
d’ouverture ci-dessous. Déplacez-y le texte de la section « When a release goes
wrong », de sa première phrase à la fin de l’étape 5. Remplacez « Use this
section only when » par « Use these steps only when », parce que le texte est
maintenant un fichier à part. Gardez le texte en anglais pour obtenir les mêmes
nombres que le cours : le titre dit d’annuler une publication du paquet de
notes, et la ligne d’ouverture dit que la skill de publication envoie l’agent
ici, de n’utiliser ces étapes que quand l’utilisateur demande d’annuler une
publication ou qu’un contrôle après l’étiquette montre qu’elle est fausse, et de
ne rien annuler d’autre.

```markdown
# Undo a release of the notes package

The release skill sends you here. Use these steps only when the user
asks you to undo a release, or when a check after the tag shows that the
release is wrong. Undo nothing else.

1. Run `git describe --tags`, `git log --format='%h %s' -n 3` and ...
```

Laissez ensuite le titre dans `SKILL.md` et remplacez le texte qui suit par un
renvoi qui dit quand lire le fichier. Le renvoi dit que si l’utilisateur demande
d’annuler une publication, ou qu’un contrôle après l’étiquette montre qu’elle est
fausse, l’agent lit `rollback.md` dans le dossier de cette skill et le suit, sans
rien annuler avant de l’avoir lu :

```markdown
## When a release goes wrong

If the user asks you to undo a release, or a check after the tag shows
that the release is wrong, read `rollback.md` in this skill's directory
and follow it. Don't undo anything before you have read it.
```

Le renvoi nomme la situation, et c’est ce qui le fait fonctionner. Une ligne qui
dit seulement « voir `rollback.md` » ne donne à l’agent aucun moyen de savoir si
cette exécution a besoin du fichier, donc il peut le lire à chaque fois, ou
jamais. Le guide d’Anthropic dit d’y faire attention quand vous testez une
skill : un agent qui n’ouvre jamais un fichier fourni avec la skill manque
peut-être d’un signal assez clair dans `SKILL.md` (@Claude docs best-practices).
L’agent ne lit le renvoi que lors d’une exécution où la skill s’est chargée. Une
annulation demandée dans une nouvelle session ne charge la skill que si sa
description nomme cette demande.

Le dépôt du cours contient le résultat dans `split/release/`. Mesurez-le, puis
mesurez votre copie avec `python3 measure.py ~/skill-copy/release`. Si vous avez
déplacé le texte comme indiqué, votre copie donne les mêmes nombres. Sa première
ligne est votre chemin.

<Pitfall title="La skill qui grandissait section par section">
La skill de publication d’une équipe commence à quarante lignes. En six mois,
des personnes ajoutent une note sur les corrections urgentes et un tableau des
incidents passés. Viennent ensuite les étapes d’annulation et un paragraphe sur
l’ancien outil de publication. Chaque modification est assez petite pour que
personne ne s’y oppose en revue. Le corps finit trois fois plus long qu’au
départ, et une publication le charge en entier, alors que la plupart des
exécutions n’ont besoin que des quarante premières lignes. Quelqu’un ajoute aussi
à la description des mots déclencheurs pour chaque nouveau cas, que chaque
session paie. Chaque modification semblait peu coûteuse, et personne n’a mesuré
la somme. Mesurez la skill chaque fois que vous y ajoutez quelque chose, et ne
gardez dans le corps que ce dont chaque exécution a besoin.
</Pitfall>

Pour aller plus loin, ces commandes placent votre skill découpée dans le clone
propre de la leçon précédente et la committent, puis font une modification que

<Recap>
1. Un agent charge une skill par étapes : le nom et la description de chaque
   skill au démarrage, le `SKILL.md` complet quand une tâche lui correspond, et
   les autres fichiers seulement quand une étape y renvoie (@Agent Skills spec)
   (@Claude docs agent-skills-overview).
2. La description se paie à chaque tour de chaque session, et le corps à chaque
   exécution de la skill. Dans Claude Code, le corps reste dans la conversation
   aux tours qui suivent son exécution (@Claude Code skills).
3. Gardez le chemin courant dans `SKILL.md`. Déplacez un cas rare ou une longue
   référence dans un fichier à un niveau de `SKILL.md`, et laissez un renvoi qui
   dit quand le lire (@Claude docs best-practices).
4. Mesurez la skill avec la même règle avant et après une modification. Une
   estimation suffit pour comparer deux versions. Le nombre exact pour un modèle
   vient du découpeur en jetons de l’éditeur.
5. Les skills grandissent petit à petit, donc mesurez après chaque ajout.
</Recap>

<Habit id="measure-after-adding">
La prochaine fois que vous ajoutez une section à une skill, mesurez la skill
avant et après la modification. Demandez-vous ensuite si chaque exécution a
besoin de la nouvelle section.
</Habit>
