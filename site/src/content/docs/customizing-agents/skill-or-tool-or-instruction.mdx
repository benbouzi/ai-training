Une équipe de quatre personnes adopte un agent de code. Pendant le premier mois,
elle remarque trois choses sur lesquelles il se trompe sans cesse. Il committe
avec un format de message que l’équipe n’utilise pas. Il écrit les notes de
version dans un ordre différent à chaque fois. Il ne sait pas dire si le compte
d’un client est sur l’ancienne formule de facturation ou sur la nouvelle, parce
que cette information se trouve dans un service interne. Quelqu’un de l’équipe a
entendu parler des skills, et écrit donc une skill pour chacune. Deux des trois
échouent. Cette leçon explique pourquoi, et donne la question à se poser avant
d’écrire quoi que ce soit.

Vous ne lancez rien ici. Les exemples sont de courts contenus de fichiers et une
décision détaillée, et l’exercice est un tri que vous faites sur papier.

## Trois mécanismes, côte à côte

Dans la boucle d’agent (agent loop) du cours sur les concepts, le modèle lit son contexte et
décide de la suite, et le logiciel qui l’entoure exécute les outils qu’il
demande (@AEC-03). Chaque façon de personnaliser un agent change l’une de ces
deux parties. Soit elle met un autre texte dans le contexte, soit elle donne au
logiciel un autre ensemble d’outils à exécuter. Le choix entre skill, outil ou
instruction revient à savoir laquelle des deux parties il faut changer.

Une **instruction** est un texte permanent, chargé au début de chaque session et
présent à chaque tour. L’`AGENTS.md` de la leçon sur les instructions de projet
en est une. Elle convient à une règle qui s’applique toujours, la commande de
test en étant l’exemple habituel. Le harnais (harness) la charge à chaque fois. Elle est là,
que la tâche en ait besoin ou non (@Academy claude-code-101) (@Claude Code memory).

Une **skill** est une procédure avec un déclencheur. C’est un dossier avec une
courte description du moment où elle s’applique, et l’agent ne voit que cette
description jusqu’à ce qu’une tâche lui corresponde. Il charge alors les
instructions complètes et les suit. Dans Claude Code, le texte chargé reste dans
la conversation pour le reste de la session, et c’est le compactage qui le
réduit (@Claude Code skills). Une skill convient à un travail que l’agent
saurait faire seul mais fait de façon irrégulière. Une liste de vérification de
publication en est l’exemple habituel (@Academy introduction-to-agent-skills).

Un **outil** est une fonction que le logiciel exécute quand le modèle le
demande. Il ajoute une capacité que le modèle n’a pas. Une requête à une base de
données et un appel à un service interne en sont deux exemples. L’agent voit au
moins le nom de l’outil à chaque tour, et sa description complète et son schéma
soit à chaque tour, soit quand il cherche l’outil, selon le client
(@Claude Code mcp). La fonction elle-même s’exécute hors du modèle. Un outil
convient à un besoin que l’agent ne peut pas satisfaire avec du texte seul.

Les mêmes faits, en tableau :

| | Instruction | Skill | Outil |
| --- | --- | --- | --- |
| Ce que c’est | Un texte permanent | Une procédure avec un déclencheur | Une fonction que le logiciel exécute |
| Chargé | À chaque tour de chaque session | Quand une tâche correspond à sa description | Le nom à chaque tour, et la définition au départ ou à la recherche |
| Corrige | L’agent ne connaît pas une règle | L’agent sait faire, mais fait différemment à chaque fois | L’agent ne peut pas le faire du tout |
| Exemple | « Tester avec `uv run pytest` » | « Préparer une version : numéro, journal des modifications, étiquette » | `billing_plan(account_id)` |

Revenons à l’équipe. Le format des commits est une règle qui s’applique à chaque
commit. Écrit sous forme de skill, l’agent ne le charge que quand il décide
qu’une tâche concerne un commit. Une bonne partie du temps, il ne le décide pas.
Le format va dans une instruction. Les notes de version sont une procédure que
l’agent sait déjà écrire et qu’il écrit chaque fois autrement, donc elles vont
dans une skill, et c’est celle des trois qui a fonctionné. La formule de
facturation est un fait que l’agent n’a aucun moyen d’atteindre, et aucun texte
ne peut le lui apprendre, donc il faut un outil.

## La question à poser d’abord

Avant de choisir parmi les trois, demandez-vous si l’agent sait déjà faire la
tâche avec ce qu’il a. Un agent de code est livré avec un shell et un éditeur,
et le modèle derrière lui a lu énormément de documentation. Une grande partie de
ce pour quoi une équipe veut une skill ou un outil est déjà à sa portée.

Prenons un cas concret. L’équipe veut que l’agent vérifie l’état de la CI d’une
pull request avant de dire que le travail est terminé. Quelqu’un commence une
skill, dont la description dit de vérifier si l’exécution de CI de la pull
request en cours a réussi, et dont le corps dit de lancer `gh pr checks`, de
lire l’état de chaque contrôle, et en cas d’échec de lancer
`gh run view --log-failed` pour résumer l’échec :

```markdown
---
name: check-ci
description: Check whether the CI run for the current pull request passed.
---

Run `gh pr checks` and read the status of each check. If any check
failed, run `gh run view --log-failed` for that run and summarize the
failure.
```

Posez maintenant la question. L’agent a un shell. La commande `gh` est installée
sur la machine. Le modèle connaît déjà `gh pr checks` et `gh run view`, parce
que leur documentation est publique et répandue. Quand on lui demande de
« vérifier si la CI a passé », l’agent lance ces commandes sans aide. La skill
ajoute un nom à la liste des skills à chaque tour et n’apprend rien que l’agent
ne savait pas.

Ce que voulait l’équipe, c’est que l’agent vérifie la CI *avant* de dire qu’il a
fini, à chaque fois. C’est une ligne dans `AGENTS.md` : « Avant de dire qu’une
tâche est terminée, lance `gh pr checks` et rapporte le résultat. » La règle
s’applique toujours, donc elle va dans le texte permanent.

Une skill mérite sa place quand la procédure contient quelque chose que l’agent
devrait deviner : l’ordre dans lequel votre équipe fait les choses, le fichier où
va un résultat, un contrôle auquel l’agent ne penserait pas, un script qui fait
une étape déterministe de la même façon à chaque fois. Une skill qui répète ce
que le modèle sait déjà dépense du contexte pour rien.

## Ce que coûte chacun

Les trois mécanismes diffèrent par ce qu’ils prennent à l’agent à chaque tour et
par ce qu’ils lui permettent de faire. Placez-les sur deux axes.

**Le contexte.** Un fichier d’instructions est lu en entier à chaque tour de
chaque session, que la tâche en ait besoin ou non. Une skill met une ligne, sa
description, dans le contexte à chaque tour, et son corps complet à partir du
tour où elle est invoquée. Avec beaucoup de skills installées, Claude Code garde
le nom de chaque skill dans la liste des skills, mais peut laisser tomber les
descriptions des skills les moins utilisées, pour rester dans un budget de
caractères calculé selon la fenêtre de contexte (@Claude Code skills). Dans un
agent qui charge tous les outils au départ, un outil met son nom, sa description
et le schéma de ses paramètres dans le contexte à chaque tour, et un serveur qui
expose trente outils en met trente (@AEC-03). Claude Code diffère par défaut le
chargement des définitions des outils MCP et ne charge au début d’une session
que les noms des outils et les instructions du serveur, donc le coût par outil y
est plus faible, et c’est quand même un coût à chaque tour (@Claude Code mcp).
L’avertissement sur les longs fichiers d’instructions de la leçon sur les
instructions de projet est le même que celui sur la connexion de trop nombreux
serveurs d’outils. Les deux dépensent le même budget.

**La permission.** Une instruction et une skill changent ce que l’agent fait avec
les capacités qu’il a déjà. Aucune des deux ne lui permet d’atteindre quelque
chose de nouveau. Un outil, si. C’est une nouvelle capacité, avec tous les accès
que portent ses identifiants, et chaque outil que l’agent reçoit est une chose de
plus à prendre en compte quand vous mesurez ce qu’une erreur peut atteindre.

Ces deux axes laissent un espace entre une commande que l’agent sait déjà lancer
et un serveur d’outils qui enveloppe un système. Prenons un service interne avec
un client en ligne de commande que l’équipe utilise déjà. L’agent a un shell,
donc il peut lancer le client tel quel, et cela suffit souvent. Quand les options
du client sont inhabituelles, ou que l’usage qu’en fait l’équipe suit un ordre
d’étapes fixe, une skill qui enveloppe le client comble l’espace. Elle ne se
charge que quand une tâche fait appel au service, elle coûte une ligne de
description d’ici là, et elle n’ajoute aucune capacité nouvelle, parce que le
shell et le client étaient déjà là. Les conseils d’Anthropic indiquent cette voie
intermédiaire : une skill autour d’une commande, avant d’écrire ou de connecter
un serveur d’outils pour elle (@Academy claude-code-101). Le guide de Claude
Code sur les coûts fait une remarque voisine sur le contexte : un client en ligne
de commande n’ajoute aucune liste d’outils, donc il coûte moins de contexte qu’un
serveur d’outils (@Claude Code costs). Un serveur d’outils est le bon choix quand
il n’y a aucun client à envelopper, quand la capacité est nouvelle pour l’agent,
ou quand vous avez besoin du schéma et du contrôle d’accès qu’un outil vous donne
et qu’une commande shell ne donne pas.

<Pitfall title="La règle qui ne s’est jamais déclenchée">
Une équipe écrit une skill appelée `no-secrets`, dont le corps dit « ne jamais
committer un fichier qui contient une clé d’API ». Sa description dit
« Empêcher que des secrets soient committés ». Deux semaines plus tard, l’agent
committe un fichier `.env`. Personne ne lui avait demandé d’empêcher quoi que ce
soit, donc aucune tâche n’a jamais correspondu à la description, et la skill n’a
jamais été chargée. Une skill est chargée quand l’agent décide qu’une tâche lui
correspond. Une règle qui doit tenir sur chaque tâche va dans le fichier
d’instructions, et une règle qui ne doit jamais être enfreinte va dans un hook
qui bloque l’action, comme l’a dit la leçon sur les instructions de projet.
</Pitfall>

Un bon résultat donne pour chaque élément une raison qu’un collègue accepterait
sans voir votre tri, et ne met pas plus de deux éléments dans le groupe outil.
La plupart de ce que veut une équipe est une règle ou une procédure, et l’agent a
déjà les mains. Quel élément a été le plus long à placer, et quelle question l’a
tranché ?
</Exercise>

<Recap>
1. Une instruction est un texte permanent présent à chaque tour, une skill est
   une procédure chargée quand une tâche correspond à sa description, et un outil
   est une fonction pour une capacité qui manque à l’agent (@AEC-17).
2. Avant d’écrire l’un d’eux, demandez-vous si l’agent sait déjà faire la tâche
   avec un shell et ce que sait le modèle. Une skill qui répète une documentation
   publique ajoute une ligne à chaque tour et n’apprend rien.
3. Choisissez selon que la règle s’applique toujours (instruction), que l’agent
   sait faire mais de façon irrégulière (skill), ou qu’il lui manque la capacité
   (outil).
4. Les instructions et les skills dépensent du contexte et n’ajoutent aucun
   nouvel accès. Un outil dépense du contexte à chaque tour et ajoute une
   capacité avec tous les accès que portent ses identifiants.
5. Une skill qui enveloppe une commande que l’agent sait déjà lancer est la voie
   intermédiaire entre la commande seule et la connexion d’un serveur d’outils
   (@Academy claude-code-101).
</Recap>
