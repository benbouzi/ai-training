La leçon sur l’écriture de votre première skill s’est terminée par une skill de
publication qui fonctionne dans le dossier où elle a été écrite. Cette leçon la
lance ailleurs : dans un clone propre, et dans une nouvelle session qui n’a rien
de la conversation que vous avez eue en l’écrivant. Le guide d’Anthropic sur
l’écriture des skills décrit la même boucle. Une session vous aide à écrire la
skill, une session neuve l’utilise sur une vraie tâche, et vous regardez où la
session neuve peine pour le reporter dans le fichier
(@Claude docs best-practices).

Vous lancez d’abord la skill et lisez dans la transcription les endroits où
l’agent a hésité, vous a demandé quelque chose ou a deviné. Vous transformez
ensuite chacun de ces endroits en une ligne de la skill, vous la relancez et vous
comparez les deux exécutions. Deux courts scripts Python montrent ce que voit
l’agent dans chaque dépôt, et le cours vérifie leur sortie à chaque construction
du site.

## La lancer ailleurs que là où elle a été écrite

Un clone propre est une copie du paquet avec son propre dépôt git, et rien
d’autre. Il n’a aucune des étiquettes de l’auteur, ni son historique, ni ses
fichiers non committés. Créez-en un hors du dépôt du cours. Claude Code lit les
fichiers `CLAUDE.md` du dossier où il démarre et de chaque dossier au-dessus
(@Claude Code memory), donc une copie dans le dépôt du cours reçoit aussi les
instructions pour agents du cours.

La mémoire automatique enregistre ce qu’une session a appris pour les sessions
suivantes. Elle est active par défaut, et elle est gardée par dépôt git
(@Claude Code memory). La même page dit de la désactiver pour un projet en
réglant `autoMemoryEnabled` à `false` dans les réglages de ce projet, et les
commandes ci-dessous le font dans `.claude/settings.local.json`. Elles disent
aussi à git d’ignorer ce fichier, pour qu’il n’apparaisse jamais comme une
modification. Vos instructions personnelles dans `~/.claude/CLAUDE.md` se
chargent dans chaque session, dans chaque projet (@Claude Code memory), et elles
atteignent quand même le test.

Lancez ces commandes depuis le haut de votre copie du dépôt du cours, pour que la
ligne `cp` trouve le paquet. La première ligne supprime `~/notes-clean`, donc les
commandes fonctionnent aussi à un second essai. La ligne `rm -rf __pycache__`
retire les fichiers compilés qui se trouvent dans le dossier de l’exemple si vous
avez lancé son contrôle dans le dépôt du cours.

```sh
rm -rf ~/notes-clean
cp -R site/examples/customizing-agents/first-skill/fixture-package ~/notes-clean
cd ~/notes-clean
rm -rf __pycache__
git init -q
echo '{ "autoMemoryEnabled": false }' > .claude/settings.local.json
mkdir -p .git/info
echo .claude/settings.local.json >> .git/info/exclude
git add .
git commit -q -m "Import the notes package"
```

La copie contient la skill de publication de la leçon sur l’écriture de votre
première skill, dans `.claude/skills/release/SKILL.md`. Lancez votre agent dans
`~/notes-clean`, dans une nouvelle session, et tapez `/release 0.4.0`. Dans
Claude Code, le nom du dossier de la skill est la commande que vous tapez
(@Claude Code skills), et dans un autre agent vous pouvez demander la version
0.4.0 avec des mots. La skill modifie des fichiers, committe et étiquette, et
c’est pourquoi elle s’exécute dans cette copie et nulle part ailleurs. La copie
n’a pas de dépôt distant, donc un push n’a nulle part où aller.

L’étape 3 de la skill dit d’écrire une puce du journal des modifications par
changement depuis la version précédente, et de lire `git log` pour en avoir la
liste. Le premier script construit deux dépôts et demande à chacun ce dont
l’étape 3 a besoin. Le dépôt de l’auteur a le paquet committé comme version
0.3.0, une étiquette `v0.3.0` sur ce commit, et une modification après lui. Le
clone propre est celui que vous venez de créer.

## Transformer chaque hésitation en ligne

Dans cette exécution, les hésitations venaient d’une skill qui supposait quelque
chose sur l’environnement, comme une étiquette ou un arbre de travail propre.
Dans d’autres exécutions, elles viennent d’une étape qui suppose qu’un outil est
installé, ou d’un test de réussite trop vague pour distinguer un bon résultat
d’un mauvais. Le guide d’Anthropic dit la même chose des scripts : ne supposez
pas qu’un paquet est installé, et nommez ce dont la skill a besoin
(@Claude docs best-practices).

La correction des deux premiers cas est une courte liste de vérifications en
haut de la skill, chacune avec quoi faire quand elle échoue. Ajoutez cette
section au-dessus de `## Steps` :

```markdown
## Before you start

Run these checks in order. If one fails, stop, and report the command, what
it printed and what the user has to do. Don't fix the repository yourself.

1. `git --version` and `python3 --version` each print a version. If one
   prints an error, that tool is missing. Name it and stop.
2. `git status --porcelain` prints nothing, or only `?? __pycache__/`.
   An error means this directory is not a git repository. Any other line
   is an uncommitted change. Say which, and stop.
3. `git describe --tags --abbrev=0` prints the tag of the previous
   release, `v` and the `__version__` in `notes.py`. If it fails, there is
   no release tag. Ask the user to tag the commit of the previous release,
   and stop. Don't work that commit out from the changelog.
4. `git log --format=%s <tag>..HEAD` prints at least one line. If it
   prints nothing, there is nothing to release. Say so and stop.
```

La section, en anglais comme le reste de la skill, demande de lancer quatre
vérifications dans l’ordre, et en cas d’échec de s’arrêter et de rapporter la
commande, ce qu’elle a affiché et ce que l’utilisateur doit faire, sans réparer
le dépôt soi-même. Première vérification : `git` et `python3` affichent chacun
une version, sinon l’outil manque. Deuxième : `git status --porcelain`
n’affiche rien, ou seulement `?? __pycache__/`, sinon le dossier n’est pas un
dépôt git ou il y a une modification non committée. Troisième :
`git describe --tags --abbrev=0` affiche l’étiquette de la version précédente.
S’il échoue, l’agent demande à l’utilisateur d’étiqueter le commit de la version
précédente et s’arrête, sans le déduire du journal des modifications.
Quatrième : `git log` depuis cette étiquette affiche au moins une ligne, sinon il
n’y a rien à publier.

Faites ensuite pointer l’étape 3 vers ce journal, et faites dire à l’étape 5 ce
qu’il faut committer :

```markdown
3. In `CHANGELOG.md`, add a `## <version>` heading under the title, above
   the previous release, with one bullet per user-visible change in the
   log from check 4. Leave out a commit a user would not notice. Never
   write a bullet that no commit in that log supports.
...
5. Stage `notes.py` and `CHANGELOG.md` only, and commit with the message
   `release: <version>`. Step 1 leaves a `__pycache__` directory behind.
   Don't commit it. Then tag the commit with `git tag v<version>`.
```

L’étape 3 écrit maintenant une puce par changement visible du journal de la
quatrième vérification, laisse de côté un commit qu’un utilisateur ne
remarquerait pas, et n’écrit jamais une puce qu’aucun commit ne justifie.
L’étape 5 n’indexe que `notes.py` et `CHANGELOG.md`, ne committe pas le dossier
`__pycache__` que laisse l’étape 1, puis étiquette le commit.

La troisième vérification est celle qui répond à la transcription. L’agent a
deviné parce que la skill ne lui donnait rien à faire quand l’étiquette manquait.
Il a maintenant une instruction, et l’instruction est de s’arrêter. Une skill qui
s’arrête sur une question claire vaut mieux qu’une skill qui termine avec un
journal des modifications inventé, parce que vous voyez l’arrêt, alors que vous
pourriez ne pas lire le journal.

## La relancer et comparer

Remettez d’abord le clone dans l’état où il était avant la première exécution.
Ces deux commandes suppriment l’étiquette `v0.4.0` et ramènent la branche au
commit d’importation, ce qui abandonne chaque modification qui le suit.
`git tag -d` affiche une erreur si la première exécution n’a pas créé
d’étiquette, et ce n’est pas grave. Le reset abandonne aussi les modifications
que vous n’avez pas committées, donc lancez-le avant de réviser la skill.

```sh
cd ~/notes-clean
git tag -d v0.4.0
git reset -q --hard "$(git rev-list --max-parents=0 HEAD)"
```

Écrivez maintenant vos révisions dans `.claude/skills/release/SKILL.md`, ou
copiez le fichier révisé depuis le dépôt du cours, et committez la modification.
La nouvelle deuxième vérification s’arrête sur toute modification non committée,
y compris une skill modifiée. Dans la ligne `cp`, remplacez `<course-repo>` par le
chemin de votre copie du dépôt du cours. Laissez de côté la ligne `cp` si vous
avez écrit votre propre révision.

```sh
cd ~/notes-clean
cp <course-repo>/site/examples/customizing-agents/testing-a-skill/release/SKILL.md .claude/skills/release/SKILL.md
git commit -q -a -m "Revise the release skill"
```

Claude Code prend en compte une skill modifiée dans la session déjà en cours
(@Claude Code skills), mais démarrez quand même une nouvelle session. L’ancienne
session contient encore votre réponse sur `__pycache__/`, et une nouvelle
exécution dans cette session teste la skill plus cette réponse. La mémoire
automatique est désactivée dans ce clone, et dans Claude Code vous pouvez lancer
`/memory` pour voir quels fichiers de mémoire une session peut charger
(@Claude Code memory). Tapez de nouveau `/release 0.4.0`.

Une bonne exécution s’arrête maintenant à la troisième vérification. L’agent
signale que `git describe` n’a trouvé aucune étiquette et vous demande
d’étiqueter le commit de la version précédente. C’est la skill qui fonctionne :
il manque au dépôt un fait qu’aucun agent ne peut déduire, et la skill dit de le
demander.

<Pitfall title="La skill qui ne marchait qu’à la maison">
Un ingénieur écrit une skill de publication dans son propre clone, la lance trois
fois à cet endroit, et la partage. Sur le portable d’une collègue, l’agent écrit
un journal à partir de tout l’historique et committe un dossier `__pycache__`.
Le clone de l’ingénieur avait les étiquettes, et quelques semaines plus tôt il
avait dit à son agent de ne pas committer `__pycache__`. Claude Code peut garder
une correction de ce genre dans la mémoire automatique, qui est active par
défaut et enregistrée par dépôt sur une machine (@Claude Code memory). La skill
ne l’a jamais dit, et c’est l’agent de l’ingénieur qui s’en souvenait pour lui.
Testez une skill dans un clone propre, dans un nouveau dossier, et demandez à un
collègue de la lancer une fois sur sa machine avant de compter sur elle.
</Pitfall>

<Exercise stretch="Demandez à un collègue de lancer votre skill révisée dans son propre clone propre, sur sa propre machine, sans votre aide. Ajoutez une ligne pour chaque question que son agent a posée.">
Si vous avez suivi la démonstration, vos exécutions dans `~/notes-clean` sont
l’exercice, et vous pouvez passer au résultat ci-dessous. Sinon, créez un clone
propre avec les commandes de la première section. Elles suppriment et recréent
`~/notes-clean`, et le clone contient la skill de publication de la leçon sur
l’écriture de votre première skill. La skill modifie `notes.py` et
`CHANGELOG.md`, committe et étiquette, donc lancez-la seulement dans cette copie,
qui n’a aucun dépôt distant vers lequel pousser. Dans une nouvelle session,
tapez `/release 0.4.0`, et notez chaque endroit de la transcription où l’agent a
hésité, vous a demandé quelque chose ou a deviné. Pour chacun, ajoutez à la skill
une vérification, une étape d’échec ou une ligne « Done when » plus précise.
Remettez ensuite le clone à zéro, committez la skill révisée et relancez-la dans
une nouvelle session, comme dans la dernière section.

Un bon résultat : votre liste compte au moins deux endroits, chacun avec la ligne
qui y répond. La nouvelle exécution s’arrête sur l’étiquette manquante sans
deviner, et après que vous avez étiqueté `v0.3.0` et fait une modification, elle
se termine avec une puce dans le journal et `git describe --tags` qui affiche
`v0.4.0`. Laquelle de vos hésitations venait de quelque chose que vous saviez
sans l’avoir jamais écrit ?
</Exercise>

<Recap>
1. Testez une skill dans un clone propre et une nouvelle session, avec la mémoire
   automatique désactivée (@Claude Code memory), pour que la conversation que
   vous avez eue en l’écrivant ne puisse pas combler un manque pour l’agent
   (@Claude docs best-practices). Vos instructions personnelles se chargent
   quand même, et la machine d’un collègue est le test qui s’en passe.
2. Lisez dans la transcription chaque endroit où l’agent a hésité, demandé ou
   deviné. Chacun est une ligne qui manque à la skill.
3. Une ligne manquante est souvent une vérification de l’environnement avant les
   étapes, une étape qui nomme l’outil ou l’état dont elle a besoin, ou un test
   de réussite assez exact pour faire échouer un mauvais résultat.
4. Quand un fait manque au dépôt, la bonne ligne dit à l’agent de s’arrêter et
   de demander. Un arrêt clair vaut mieux qu’une supposition qui passe le
   contrôle.
5. Relancez dans une nouvelle session après chaque révision, et comparez les deux
   exécutions.
</Recap>

<Habit id="rerun-before-sharing">
La prochaine fois que vous écrivez ou modifiez une skill, lancez-la une fois dans
une nouvelle session sur une copie propre avant de la partager, et lisez où
l’agent a hésité.
</Habit>
