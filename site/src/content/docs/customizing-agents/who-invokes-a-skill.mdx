La leçon précédente a écrit une skill de publication et l’a enregistrée dans le
paquet, dans `.claude/skills/release/SKILL.md`. Ce fichier est venu avec des
décisions que la leçon a prises par défaut. L’une porte sur qui peut lancer la
skill. Telle qu’elle est écrite, l’agent la charge quand une demande correspond
à la description, et vous pouvez aussi la lancer en tapant `/release`. L’autre
porte sur l’endroit où se trouve le fichier. Il est dans le dossier du projet,
donc une fois committé, toute l’équipe l’a. Personne en dehors du dépôt ne l’a.

Cette leçon prend ces deux décisions délibérément. Qui peut lancer une skill,
c’est son mode d’invocation. L’endroit où elle est installée, c’est la portée
d’une skill. Vous ne lancez rien ici. Les exemples sont quelques lignes d’en-tête
et quelques chemins de dossiers, et l’exercice est une décision que vous écrivez.

## Qui peut lancer une skill

Dans Claude Code, une skill sans réglage supplémentaire peut être lancée de deux
façons. Vous tapez son nom après une barre oblique, ou le modèle la charge quand
votre demande correspond à sa description. Chacun de ces champs d’en-tête retire
l’une des deux (@Claude Code skills) :

- `disable-model-invocation: true` retire le modèle. Seule une personne qui tape
  `/name` lance la skill. Si le modèle essaie quand même de la lancer, Claude
  Code refuse l’appel.
- `user-invocable: false` retire la personne. La skill n’est plus dans le menu
  `/`, et taper son nom ne la lance pas. Le modèle la charge toujours quand une
  demande correspond.

Ce choix décide aussi de ce que coûte la skill avant que quiconque l’utilise.
Une skill que le modèle peut lancer a sa description dans le contexte de chaque
session, pour que le modèle puisse y comparer les demandes. Une skill que seule
une personne peut lancer n’a aucune description dans le contexte, et rien d’elle
ne se charge tant que quelqu’un ne tape pas son nom (@Claude Code skills). Une
skill sans effet de bord qui n’aide que rarement, comme un rapport que vous
lancez quelques fois par an, met quand même sa description dans chaque session
entre deux usages tant que le modèle peut la lancer. La réserver à une personne
supprime ce coût.

| En-tête | Une personne peut la lancer | Le modèle peut la lancer | Description dans chaque session |
| --- | --- | --- | --- |
| Aucun des deux champs | Oui | Oui | Oui |
| `disable-model-invocation: true` | Oui | Non | Non |
| `user-invocable: false` | Non | Oui | Oui |

Réservez une skill à une personne quand une exécution a des effets dont vous
voulez choisir le moment. Un déploiement, un message dans un canal que d’autres
lisent, et une suppression sur un compte partagé en sont des exemples. Une skill
invoquée par le modèle démarre dès qu’une demande ressemble à sa description, et
une demande peut lui ressembler un jour où personne ne voulait déployer. La page
de Claude Code donne les effets de bord comme raison d’être du champ
(@Claude Code skills). La skill de publication de la leçon précédente committe
et étiquette, mais ne pousse pas. Une mauvaise exécution reste sur votre machine,
et `git` peut l’annuler. La laisser invocable par le modèle est un choix
raisonnable. Une version qui pousserait aussi l’étiquette serait réservée à une
personne.

Laissez le modèle quand la skill contient un savoir ou une procédure qui doit
s’appliquer chaque fois que le travail le demande, comme les règles de l’équipe
pour écrire une migration de base de données. Le réglage réservé au modèle,
`user-invocable: false`, sert à une skill qu’une personne ne lancerait pas comme
une commande, par exemple des notes sur le fonctionnement d’un vieux module, dont
l’agent a besoin quand il modifie ce module et qu’une personne ne tape jamais.

Une phrase dans la description comme « à utiliser seulement quand
l’utilisateur le demande » est un texte que le modèle lit et pèse. Ce n’est pas
un réglage, donc la description est toujours dans le contexte, et le modèle peut
toujours décider qu’une demande correspond. C’est le champ que Claude Code
impose.

Ces deux champs sont propres à Claude Code. Le format ouvert des skills liste
`name`, `description`, `license`, `compatibility`, `metadata` et `allowed-tools`
comme champs d’en-tête, et aucun ne dit qui peut lancer une skill
(@Agent Skills spec). La page de Claude Code dit aussi que lorsque vous téléversez
une skill sur claude.ai, un champ hors de cette liste fait échouer le
téléversement (@Claude Code skills). Quand vous déplacez une skill vers un autre
produit, vérifiez comment ce produit décide qui la lance.

<Pitfall title="L’annonce qui s’est envoyée toute seule">
Une équipe écrit une skill qui rédige les notes de version et les envoie par
courriel à la liste de diffusion des clients, et laisse l’en-tête par défaut. Un
mois plus tard, un développeur demande à l’agent de « résumer ce qui a changé
cette semaine » pour une réunion interne. La demande correspond à la
description, le modèle charge la skill, et le brouillon part chez les clients.
Les étapes étaient justes, et le problème venait de la permission du modèle de
les lancer. Donnez à chaque skill qui envoie, publie, déploie ou supprime
`disable-model-invocation: true` avant de la committer.
</Pitfall>

## Où une skill est installée

Le dossier où se trouve une skill décide de qui l’a. Claude Code lit les skills à
ces endroits (@Claude Code skills) :

| Portée | Dossier | Qui l’a |
| --- | --- | --- |
| Personnelle | `~/.claude/skills/<name>/SKILL.md` | Vous, dans chaque projet sur cette machine |
| Projet | `.claude/skills/<name>/SKILL.md` dans le dépôt | Toute personne qui travaille dans le dépôt, une fois la skill committée |
| Entreprise | `.claude/skills/<name>/SKILL.md` dans le dossier des réglages gérés | Chaque utilisateur des machines où l’organisation l’installe |

Un plugin peut aussi contenir des skills. [La leçon sur les
plugins](/customizing-agents/plugins/) en parle. Claude Code donne à chaque skill
de plugin le nom du plugin comme préfixe, pour qu’elle n’entre jamais en conflit
avec une skill de ces dossiers (@Claude Code skills).

Une skill de projet fait partie du dépôt. Elle change dans un commit, un
relecteur lit la modification, et un collègue qui récupère la branche a la même
version que vous. Mettez une skill à cet endroit quand l’équipe en a besoin pour
travailler sur ce code, comme la procédure de publication du paquet. Une skill
personnelle n’est que sur votre machine et change quand vous la modifiez. Elle
convient à une habitude à vous que vous voulez dans chaque projet, comme le
format que vous aimez pour les comptes rendus de réunion.

Quand deux de ces dossiers contiennent une skill du même nom, Claude Code en
lance une seule. L’entreprise l’emporte sur le personnel, et le personnel
l’emporte sur le projet (@Claude Code skills). Une skill `release` personnelle
dans votre dossier personnel masque la skill `release` de l’équipe dans le dépôt,
et `/release` lance votre copie, même si elle a des mois de retard.

<Exercise stretch="Listez les skills de votre propre dossier ~/.claude/skills/ et celles du dossier .claude/skills/ d’un dépôt sur lequel vous travaillez. Un nom apparaît-il dans les deux ? Si oui, laquelle se lance quand vous le tapez, et est-ce celle que vous voulez ?">
Une équipe prévoit d’ajouter les skills ci-dessous à un dépôt. Pour chacune,
notez qui peut la lancer (seulement une personne, ou aussi le modèle) et où elle
va (le projet ou votre propre dossier personnel). Écrivez ensuite le chemin du
dossier et la ligne d’en-tête que vous ajouteriez. Écrivez « aucune » quand les
réglages par défaut conviennent.

1. Une skill qui ouvre une pull request et demande aux deux responsables du code
   de la relire.
2. Vos propres règles pour formuler les messages de commit, que vous suivez dans
   chaque projet et que personne d’autre de l’équipe n’utilise.
3. Une skill qui explique ce que veut dire chaque code d’erreur des journaux de
   ce service, pour toute tâche où l’agent lit les journaux.
4. Une skill qui supprime les environnements de prévisualisation de l’équipe
   vieux de plus d’une semaine, sur le compte cloud partagé.

Un bon résultat : les skills 1 et 4 sont réservées à une personne, avec
`disable-model-invocation: true`, parce que toutes les deux agissent sur des
choses que d’autres personnes voient ou utilisent. Les skills 2 et 3 laissent le
modèle et n’ont pas besoin de ligne. La skill 3 pourrait aussi être réservée au
modèle avec `user-invocable: false`, puisque personne ne la tape comme une
commande. Les skills 1, 3 et 4 vont dans le dossier `.claude/skills/` du projet,
parce que l’équipe en a besoin pour ce code, et la skill 2 va dans
`~/.claude/skills/`. Sur quelle skill avez-vous hésité, et le doute portait-il
sur qui la lance ou sur qui l’a ?
</Exercise>

<Recap>
1. Dans Claude Code, une personne et le modèle peuvent tous les deux lancer une
   skill, sauf si l’en-tête dit autre chose. `disable-model-invocation: true` ne
   laisse que la personne, et `user-invocable: false` ne laisse que le modèle
   (@Claude Code skills).
2. Réservez une skill à une personne quand une exécution déploie, envoie, publie
   ou supprime. Une phrase dans la description est un conseil au modèle, et le
   champ est une règle que Claude Code impose.
3. Une skill que le modèle peut lancer a sa description dans chaque session. Une
   skill réservée à une personne ne coûte aucun contexte tant que personne ne
   tape son nom (@Claude Code skills). Pour une skill rarement utilisée, cette
   économie peut décider du choix, même quand la skill n’a pas d’effet de bord.
4. Une skill de projet est committée dans le dépôt et atteint toute l’équipe, et
   une skill personnelle dans votre dossier personnel n’atteint que vous, dans
   chaque projet. Quand les noms entrent en conflit, l’entreprise l’emporte sur
   le personnel, et le personnel sur le projet (@Claude Code skills).
5. Le format ouvert des skills n’a aucun champ pour qui lance une skill, donc
   vérifiez comment chaque produit le décide quand vous déplacez une skill
   (@Agent Skills spec).
</Recap>

<Habit id="person-only-before-commit">
Avant de committer une skill qui envoie, publie, déploie ou supprime quoi que ce
soit, vérifiez que son en-tête dit que seule une personne peut la lancer.
</Habit>
